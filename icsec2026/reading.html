ถ้ามีเวลาอ่านแค่ย่อหน้าเดียว

เราอยากรู้ว่าบอร์ด Jetson ตัวเดียวกัน รันโค้ดชุดเดียวกัน แต่เริ่มทดสอบตอนเครื่องเย็นกับตอนเครื่องเพิ่งทำงานหนักมา จะทำให้ด่านตรวจ performance ใน CI ตัดสิน “ผ่าน” หรือ “ไม่ผ่าน” ต่างกันหรือเปล่า เราเก็บข้อมูล 300 run บน Jetson AGX Xavier ที่ตรึงความถี่และปิดพัดลมไว้ โดยกำหนด threshold ของทุกด่านไว้ก่อนเก็บข้อมูล ผลที่ได้มีสองด้าน ด้านหนึ่ง พลังงานต่อ request ตอนเครื่องอุ่นสูงขึ้น 2.78–3.73% ในทุกเวอร์ชันของโปรแกรม และภายในแต่ละเวอร์ชัน ทุก run ตอนเครื่องอุ่นใช้พลังงานมากกว่าทุก run ตอนเครื่องเย็น อีกด้านหนึ่ง คำตัดสินของด่านกลับนับได้เท่ากันใน 15 จาก 16 กรณี กรณีเดียวที่ต่างคือ latency ของ variant ที่อยู่ใกล้ threshold ที่สุด คำอธิบายที่เราเห็นคือ baseline ที่วัดในสภาพความร้อนเดียวกันขยับขึ้นตามไปด้วย และผลด้านพลังงานอยู่ห่างเส้นตัดสินมากเมื่อเทียบกับความแกว่งระหว่าง run ข้อเสนอของเราจึงเป็นการวัด baseline ในสภาพเดียวกับ candidate และดูระยะห่างจากเส้นในหน่วยของความแกว่ง ซึ่งยังต้องพิสูจน์บนบอร์ดอื่นต่อ และต้องอ่านโดยรู้ว่าเรามีบอร์ดเดียว การจัดลำดับแบบบล็อกยังแยกอุณหภูมิออกมาเป็นสาเหตุไม่ได้ และการนับได้เท่ากันไม่ได้แปลว่าโอกาสเท่ากัน

บทความนี้ยาว เราแบ่งไว้ให้อ่านทีละช่วง ส่วนที่ 1–3 ปูพื้นและเล่าว่าทำไมเรื่องนี้น่าถาม ส่วนที่ 4–5 คือสิ่งที่เราทำและสิ่งที่พบ ส่วนที่ 6 ลงลึกเรื่องสถิติว่าแต่ละวิธีคืออะไรและทำไมเราเลือก ส่วนที่เหลือเป็นข้อจำกัด ข้อเสนอ บทเรียนจากหน้าเครื่อง และงานต่อไป ตัวเลขในวงเล็บเหลี่ยม เช่น [4] คือเอกสารอ้างอิงท้ายบทความ เลข [1]–[19] ตรงกับ reference ใน paper ส่วนเลขตั้งแต่ [20] เป็นเอกสารที่เราเพิ่มเพื่ออธิบายพื้นฐาน ใต้รูปทุกรูปมีบรรทัด “ที่มา” บอกว่าข้อมูลมาจากส่วนไหนของ paper มาจากบันทึกการเตรียมเครื่องของเรา หรือเป็นภาพประกอบเพื่ออธิบายแนวคิด และท้ายบทความมีตารางไล่ที่มาของตัวเลขทุกกลุ่ม

ส่วนที่ 1เริ่มจากเรื่องที่คุ้นเคย

1.1 โค้ดที่ยังตอบถูก แต่ทำงานแย่ลง

เวลาพูดถึงการทดสอบซอฟต์แวร์ คนส่วนใหญ่นึกถึงคำถามว่าโปรแกรมให้ผลถูกหรือเปล่า ใส่ภาพแมวเข้าไป โมเดลตอบว่าแมวไหม การทดสอบแบบนี้เรียกว่า functional test แต่ในงานจริง โปรแกรมที่ตอบถูกทุกข้ออาจแย่ลงได้ในแง่อื่น เช่น ตอบช้าลง ใช้หน่วยความจำมากขึ้น หรือกินไฟมากขึ้น คุณสมบัติกลุ่มนี้เรียกรวมว่า non-functional และเมื่อแก้โค้ดแล้วคุณสมบัติเหล่านี้แย่ลง เราเรียกว่า non-functional regression

บนอุปกรณ์ปลายทางอย่างกล้องอัจฉริยะ หุ่นยนต์ หรือโดรน ซึ่งเรียกรวม ๆ ว่าอุปกรณ์ edge ปัญหานี้หนักกว่าบนเซิร์ฟเวอร์ งานต้องเสร็จทันเฟรม และพลังงานมีจำกัด ตัวอย่างในรูปด้านล่างมาจากการทดลองของเราเอง เวอร์ชัน V2 ให้ label ตรงกับต้นฉบับทุกภาพ ถ้าดูแค่ functional test จะผ่านสบาย ๆ แต่ p95 latency ช้าลงราว 18% และพลังงานต่อ request เพิ่มราว 9%

ชื่อ V0 และ V2 ในรูปนี้จะเจออีกตลอดบทความ V0 คือโปรแกรมต้นฉบับ ส่วน V1–V4 คือเวอร์ชันที่เราตั้งใจทำให้แย่ลงทีละจุด เพื่อใช้เป็นกรณีที่รู้คำตอบล่วงหน้า แนวคิดเบื้องหลังอธิบายไว้เต็มในหัวข้อ 4.3

1.2 ด่านตรวจอัตโนมัติใน CI

Continuous integration หรือ CI คือแนวปฏิบัติที่ให้ระบบอัตโนมัติ build และทดสอบโค้ดทุกครั้งที่มีคนส่งการแก้ไขเข้ามา ถ้าผ่านจึงรวมเข้ากับโค้ดหลัก [20], [21] เครื่องที่ทำงานพวกนี้เรียกว่า runner ถ้างานต้องทดสอบบนฮาร์ดแวร์จริง เช่น บอร์ด Jetson ทีมมักต่อบอร์ดจริงเข้ากับระบบ CI เป็น self-hosted runner ที่รับงานต่อกันไปเรื่อย ๆ

สำหรับคุณสมบัติ non-functional ด่านตรวจในงานนี้เรียกว่า regression gate หลักการง่ายมาก ระบบวัดเวอร์ชันใหม่ที่เรียกว่า candidate แล้วเทียบกับเวอร์ชันอ้างอิงที่เรียกว่า baseline ถ้าเปลี่ยนไปเกินเกณฑ์ที่ตั้งไว้ (threshold) ก็ไม่ให้ผ่าน

relative change = 100 × (x ÷ b − 1) %x คือค่าที่วัดจาก candidate และ b คือค่า baseline (นิยามตาม paper หัวข้อ III-E)

ลองคิดเลขดูสักตัวอย่าง baseline ของเรามี p95 latency 1.550 ms ถ้า candidate วัดได้ 1.700 ms จะเปลี่ยนไป 100 × (1.700 ÷ 1.550 − 1) = +9.7% ยังไม่เกิน +10% จึงผ่าน แต่ถ้าวัดได้ 1.720 ms จะเป็น +11.0% และไม่ผ่าน สองค่านี้ต่างกันแค่ 0.02 ms แต่คำตัดสินกลับด้าน ทั้งบทความนี้คุยกันอยู่รอบเรื่องนี้ ด่านตอบได้แค่ผ่านหรือไม่ผ่าน แต่ค่าที่วัดได้ไม่เคยนิ่งสนิท

throughput ทำงานกลับทิศ baseline 668 request/s ถ้า candidate ทำได้ 600 request/s จะเปลี่ยน −10.2% ต่ำกว่า −10% จึงไม่ผ่าน ด่านทั้งสี่ของเรากำหนดไว้ก่อนเก็บข้อมูลและไม่เคยปรับเลย

1.3 วัดซ้ำแล้วได้ไม่เท่าเดิม

ใครเคยจับเวลาโปรแกรมเดิมหลาย ๆ รอบจะรู้ว่าตัวเลขไม่เคยออกมาเท่ากันเป๊ะ ระบบปฏิบัติการจัดคิวงานต่างไป cache อยู่ในสภาพต่างกัน มีการขัดจังหวะเข้ามา และในงานของเรา ชิปก็ร้อนไม่เท่ากัน งานด้าน performance evaluation พูดเรื่องนี้มานานแล้ว Mytkowicz และคณะแสดงว่าแม้แต่ปัจจัยที่ดูไม่เกี่ยว เช่น ขนาดของ environment variable ก็ทำให้ผลการวัดเอนได้ [22] หลายงานจึงเสนอให้รันซ้ำหลายครั้งและสรุปด้วยสถิติแทนตัวเลขครั้งเดียว [23], [24] ฝั่ง CI ก็มีงานที่พยายามจัดการ noise แบบนี้ในระบบจริง [1], [2], [3]

  • p95 ใน run หนึ่งมี 10,000 request ถ้าเรียงเวลาจากน้อยไปมาก p95 คือค่าแถว ๆ ตำแหน่งที่ 9,500 ใช้แทน “เวลาที่ผู้ใช้เกือบทุกคนได้รับ” และไวต่อการสะดุดมากกว่าค่าเฉลี่ย ในระบบที่ต้องตอบสนองเร็ว หางของการแจกแจงสำคัญพอ ๆ กับค่ากลาง [25]
  • SD หรือส่วนเบี่ยงเบนมาตรฐาน บอกว่าค่าแต่ละ run กระจายห่างค่ากลางแค่ไหน SD ที่สำคัญที่สุดในงานนี้คือ SD ของ % การเปลี่ยนแปลงระหว่าง run ซึ่งเราเรียกว่า σ
  • percentage point (pp) ใช้เมื่อเทียบค่าที่เป็นเปอร์เซ็นต์อยู่แล้ว จาก +8.8% เป็น +12.8% คือเพิ่ม 4.0 percentage points ไม่ใช่เพิ่ม 4% paper ใช้ทั้งสองคำ จึงควรแยกให้ออก

1.4 ระยะห่างจากเส้นตัดสิน

ลองเทียบกับการสอบดู สมมติเกณฑ์ผ่านคือ 50 คะแนน นักศึกษาที่ปกติได้ 80 คะแนนจะผ่านแทบทุกครั้งแม้วันนั้นจะง่วง ส่วนคนที่ปกติได้ 52 คะแนน วันดีก็ผ่าน วันแย่ก็ตก ผลสอบจะนิ่งแค่ไหนจึงขึ้นกับสองอย่างพร้อมกัน คือคะแนนปกติอยู่ห่างเกณฑ์เท่าไร และคะแนนแต่ละครั้งแกว่งมากน้อยแค่ไหน

ใน paper เราเรียกระยะนี้ว่า margin และวัดในหน่วยของ σ

margin = (τ − μ) ÷ s สำหรับด่านที่มีขอบบน (latency, energy, RAM)
margin = (μ − τ) ÷ s สำหรับ throughput ซึ่ง τ = −10%τ คือ threshold · μ คือค่าเฉลี่ยของมัธยฐานการเปลี่ยนแปลงในสภาพ cold และ warm · s คือ root-mean-square ของ SD ภายในแต่ละสภาพ · margin เป็นบวกแปลว่าค่ากลางอยู่ฝั่งผ่าน (paper หัวข้อ III-F)

ถ้ายอมสมมติว่าความแกว่งมีรูปทรงระฆังคว่ำ โอกาสที่ run หนึ่งจะข้ามเส้นประมาณได้จาก Φ(−margin) โดย Φ คือฟังก์ชันสะสมของการแจกแจงปกติมาตรฐาน ตัวเลขที่จำไว้ใช้ได้บ่อยคือ margin 0 ให้โอกาส 50% margin 1 ให้ราว 16% margin 2 ให้ราว 2.3% และ margin 3 ให้ราว 0.13% เราใช้ข้อนี้เป็นเครื่องมืออธิบาย ไม่ได้อ้างว่าข้อมูลเป็นระฆังคว่ำจริง

สองกรณีนี้เราจะกลับมาพูดถึงอีกหลายครั้ง ผลด้านพลังงานของ V2 อยู่ใต้เส้น 5.9 percentage points ส่วน latency ของ V1 อยู่ใต้เส้นแค่ 2.2 แต่ที่ต่างกันจริง ๆ คือความแกว่ง พลังงานแกว่งน้อยมาก 5.9 percentage points จึงเท่ากับราว 9 เท่าของ σ ขณะที่ 2.2 ของ latency เท่ากับไม่ถึง 2 เท่า

2.2 ความถี่ที่ขยับได้เอง

ตามค่าเริ่มต้น บอร์ดจะปรับความถี่ขึ้นลงเองตามภาระงานและความร้อน เทคนิคนี้เรียกว่า DVFS (dynamic voltage and frequency scaling) เอกสารของ NVIDIA ระบุว่าบน Xavier การปรับความถี่ของ GPU เปิดอยู่โดยปริยาย และ CPU ใช้ governor ชื่อ schedutil [26] DVFS ช่วยประหยัดไฟ แต่สำหรับการวัด performance มันคือตัวแปรที่ขยับเองโดยเราคุมไม่ได้ เราจึงใช้สคริปต์ jetson_clocks ซึ่งตั้งความถี่ของ CPU, GPU และ EMC ให้คงที่ที่ค่าสูงสุด [26] แล้วตรวจจาก telemetry อีกชั้นว่าความถี่ไม่หลุดจริง

2.3 ชิปที่ร้อนขึ้นกินไฟมากขึ้น

ต่อให้ความถี่คงที่ ทรานซิสเตอร์ที่ร้อนขึ้นจะมีกระแสรั่ว (leakage) มากขึ้น งานเดิมจึงใช้ไฟมากขึ้นเล็กน้อยเมื่อชิปร้อน [28] ตอนวางแผนเราจึงคาดว่าพลังงานจะเป็นตัวที่ไวต่อสภาพความร้อนที่สุด ส่วน latency ไม่น่าขยับมากเพราะความถี่ถูกตรึงแล้ว แต่กลไกจริงจะเป็น leakage หรือไม่ งานของเราไม่ได้พิสูจน์ แบบจำลองกำลังไฟขณะว่างในหัวข้อ 4.7 เป็นเพียงการปรับเชิงประจักษ์ ใน paper จึงเขียนไว้ชัดว่าไม่ได้ระบุว่าเป็น leakage

2.4 ชิปเย็นเร็ว แต่ฮีตซิงก์เย็นช้า

ความร้อนไหลจากตัวชิป (die) ไปที่ฮีตซิงก์ แล้วค่อยออกสู่อากาศ เมื่อปิดพัดลม ขั้นสุดท้ายช้ามาก ในบันทึกของเรา พฤติกรรมนี้เห็นเป็นสองจังหวะชัดเจน หลังหยุดโหลด die ร่วงลงราว 6 °C แทบทันที เพราะ die มีมวลความร้อนน้อย แล้วจากนั้นทั้งบอร์ดค่อย ๆ เย็นตามฮีตซิงก์แบบเลขชี้กำลัง ซึ่งเป็นรูปแบบเดียวกับแบบจำลองความร้อนแบบก้อนเดียว (lumped capacitance) ในตำราการถ่ายเทความร้อน [29]

สองจังหวะนี้อธิบายสิ่งที่เราเห็นตอนทดลองได้ เราให้โหลดจน zone ของ GPU อ่านได้ 54 °C แต่พอ run แบบ warm เริ่มจริง อ่านได้ราว 47 °C เพราะ die ร่วงลงหาอุณหภูมิของฮีตซิงก์ไปแล้ว ส่วนการรอให้ลงถึง 38 °C ต้องรอทั้งฮีตซิงก์ จึงนานกว่ามาก

จากหน้าเครื่อง

ตัวเลข 17 นาทีนี้มีผลกับการตั้งค่าโดยตรง รอบแรกเราตั้งเวลารอสูงสุดของ cold gate ไว้ 900 วินาที ซึ่งสั้นกว่าเวลาเย็นตัวจริง พอคำนวณจากเส้นนี้ก็รู้ว่าต้องขยายเป็น 1,800 วินาที ภายหลังเราวัดซ้ำในสภาพห้องอีกแบบได้ τ ราว 1,006 วินาที แปลว่าค่าคงที่เวลาขึ้นกับสภาพห้อง ควรวัดใหม่ทุกครั้งที่ย้ายที่หรือเปลี่ยนการปรับอากาศ

ส่วนที่ 3คำถามของเรามาจากไหน

3.1 runner ไม่ได้เริ่มจากศูนย์ทุกครั้ง

self-hosted runner รับงานตามคิว งานหนึ่งอาจมาถึงหลังบอร์ดว่างมาครึ่งชั่วโมง อีกงานอาจมาต่อจากงานที่เพิ่ง benchmark หนัก ๆ ไปหลายนาที ระบบ CI ทั่วไปไม่ได้บันทึกหรือควบคุมเรื่องนี้ สภาพความร้อนตอนเริ่มทดสอบจึงอยู่นอกการควบคุมของ pipeline โดยปริยาย

ถ้าความร้อนเปลี่ยนค่าที่วัดได้ ก็มีโอกาสเปลี่ยนคำตัดสินได้สองทาง ทางหนึ่งคือด่านไม่ให้ผ่านทั้งที่โค้ดไม่ได้แย่ลง ซึ่งเสียเวลานักพัฒนาและทำให้คนเลิกเชื่อด่าน อีกทางคือด่านปล่อยผ่านทั้งที่โค้ดแย่ลงจริง อาการแบบนี้คล้าย flaky test ที่ผลเปลี่ยนได้โดยโค้ดไม่เปลี่ยน [11], [12] แต่กลไกต่างกัน ในงานของเรา คำตัดสินมาจากอัตราส่วนตัวเลขที่ข้ามเส้น ไม่ได้มาจาก test ที่พึ่งลำดับการทำงานหรือทรัพยากรภายนอก

3.2 คนอื่นทำอะไรไว้แล้วบ้าง

ก่อนออกแบบการทดลอง เราไล่ดูงานที่ใกล้เคียง สรุปไว้ในตารางด้านล่าง ข้อสังเกตหลักคือมีงานที่ดูการวัดที่ขยับ และมีงานที่ดูว่า test จับ regression ได้หรือไม่ แต่ยังไม่มีงานที่ถามตรง ๆ ว่าคำตัดสินของด่านเปลี่ยนไหมเมื่อสภาพของเครื่องเปลี่ยน

3.3 สามชั้นที่คั่นระหว่างค่าที่วัดกับคำตัดสิน

เมื่ออ่านงานพวกนี้ครบ เราเห็นว่าคำถามว่า “ค่าที่วัดขยับไหม” กับ “คำตัดสินเปลี่ยนไหม” เป็นคนละคำถามกัน ด่านเทียบ run หนึ่งกับ baseline แล้วใช้ threshold ดังนั้นการวัดที่ขยับต้องผ่านสามชั้นก่อนจะกลายเป็นคำตัดสินที่เปลี่ยน

ชั้นแรกคือ baseline อาจขยับตามไปด้วย ถ้า baseline วัดในสภาพเดียวกัน ทั้งตัวตั้งและตัวหารสูงขึ้นพร้อมกัน การขยับก็หักล้างกันในอัตราส่วน ชั้นที่สองคือผลอาจอยู่ไกลจาก threshold ถ้า variant แย่ลง 3% และ threshold คือ 15% การขยับเพิ่มอีกหนึ่งเปอร์เซ็นต์ก็ยังไม่ถึงเส้น ชั้นที่สามคือถ้าผลอยู่ชิดเส้น ความแกว่งระหว่าง run อาจให้ทั้งผ่านและไม่ผ่านกับโค้ดชุดเดียวกัน จนผลของความร้อนจมหายไปใน noise

3.4 สิ่งที่เราคาดไว้ก่อนเริ่ม

ก่อนเก็บข้อมูล เราจดลำดับความเปราะบางที่คาดไว้ไว้ตั้งแต่ต้น คือ พลังงาน อุณหภูมิ throughput p95 latency หน่วยความจำ และความถูกต้อง เหตุผลคือกำลังไฟของ GPU บนบอร์ดนี้กว้างราว 11 เท่าระหว่างตอนว่างกับตอนโหลดเต็ม ขณะที่ latency ถูกตรึงด้วยความถี่คงที่ เราเล่าเรื่องนี้ไว้ตั้งแต่ตอนนี้เพราะผลออกมาไม่เป็นตามคาด และเราเขียนไว้ตรง ๆ ใน paper ว่าความคาดหวังนี้ไม่ได้รับการสนับสนุน

คำถามวิจัย

RQ1 latency, throughput, energy per request และ peak RAM ต่างกันอย่างไรระหว่างการเริ่มแบบ cold กับ warm

RQ2 ภายใต้ threshold ที่กำหนดไว้ก่อนเก็บข้อมูล อัตรา gate event (fail หรือ RAM alert) ที่สังเกตได้ต่างกันอย่างไรระหว่างสองสภาพนี้

4.1 ทำให้เครื่องเงียบก่อน

ถ้าอยากเห็นผลของความร้อน ต้องตัดสาเหตุอื่นของความแกว่งออกให้มากที่สุดก่อน นอกจากการตรึงความถี่ ปิด CPU idle states และปิดพัดลมตามตารางในหัวข้อ 2.1 เรายังปิด service พื้นหลังที่ไม่จำเป็นด้วย

จากหน้าเครื่อง

ระหว่างเตรียมเครื่อง เราพบ worker agent ของ Kubernetes ตัวหนึ่ง (k0s) ที่ติดตั้งไว้นอก package manager และรันอยู่เบื้องหลังโดยไม่มีใครนึกถึง พอปิดแล้ว หน่วยความจำขณะว่างลดจาก 3.9 GB เหลือ 0.33 GB ตั้งแต่นั้นเราใส่ quiet-host check ไว้หน้าทุก run คือต้องมี CPU ต่ำกว่า 10% และหน่วยความจำต่ำกว่า 1.5 GB ก่อนจึงจะเริ่มวัด (ตัวเลขทั้งหมดอยู่ใน paper หัวข้อ III-B ส่วนชื่อ k0s มาจากบันทึกของเรา)

มีข้อหนึ่งที่ต้องรู้ไว้ก่อนอ่านตัวเลขกำลังไฟ การวัดกำลังไฟขณะว่างก็ใช้การตั้งค่าเดียวกันนี้ คือความถี่ตรึงที่ค่าสูงสุดและปิด idle states ตัวเลขกำลังไฟทุกตัวของเราจึงรวม “พื้น” ที่สูงกว่าการใช้งานปกติไว้แล้ว ไม่ควรเอาค่าสัมบูรณ์ไปเทียบกับบอร์ดที่ตั้งค่าต่างกัน

workload คือโมเดลจำแนกภาพ MobileNetV2 [30] ที่ compile เป็น TensorRT engine ป้อนด้วย tensor สังเคราะห์ 500 ชุด ขนาด 3 × 224 × 224 ซึ่งสร้างซ้ำได้จาก seed ที่บันทึกไว้ หลัง warm-up 20 request แต่ละ run ประมวลผลชุดนี้ 20 รอบ รวม 10,000 request ใช้เวลา 14.65–26.21 วินาทีต่อ run เราเลือก tensor สังเคราะห์เพื่อให้ข้อมูลเข้าเหมือนกันทุก run และสร้างซ้ำได้ แลกกับการที่มันไม่ใช่ภาพธรรมชาติ

4.3 V0–V4 คืออะไร และทำไมต้องมี

ตัวอักษร V0 ถึง V4 ปรากฏตั้งแต่รูปแรกของบทความ หัวข้อนี้อธิบายว่ามันคืออะไร และทำไมการทดลองนี้ขาดมันไม่ได้

ต้องรู้คำตอบที่ถูกก่อน

สมมติเราอยากรู้ว่าเครื่องชั่งในร้านทองยังแม่นอยู่ไหมเมื่ออากาศร้อน เอาทองจริงมาชั่งไม่ช่วย เพราะเราไม่รู้ว่ามันหนักเท่าไรจริง วิธีที่ใช้กันคือชั่งตุ้มน้ำหนักมาตรฐานที่รู้ค่าอยู่แล้ว ทั้งตุ้มเบา ตุ้มที่ใกล้พิกัด และตุ้มที่เกินพิกัด แล้วดูว่าเครื่องยังอ่านถูกไหมเมื่อสภาพเปลี่ยน

คำถามของเราก็เป็นแบบเดียวกัน เราอยากรู้ว่า regression gate ตัดสินเหมือนเดิมไหมเมื่อเครื่องเย็นหรืออุ่น การจะตอบได้ เราต้องมีโค้ดที่รู้ล่วงหน้าว่าช้าลงหรือกินไฟมากขึ้นราวเท่าไร และควรถูกตัดสินอย่างไร ถ้าใช้ commit จริงจากโปรเจกต์ใดโปรเจกต์หนึ่ง เราจะไม่รู้ว่าแต่ละ commit แย่ลงเท่าไรจริง และ commit พวกนั้นก็ไม่ได้เรียงตัวอยู่ในระยะห่างจากเส้นที่เราต้องการทดสอบ เราจึงสร้างเวอร์ชันของโปรแกรมขึ้นมาเองให้เป็นเหมือนตุ้มน้ำหนักมาตรฐาน

V0 คือต้นฉบับ ส่วน V1–V4 คือสำเนาที่เปลี่ยนทีละจุด

V0 คือโปรแกรมต้นฉบับ ใช้ engine แบบ FP16 และทำหน้าที่เป็น baseline ส่วน V1–V4 เรียกว่า variant แต่ละตัวคือสำเนาของ V0 ที่ถูกแก้ เพียงจุดเดียว โดยเจตนาให้ทำงานแย่ลง การแก้จุดเดียวสำคัญมาก เพราะทำให้รู้ว่าผลที่เห็นมาจากอะไร แนวคิดการฉีด regression ที่รู้ขนาดเข้าไปในโค้ดไม่ใช่ของใหม่ งานของ Danglot และคณะใช้ mutation ฉีด energy regression เพื่อดูว่า test ของนักพัฒนาจับได้ไหม [7] แต่จุดประสงค์ของเราต่างออกไป เราใช้ variant เป็นกรณีที่รู้คำตอบล่วงหน้า เพื่อดูว่าคำตัดสินของด่านยังเหมือนเดิมไหมเมื่อสิ่งเดียวที่เปลี่ยนคือสภาพความร้อนตอนเริ่ม

แต่ละ variant เลียนแบบความผิดพลาดที่เจอได้ในโค้ดทั่วไป

  • V1 ทำ normalization ซ้ำฝั่ง host ก่อนส่งข้อมูลเข้าโมเดล CPU ต้องทำงานคำนวณเพิ่มกับทุก request โดยผลลัพธ์ไม่เปลี่ยน เหมือนโค้ดที่มีคนเพิ่มขั้นตอนเตรียมข้อมูลซ้ำโดยไม่รู้ว่ามีอยู่แล้ว
  • V2 เปลี่ยน post-processing บางส่วนเป็น loop แบบ interpreted คือแทนที่จะสั่งให้ไลบรารีคำนวณทั้งก้อนในครั้งเดียว กลับวนทีละค่าในภาษา interpreted เปรียบได้กับการนับเหรียญทีละเหรียญแทนการเอาไปชั่งทั้งถุง ได้คำตอบเท่ากันแต่ช้ากว่ามาก
  • V3 คัดลอกข้อมูลจาก host ไป device เพิ่ม บน Jetson แม้ CPU กับ GPU จะใช้ DRAM ชุดเดียวกัน [46] การสั่งคัดลอกระหว่างบัฟเฟอร์ก็ยังต้องอ่านและเขียนข้อมูลซ้ำจริง จึงเสียทั้งเวลาและพลังงาน
  • V4 เปลี่ยน engine จาก FP16 เป็น FP32 ตัวเลขทศนิยมยาวขึ้นเท่าตัว โดยทั่วไปทำให้ GPU คำนวณช้าลงและเคลื่อนย้ายข้อมูลมากขึ้น ผลลัพธ์จึงไม่เหมือน V0 เป๊ะ top-1 ต่างจาก label ของ V0 อยู่ 1.0% ต้องย้ำว่า “ต่างจาก V0” ไม่ได้แปลว่า “ผิด” เพราะเราใช้ label ของ V0 เป็นตัวอ้างอิง

ทำไมต้องมีสี่ตัว

ย้อนไปที่สามชั้นในหัวข้อ 3.3 ผลจะเปลี่ยนคำตัดสินหรือไม่ ขึ้นกับว่ามันอยู่ห่างเส้นแค่ไหน ถ้าทุก variant อยู่ไกลเส้นหมด เราจะเห็นแต่คำตัดสินที่นิ่ง และสรุปผิด ๆ ว่าความร้อนไม่เคยมีผล ถ้าทุกตัวอยู่ชิดเส้นหมด ผลจะจมอยู่ใน noise จนอ่านอะไรไม่ออก เราจึงออกแบบให้ variant เรียงกันเป็นบันได ตั้งแต่ใกล้เส้นฝั่งผ่าน เลยเส้นไปเล็กน้อย เลยเส้นชัดเจน จนถึงเลยไปไกลมาก

บันไดนี้ออกแบบบนแกน latency เพราะตอนวางแผนเราคิดว่าเป็นจุดที่ความร้อนน่าจะพลิกคำตัดสินได้ง่ายที่สุด ความแรงของ V1 และ V2 จึงถูก calibrate ใน pilot ให้คร่อมเส้น +10% (pilot ได้ +6.2% และ +16.1% ผลจริงในการทดลองหลักคือ +7.8% และ +18.2%) บน metric อื่น ตำแหน่งของแต่ละ variant ต่างกันไปเองตามธรรมชาติของการเปลี่ยนแปลง เช่น พลังงานของ V1 และ V2 อยู่ใต้เส้น +15% (+3.7% และ +9.1%) ส่วน peak RAM มีแค่ V4 ที่เกิน +20% ผลคือ 4 variant × 4 metric ให้ 16 กรณีที่กระจายตั้งแต่ไกลเส้นฝั่งผ่าน ใกล้เส้น ไปจนถึงไกลเส้นฝั่งไม่ผ่าน ซึ่งเป็นสิ่งที่เราต้องการเพื่อทดสอบกรอบสามชั้น

ข้อที่เรายอมรับใน paper คือไม่มี variant ตัวไหนเล็งไว้ที่ threshold ของพลังงาน และ threshold ทั้งสี่ไม่เคยถูกปรับเพื่อให้เข้ากับ variant อีกเรื่องที่ต้องชั่งคือเวลาเครื่อง ทุกเวอร์ชันที่เพิ่มหมายถึงอีก 60 run (30 run × 2 สภาพ) บนบอร์ดเดียว

V0 กับ V4 คือตัวควบคุม

ชุดตรวจ ATK มีขีด C ไว้บอกว่าชุดตรวจทำงาน ถ้าขีด C ไม่ขึ้น ผลทั้งชุดเชื่อไม่ได้ การทดลองของเราก็มีตัวควบคุมแบบเดียวกันสองตัว

V0 เป็น negative control เราเอา run ของ V0 แต่ละ run มาตัดสินเทียบกับ V0 run อื่นที่เหลือ (leave-one-out) ถ้าด่านตัดสินว่าโค้ดเดิมแย่ลง แปลว่าด่านตกใจเกินเหตุ ผลคือไม่พบ false positive ของด่าน metric ใดเลย ภายใต้นโยบาย baseline ทุกแบบ

V4 เป็น positive control มันแย่ลงชัดจนทุกด่านควรจับได้ ถ้าจับไม่ได้ แปลว่าเครื่องมือวัดหรือสคริปต์มีปัญหา ผลคือ V4 ไม่ผ่านทุกด่านในทุก run ทั้งสองสภาพ เป็นตัวเดียวที่ข้ามเส้น RAM และการตรวจความถูกต้องแบบเข้มงวดก็จับความต่างของ label ได้ตามคาด

ทำไม V1–V3 ต้องให้คำตอบเหมือนเดิม

เพราะปัญหาที่เราสนใจคือโค้ดที่ผ่าน functional test แต่แย่ลงด้าน non-functional ตามที่เล่าในหัวข้อ 1.1 ถ้า variant เปลี่ยนคำตอบด้วย functional test จะจับได้ก่อนถึงด่าน performance และเราจะแยกไม่ออกว่ากำลังวัดเรื่องอะไร เราจึงตรวจทุก run ที่ไม่ใช่ V0 เทียบกับ label อ้างอิงชุดเดียวของ V0 (oracle) ผลคือ V0–V3 ให้ digest ของ label ชุดเดียวกันทั้ง 240 run V4 นับเป็น run ที่ใช้ได้ถ้า top-1 ต่างไม่เกิน 1% ซึ่งเป็นเกณฑ์คนละตัวกับการตรวจแบบเข้มงวดที่ V4 ไม่ผ่าน

จากหน้าเครื่อง

การ calibrate ความแรงของ variant สอนเราเรื่องหนึ่ง ใน pilot รอบแรกที่ไม่ได้รอให้เครื่องเย็นตามขั้นตอน ผลของ variant ออกมาสูงเกินจริง 1.4–7.5 เท่าเมื่อเทียบกับตอนทำตามขั้นตอนครบ (จากบันทึกของเรา ไม่อยู่ใน paper) บทเรียนคือ pilot ต้องใช้ขั้นตอนเตรียมเครื่องเดียวกับการทดลองจริง ไม่อย่างนั้นตัวเลขที่ได้ไปตั้งความแรงจะเพี้ยนตั้งแต่ต้น

ข้อจำกัดของแนวทางนี้คือ variant ที่สร้างขึ้นเองอาจไม่เป็นตัวแทนของ regression ในโปรเจกต์จริงทั้งหมด เราจึงระบุไว้เป็น external threat ในส่วนที่ 7

4.4 ทำให้เครื่องเย็นหรืออุ่นตามที่ต้องการ

ก่อนทุก run ระบบอ่านอุณหภูมิของ thermal zone ชื่อ GPU-therm สภาพ cold คือรอจน zone นี้เย็นลงถึง 38 °C หรือต่ำกว่า สภาพ warm คือให้โหลด TensorRT สังเคราะห์จน zone ถึง 54 °C และให้โหลดซ้ำทุกครั้งที่ลดลงต่ำกว่า 52 °C ทั้งสองแบบเป็นการเตรียมก่อน run แต่ละ run ไม่ใช่เตรียมครั้งเดียวต่อบล็อก

จากหน้าเครื่อง

เวอร์ชันแรกของสคริปต์เอาค่าสูงสุดของทุก thermal zone มาใช้ ซึ่งดูเหมือนปลอดภัยกว่า แต่บนบอร์ดนี้มีเซนเซอร์ของ PMIC (zone ชื่อ PMIC-Die) ที่อ่านค่า 50 °C คงที่ตลอดเวลา ค่าสูงสุดจึงไม่เคยต่ำกว่า 50 °C และไม่ได้สะท้อนอุณหภูมิของ GPU เลย ผลคือ cold gate หยุดทำหน้าที่ไปโดยไม่มีอะไรเตือน (paper ใช้คำว่า silently disable) เราจึงเปลี่ยนเป็นอ่าน zone ตามชื่อ

เพราะ setpoint (54 และ 38 °C) ต่างจากค่าที่เกิดขึ้นจริง (ราว 47 และ 38 °C) ใน paper เราจึงอธิบายสภาพด้วยอุณหภูมิเริ่มต้นที่วัดได้ ไม่ใช้ setpoint ความต่างที่เกิดจริงคือ 9 °C ไม่ใช่ 16 °C ข้อนี้ทำให้ผลของเรามีขอบเขตชัดเจน เรากำลังพูดถึงความต่างระหว่างการเริ่มแบบเย็นกับการเริ่มหลังงานหนัก ซึ่งยังห่างจากช่วงที่บอร์ดเริ่มลดความถี่เพื่อป้องกันตัวเองมาก เอกสารของ NVIDIA ระบุว่า zone GPU-therm จะเริ่มลดความถี่เมื่อข้าม passive trip point ชื่อ gpu-sw-throttle ที่ 92.5 °C [26] ขณะที่อุณหภูมิสูงสุดที่เราบันทึกระหว่าง run คือ 53.5 °C

4.5 ลำดับการรัน

การทดลองหลักมี 5 เวอร์ชัน × 2 สภาพ × 30 run = 300 run เก็บใน 232 นาที run ทั้ง 150 run ของแต่ละสภาพถูกสลับลำดับด้วย seed ที่บันทึกไว้ แล้วแบ่งเป็นสามบล็อก บล็อกละ 50 run ทำให้ในหนึ่งบล็อกมี run ของเวอร์ชันหนึ่ง ๆ ได้ตั้งแต่ 4 ถึง 14 run บล็อก cold กับ warm สลับกัน โดยเริ่มจาก cold

ทำไมไม่สุ่มสภาพทีละ run ซึ่งเป็นแบบที่ตำราแนะนำ เหตุผลเชิงปฏิบัติคือการสลับจาก warm ไป cold แต่ละครั้งต้องรอให้ทั้งบอร์ดเย็นลงหลายนาทีตามที่เล่าในหัวข้อ 2.4 ถ้าสลับทุก run เวลาทดลองจะยืดออกมาก แต่ราคาที่จ่ายก็ชัดเจน ในแบบนี้ cold กับ warm ไม่ได้ต่างกันแค่ความร้อน ยังต่างกันที่วิธีเตรียม (รอให้เย็นกับให้โหลด) เวลา (ในแต่ละคู่บล็อก cold มาก่อน) และลำดับ (เรียงตายตัว) ในทางระเบียบวิธีเรียกว่า confounding นอกจากนี้ run ที่อยู่บล็อกเดียวกันยังไม่อิสระต่อกันเต็มที่ ซึ่งเป็นปัญหาที่ Hurlbert เรียกว่า pseudoreplication [31] เราจึงพูดได้แค่ว่าผลที่พบ สัมพันธ์กับสภาพตอนเริ่ม ไม่ได้พูดว่าอุณหภูมิเป็นสาเหตุ และเรียกช่วงความเชื่อมั่นทุกช่วงว่า nominal (รายละเอียดในหัวข้อ 6.10)

4.6 วัดพลังงานอย่างไร

เวลาของแต่ละ request นับรวม preprocessing, inference และ postprocessing throughput คือจำนวน request ที่เสร็จหารด้วยผลรวมเวลาของ request ส่วนพลังงานใช้เวลาจริงของ workload ทั้งก้อน (wall time) ซึ่งวัดแยกต่างหาก ไม่ได้อนุมานจากอัตราการสุ่มตัวอย่าง

กำลังไฟมาจากหกช่องของ tegrastats (GPU, CPU, SOC, CV, VDDRQ, SYS5V) ที่ 10 Hz ค่าเริ่มต้นของ tegrastats คือทุก 1,000 ms และปรับได้ด้วยตัวเลือก --interval [27] แต่ละช่องเฉลี่ยเฉพาะช่วง workload โดยตัดหัวและท้ายออกอย่างละ 1 วินาที เพราะ timestamp ของ log ละเอียดแค่ระดับวินาที จากนั้นจึงรวมค่าเฉลี่ยทั้งหกช่อง

Ereq = P̄window × twall ÷ NP̄ คือกำลังไฟเฉลี่ยรวม (W) · twall คือเวลาจริงของ workload (s) · N = 10,000 request · ได้หน่วยจูลต่อ request ซึ่ง paper รายงานเป็น mJ (หัวข้อ III-D)

4.7 หักไฟขณะว่างออก

ถ้าเครื่องที่ร้อนกินไฟมากขึ้นแม้ไม่ได้ทำงานอะไร พลังงานที่เพิ่มในสภาพ warm บางส่วนอาจเป็นแค่พื้นที่ยกตัวขึ้น เพื่อดูว่าผลยังอยู่หลังหักส่วนนี้ เราวัดกำลังไฟขณะว่างสี่จุดระหว่าง 34 ถึง 49 °C แล้ว fit เส้นตรง

ต้องบอกให้ชัดว่านี่เป็นการปรับเชิงประจักษ์ มันไม่ได้แยกพลังงานของ workload ออกมาจริง ไม่ได้พิสูจน์ว่าเป็น leakage และไม่ได้ส่งต่อความไม่แน่นอนของเส้นที่ fit จากแค่สี่จุด เราใช้มันเป็น sensitivity analysis เท่านั้น

4.8 จะเทียบกับ baseline ตัวไหน

ตอนออกแบบ คำถามนี้ดูเป็นรายละเอียดเล็ก ๆ แต่สุดท้ายกลายเป็นตัวแปรสำคัญที่สุดตัวหนึ่งของงาน เราใช้ baseline สามแบบ ตามรูปด้านล่าง

5.2 ค่าที่วัดเปลี่ยนไหม (RQ1)

พลังงานเป็น metric เดียวที่การแจกแจงของ cold กับ warm ไม่ทับกันเลย ในทุกเวอร์ชัน run แบบ warm ใช้พลังงานต่อ request มากกว่าทุก run แบบ cold ค่าที่ใช้บอกเรื่องนี้คือ Cliff's δ ซึ่งเท่ากับ 1.00 แปลตรง ๆ ว่าจับคู่ warm กับ cold แบบไหน warm ก็สูงกว่าทุกคู่ (รายละเอียดในหัวข้อ 6.2) มัธยฐานสูงกว่า 2.78–3.73% และช่วง bootstrap ทุกช่วงอยู่ระหว่าง +2.4% ถึง +4.1% กำลังไฟรวมจากเซนเซอร์ก็ให้ภาพเดียวกัน

5.5 ทำไมพลังงานขยับ แต่คำตัดสินไม่เปลี่ยน

ผลข้อนี้ทำให้เราต้องกลับไปคิดใหม่ เพราะมันขัดกับที่คาดไว้ตรง ๆ พลังงานเป็น metric ที่ขยับชัดที่สุด แต่คำตัดสินด้านพลังงานไม่เปลี่ยนเลย คำอธิบายมีสามข้อ ซึ่งตรงกับสามชั้นในหัวข้อ 3.3

ข้อแรก baseline ในสภาพเดียวกันหักล้างการขยับ

ใน run แบบ warm ทั้ง V2 และ V0 ใช้พลังงานมากขึ้นพร้อมกัน อัตราส่วนระหว่างสองตัวจึงแทบไม่ขยับ ลองดูว่าจะเกิดอะไรถ้าเราใช้ baseline ที่วัดตอน cold ครั้งเดียวแล้วใช้กับทุก run แบบที่ทีมจำนวนมากทำกันจริง

ตัวเลขนี้บอกเราสองเรื่อง เรื่องแรก baseline ที่ไม่ตรงสภาพดันผลไปทางไม่ผ่านจริง เรื่องที่สอง ในการทดลองนี้มันยังไม่ถึงขั้นเปลี่ยนคำตัดสิน เพียงเพราะ V2 เริ่มต้นห่างเส้นพอสมควร ถ้ามี variant ด้านพลังงานที่อยู่ใกล้เส้นกว่านี้ ผลอาจออกมาอีกแบบ ซึ่งเป็นเหตุผลที่เราใส่เรื่องนี้ไว้ในงานต่อไป

ข้อสอง ผลด้านพลังงานอยู่ไกลเส้นตัดสิน

ข้อสาม พลังงานแกว่งน้อยที่สุด

สามข้อนี้รวมกันทำให้ความคาดหวังของเราที่ว่าพลังงานจะเป็นด่านที่เปราะที่สุดไม่ได้รับการสนับสนุนที่ threshold ชุดนี้ ค่าความเปราะบาง F = |RD| เฉลี่ยข้ามสี่ variant เป็นศูนย์สำหรับพลังงาน throughput และ RAM และเป็น 0.0083 สำหรับ latency (คือ 0.033 ของ V1 หารสี่) การที่กำลังไฟกว้าง 11 เท่าระหว่างว่างกับโหลดเต็มไม่ได้บอกล่วงหน้าว่า energy gate จะเปราะ

มีสิ่งหนึ่งที่เราต้องระวังไม่ให้ตัวเองสรุปเกิน ผลนี้ไม่ได้แปลว่า latency gate เปราะกว่าโดยธรรมชาติ V1 เปราะเพราะเราตั้งใจ calibrate ให้มันอยู่ใกล้ threshold ของ latency ตั้งแต่แรก ถ้าเราตั้ง variant ด้านพลังงานไว้ใกล้เส้นแบบเดียวกัน ภาพอาจกลับด้าน หัวข้อถัดไปมีหลักฐานว่าอาจเป็นเช่นนั้นจริง

5.6 ถ้าเส้นตัดสินอยู่ชิดผลพอดี

หลัง review เราทำการตรวจเพิ่มเติมแบบ post hoc ข้อหนึ่ง พลังงานแกว่งน้อย จึงแปลว่าถ้า threshold อยู่ใกล้ผล การขยับเพียงเล็กน้อยก็มีผล เราลองวาง energy threshold ไว้ที่ผลรวม (pooled effect) ของ V2 คือ +9.06% ซึ่งเป็นตำแหน่งที่ไวที่สุด

ผลนี้ไม่ได้บอกว่าสภาพ warm ทำให้ผ่านง่ายขึ้น ส่วนต่าง 0.50 percentage points ที่เหลือกลับทิศในหนึ่งจากสามคู่บล็อก (exact p ระดับบล็อก = 0.30) จึงอาจมาจากความแกว่งของ baseline ระหว่างบล็อกเท่านั้น สิ่งที่มันบอกคือ ใกล้ threshold แม้ baseline ตรงสภาพแล้ว ส่วนต่างเล็ก ๆ ที่เหลือก็เปลี่ยนคำตัดสินด้านพลังงานได้มาก ข้อเสนอในส่วนที่ 8 จึงให้ดูทั้ง baseline และ margin ไม่ใช่ข้อใดข้อหนึ่ง

5.7 การทดลองเสริมที่ขอบ latency threshold

ผลของการทดลองเสริม (หัวข้อ 4.10) ยืนยันภาพเดียวกันจากอีกมุมหนึ่ง variant ตัวนี้มีมัธยฐาน latency regression +9.390% ตอน cold และ +9.551% ตอน warm คือต่ำกว่า +10% อยู่ 0.61 และ 0.45 percentage points จาก 60 run มี 38 run ที่อยู่ภายใน 1 percentage point ของ threshold margin คือ 0.62σ อุณหภูมิเริ่มต้นอยู่ที่ 38.0–38.5 °C สำหรับ cold และ 47.0–48.5 °C สำหรับ warm

ข้อที่เราอยากให้จำจากการทดลองนี้คือ variant ที่มัธยฐานอยู่ใต้ threshold ยังไม่ผ่าน 30% ของ run และสูตร Φ(−0.62) ทำนายไว้ 0.27 ใกล้กับที่เห็นจริง ที่ขอบ threshold ความแกว่งระหว่าง run กลบผลของสภาพจนมองไม่เห็น เมื่อตัดบล็อกออกทีละคู่ RD อยู่ระหว่าง −0.15 ถึง +0.15 และช่วงที่กว้างทำให้เรายังตอบไม่ได้ว่าสภาพมีผลหรือไม่ ตัวเลข 5.3 เท่าเป็นเพียงการเทียบเชิงพรรณนา เพราะช่วงของการขยับคร่อมศูนย์

6.1 ใช้ Mann–Whitney U แทน t-test

t-test เป็นเครื่องมือแรกที่หลายคนนึกถึงเวลาเทียบสองกลุ่ม แต่มันเทียบค่าเฉลี่ย และไวต่อข้อมูลที่เบ้หรือมีค่าโดด ซึ่งเป็นลักษณะปกติของข้อมูลเวลาและพลังงาน Mann–Whitney U ใช้อันดับแทนค่าดิบ [37] วิธีคิดที่ง่ายที่สุดคือจับคู่ทุก run แบบ warm กับทุก run แบบ cold ได้ 30 × 30 = 900 คู่ แล้วนับว่ามีกี่คู่ที่ warm สูงกว่า จำนวนนี้คือ U ถ้าสองกลุ่มไม่ต่างกัน U ควรอยู่แถว ๆ 450

เราทดสอบ 20 ครั้ง (4 metric × 5 เวอร์ชัน) แบบสองทาง ใช้ normal approximation พร้อมการแก้ค่าที่ซ้ำกันและ continuity correction สำหรับพลังงาน warm สูงกว่าครบทั้ง 900 คู่ในทุกเวอร์ชัน

ข้อที่ต้องระวังคือ p-value บอกว่าสองกลุ่มต่างกันหรือไม่ แต่ไม่บอกว่าต่างมากแค่ไหน เราจึงรายงานคู่กับ Cliff's δ และ median shift เสมอ และการทดสอบนี้สมมติว่า run แต่ละ run อิสระต่อกัน ซึ่งไม่จริงเต็มที่ในแบบการทดลองของเรา (หัวข้อ 6.10)

6.2 บอกขนาดของความต่างด้วย Cliff's δ

Cliff's δ ต่อยอดจากการนับคู่แบบเดียวกัน [16] คือเอาจำนวนคู่ที่ warm สูงกว่า ลบจำนวนคู่ที่ warm ต่ำกว่า แล้วหารด้วยจำนวนคู่ทั้งหมด ค่าอยู่ระหว่าง −1 ถึง +1 ถ้าเป็น +1 แปลว่าทุก run แบบ warm สูงกว่าทุก run แบบ cold ถ้าเป็น 0 แปลว่าแยกไม่ออก และค่านี้สัมพันธ์ตรงกับ U คือ δ = 2U ÷ (n₁n₂) − 1 เมื่อนับคู่ที่เท่ากันเป็นครึ่ง

เราชอบ δ เพราะไม่ขึ้นกับหน่วย ใช้เทียบข้าม metric ได้ และแปลเป็นภาษาคนได้ทันที ในงานนี้พลังงานได้ δ = 1.00 ทุกเวอร์ชัน latency อยู่ระหว่าง −0.39 ถึง −0.02 throughput +0.03 ถึง +0.46 และ peak RAM −0.90 ถึง +0.64 แต่ต้องระวังว่า δ = 1 บอกว่าแยกกันสนิท ไม่ได้บอกว่าห่างกันมาก พลังงานของเราแยกกันสนิทแต่ต่างกันแค่ราว 3% ข้อมูลที่แกว่งน้อยจะได้ δ สูงได้ง่าย จึงต้องอ่านคู่กับ median shift

6.3 ช่วงความเชื่อมั่นของมัธยฐานด้วย bootstrap

มัธยฐานไม่มีสูตรความคลาดเคลื่อนมาตรฐานที่ใช้ง่ายแบบค่าเฉลี่ย bootstrap แก้ปัญหานี้ด้วยการให้คอมพิวเตอร์ทำงานแทนสูตร [38] เราสุ่ม run จากข้อมูลจริงแบบใส่คืนให้ได้จำนวนเท่าเดิม บาง run ถูกเลือกซ้ำ บาง run ไม่ถูกเลือก คำนวณผลต่างของมัธยฐาน ทำซ้ำหลายพันครั้ง แล้วใช้เปอร์เซ็นไทล์ที่ 2.5 และ 97.5 ของผลทั้งหมดเป็นช่วง 95%

ใน RQ1 เราใช้ 10,000 รอบ ช่วงของผลต่างพลังงานทุกเวอร์ชันอยู่ระหว่าง +2.4% ถึง +4.1% ในการทดลองเสริมได้ [−0.47, +0.82] ซึ่งคร่อมศูนย์ และใน sensitivity check เราสุ่ม V0 ที่ใช้คำนวณ baseline ของแต่ละบล็อกซ้ำ 2,000 รอบ ข้อจำกัดคือการสุ่มระดับ run ถือว่า run อิสระต่อกัน จึงมองไม่เห็นความแกว่งระหว่างบล็อก และกับตัวอย่าง 30 ค่า ช่วงแบบ percentile อาจครอบคลุมได้ไม่ครบ 95% จริง

6.4 ทดสอบ 20 ครั้งจึงต้องปรับด้วย Holm

ถ้าทดสอบ 20 ครั้งที่ระดับ 0.05 และไม่มีความต่างจริงเลย เราคาดว่าจะเจอผลที่ดูมีนัยสำคัญโดยบังเอิญราวหนึ่งครั้ง วิธีของ Holm [17] แก้ปัญหานี้โดยเรียง p-value จากน้อยไปมาก ตัวแรกต้องต่ำกว่า 0.05 ÷ 20 ตัวที่สองต่ำกว่า 0.05 ÷ 19 และไล่ไปเรื่อย ๆ จนกว่าจะเจอตัวที่ไม่ผ่านจึงหยุด วิธีนี้คุมโอกาสที่จะมีผลบังเอิญแม้แต่ตัวเดียวในทั้งชุด โดยไม่ต้องสมมติความสัมพันธ์ระหว่างการทดสอบ และมีกำลังไม่น้อยกว่า Bonferroni เสมอ

ใน RQ1 หลังปรับแล้ว พลังงานมีนัยสำคัญทั้งห้าเวอร์ชัน peak RAM ทั้งห้า throughput เฉพาะ V2 และ latency ไม่มีเลย ใน RQ2 เราปรับ Fisher's exact test 16 ครั้ง ข้อที่ต้องระวังคือการไม่มีนัยสำคัญไม่ได้แปลว่าไม่มีผล และการกำหนดว่าอะไรอยู่ใน “ชุด” เป็นการตัดสินใจของผู้วิจัย ในงานนี้ sensor power และ incremental energy อยู่นอกชุด 20 การทดสอบ

6.5 นับได้ 0 จาก 30 แปลว่าอะไร (Wilson และ Newcombe)

นี่เป็นหัวข้อที่เราใช้เวลาคิดนานที่สุด เพราะข้อมูล RQ2 ของเราเกือบทั้งหมดเป็น 0/30 หรือ 30/30 ช่วงความเชื่อมั่นแบบที่สอนในวิชาสถิติเบื้องต้น (Wald: p̂ ± 1.96·SE) ใช้ไม่ได้เลยในกรณีนี้ เพราะเมื่อ p̂ = 0 ค่า SE ก็เป็นศูนย์ ได้ช่วงกว้างศูนย์ ซึ่งเท่ากับอ้างว่ารู้ค่าจริงแน่นอนทั้งที่ทดลองแค่ 30 ครั้ง

ทางออกคือช่วงแบบ Wilson score [39] ซึ่งยังให้ช่วงที่สมเหตุสมผลแม้นับได้ศูนย์ สำหรับ 0/30 ช่วง Wilson คือ [0, 0.114] สอดคล้องกับกฎ 3 ÷ n ที่เล่าไว้ในหัวข้อ 5.4 ส่วนผลต่างของสองสัดส่วน เราใช้วิธี hybrid score ของ Newcombe ซึ่งเอาช่วง Wilson ของแต่ละสัดส่วนมารวมกัน และเป็นหนึ่งในวิธีที่ทำงานได้ดีกับตัวอย่างเล็กจากการเปรียบเทียบ 11 วิธีของเขา [18] ผลที่ได้คือ 15 กรณีที่นับเท่ากันมี RD = 0 ช่วง [−0.114, +0.114] V1 latency มี RD = −0.033 ช่วง [−0.167, +0.083] และการทดลองเสริมมี RD = 0 ช่วง [−0.223, +0.223]

ข้อที่ต้องระวังมีสองข้อ ช่วงเหล่านี้ไม่ได้ปรับ multiplicity และถือว่า run อิสระต่อกัน ที่ต้องระวังยิ่งกว่านั้นคือ การนับได้เท่ากันไม่ได้แปลว่าเท่ากัน ถ้าอยากอ้างว่าสองสภาพให้คำตัดสินเทียบเท่ากัน ต้องกำหนดขอบที่ยอมรับได้ไว้ล่วงหน้าแล้วทำ equivalence test [36] ซึ่งงานนี้ไม่ได้ทำ

6.6 Fisher's exact test

สำหรับตาราง 2 × 2 (สภาพ × ข้าม / ไม่ข้าม) Fisher's exact test คำนวณความน่าจะเป็นแบบแม่นตรงว่า ถ้าสภาพไม่มีผลเลย จะได้การแบ่งแบบที่เห็นหรือสุดโต่งกว่าบ่อยแค่ไหน [40] เราเลือกวิธีนี้เพราะจำนวนนับน้อยมาก การประมาณแบบ chi-square ใช้ไม่ได้ V1 latency (1/30 กับ 0/30) ได้ p = 1.0 หลังปรับ Holm และการทดลองเสริม (9/30 กับ 9/30) ได้ p = 1.0 แบบไม่ปรับ กับตัวอย่างเล็ก วิธีนี้ค่อนข้างอนุรักษ์นิยม และ p = 1.0 ไม่ได้บอกว่าสองอัตราเท่ากัน บอกแค่ว่าข้อมูลไม่มีหลักฐานว่าต่าง

6.7 เรื่องของ Firth model ที่เราลดชั้น

หัวข้อนี้เราเล่าละเอียดเพราะเป็นการเปลี่ยนแผนหลังเห็นข้อมูล ซึ่งผู้อ่านควรรู้ แผนวิเคราะห์ที่เราเขียนหลังเก็บข้อมูลเลือก logistic regression แบบ Firth เป็นการวิเคราะห์หลักตั้งแต่แรก logistic regression ทำนายโอกาสที่ run จะข้าม threshold จากตัวแปรอย่างสภาพและอุณหภูมิเริ่มต้น ปัญหาที่เจอบ่อยกับข้อมูลแบบเราคือ separation เมื่อทุก run ในกลุ่มหนึ่งไม่ข้ามเลยหรือข้ามทุก run ค่าประมาณแบบ maximum likelihood จะวิ่งไปที่อนันต์ วิธีของ Firth [19] เติม penalty เข้าไปใน likelihood ทำให้ได้ค่าประมาณที่จำกัดและ bias น้อยลง และถูกเสนอให้เป็นทางแก้มาตรฐานของ separation [41] มันจึงดูเหมาะในตอนแรก

ปัญหาโผล่ตอนเราดูข้อมูลจริง สภาพกับอุณหภูมิเริ่มต้นแทบเป็นตัวแปรเดียวกัน เพราะ cold เริ่มราว 38 °C และ warm เริ่มราว 47 °C เสมอ สหสัมพันธ์คือ r = 0.986 อาการนี้เรียกว่า collinearity ตัวชี้วัดที่ใช้กันคือ variance inflation factor หรือ VIF = 1 ÷ (1 − R²) โดย R² มาจากการทำนายตัวแปรหนึ่งด้วยตัวแปรอื่นในโมเดล ถ้ามีเพียงสองตัวแปร VIF จะเท่ากับ 1 ÷ (1 − r²) ≈ 36 ค่าที่คำนวณจากโมเดลจริงคือ 39.6 แปลว่าความแปรปรวนของค่าสัมประสิทธิ์ขยายขึ้นราว 40 เท่า หรือ SE ขยายราว 6.3 เท่า กฎหัวแม่มือที่ใช้กันบ่อยถือว่าเกิน 10 ก็รุนแรงแล้ว แม้จะมีผู้เตือนว่ากฎนี้ต้องใช้ด้วยวิจารณญาณ [42] สรุปคือโมเดลแยกไม่ออกว่าผลมาจากสภาพหรืออุณหภูมิ

เราจึงลด Firth model เป็น sensitivity check และให้ RD กับ Fisher/Newcombe เป็นผลหลักแทน Firth model ไม่พบพจน์ของสภาพที่มีนัยสำคัญในด่านใดเลย (p ≥ 0.146) แต่ด้วยเหตุผลข้างต้น ค่าสัมประสิทธิ์ก็อ่านเป็นผลของความร้อนไม่ได้อยู่ดี การเปลี่ยนลำดับนี้ทำหลังเห็นสรุปผล ไม่ได้ลงทะเบียนล่วงหน้า และ paper เปิดเผยไว้ตรง ๆ ในหัวข้อ III-F และ VI

6.8 margin กับ normal approximation

margin ที่เล่าไว้ในหัวข้อ 1.4 เป็นสะพานระหว่าง RQ1 กับ RQ2 มันบอกได้ว่าทำไมการขยับที่ชัดเจนจึงไม่เปลี่ยนคำตัดสิน และด่านไหนควรระวัง เราลองเทียบสิ่งที่สูตร Φ(−margin) ทำนายกับสิ่งที่เห็นจริง V1 latency (1.8σ) ทำนาย 0.036 พบจริง 0.017 V1 throughput (2.9σ) ทำนาย 0.002 พบจริง 0 และการทดลองเสริม (0.62σ) ทำนาย 0.27 พบจริง 0.30

ตัวเลขใกล้กันพอให้เห็นแนวโน้ม แต่ใน paper เราเขียนชัดว่าเป็นการเทียบเชิงพรรณนา ไม่ได้ยืนยันว่าแบบจำลองปกติถูก margin เป็นระยะเชิงพรรณนา ไม่ใช่ช่วงความเชื่อมั่น หางของข้อมูลจริงอาจหนากว่าระฆังคว่ำ และ s รวม SD จากสองสภาพเข้าด้วยกัน การทดสอบว่าสูตรนี้ทำนายล่วงหน้าได้จริงหรือไม่ เป็นคำถามของงานถัดไปของเรา

6.9 permutation test ระดับบล็อก

reviewer ชี้ว่าการทดสอบระดับ run ไม่ได้เคารพโครงสร้างบล็อก เราจึงเพิ่มการทดสอบที่ใช้บล็อกเป็นหน่วย หลักคิดคือ ถ้าป้าย cold / warm ไม่มีความหมาย การสลับป้ายระหว่างบล็อกก็ไม่ควรเปลี่ยนภาพ มีหกบล็อก เลือกสามบล็อกให้เป็น warm ได้ 20 แบบ แล้วดูว่าแบบที่เกิดจริงสุดโต่งแค่ไหนเมื่อเทียบกับทั้ง 20 แบบ

ข้อมูลจริงตรงกับแบบที่สุดโต่งที่สุด คือทุกบล็อก warm สูงกว่าทุกบล็อก cold p สองทางจึงเท่ากับ 2 ÷ 20 = 0.10 ข้อควรรู้คือด้วยสามบล็อกต่อสภาพ p ไม่มีทางต่ำกว่า 0.10 ไม่ว่าผลจะชัดแค่ไหน และตรรกะของ randomization test อิงการสุ่มกำหนดสภาพให้บล็อก [43] ซึ่งเราไม่ได้ทำ ผลนี้จึงเป็นเชิงพรรณนา

6.10 ทำไมทุกช่วงในงานนี้จึงเรียกว่า nominal

run ที่อยู่บล็อกเดียวกันมีบางอย่างร่วมกัน เช่น อยู่ในช่วงเวลาเดียวกันและใช้ baseline ตัวเดียวกัน จึงไม่อิสระต่อกันจริง ในทางสถิติเรียกว่าข้อมูลมีโครงสร้างแบบ cluster จำนวนข้อมูลที่มีผลจริงจึงน้อยกว่า 30 run ต่อกรณี ถ้าวิเคราะห์ราวกับว่ามี 30 run อิสระ ช่วงที่ได้จะแคบเกินจริง ซึ่งเป็นกับดักที่ Hurlbert เตือนไว้ [31] ทุกช่วงระดับ run ใน paper จึงเรียกว่า nominal การตัดบล็อกออกทีละคู่และการตัด run ช่วง cold boot ช่วยดูความไว แต่ไม่ได้แก้ข้อจำกัดนี้ ทางแก้จริงคือสุ่มสภาพให้บล็อกจำนวนมากขึ้น แล้ววิเคราะห์ด้วยโมเดลระดับบล็อกหรือ mixed-effects model ซึ่งเราวางไว้เป็นงานต่อไป

Construct validityวัดสิ่งที่ตั้งใจวัดจริงไหมเซนเซอร์ภายในไม่ได้ calibrate กับเครื่องวัดภายนอก [14] และไม่ได้ยืนยันว่าหกช่องรวมกันเท่ากับกำลังไฟเข้า module · ความคลาดเคลื่อนแบบคูณที่เหมือนกันจะหักล้างในอัตราส่วน แต่แบบที่ขึ้นกับโหลดจะไม่หักล้าง · แบบจำลองไฟขณะว่างมีแค่สี่จุดและไม่ได้ส่งต่อความไม่แน่นอน · อุณหภูมิของ zone เป็นเพียงตัวแทนของสภาพเครื่อง · ความต่างจริง 9 °C น้อยกว่า 16 °C ระหว่าง setpoint · RAM ของระบบรวมกิจกรรมพื้นหลัง · ข้อมูลเข้าเป็น tensor สังเคราะห์
Internal validityสิ่งที่เห็นเกิดจากตัวแปรที่สนใจไหมสองสภาพเตรียมต่างกันและสลับในลำดับตายตัว สามบล็อกต่อสภาพ · การทดลองหลักเริ่ม cold การทดลองเสริมเริ่ม warm แต่การกลับลำดับไม่ได้ขจัด confounding · สภาพกับอุณหภูมิเริ่มต้นเกือบ collinear · run ที่ใช้บล็อกและ baseline ร่วมกันทำให้ช่วงระดับ run ไม่ครอบคลุม cluster dependence · telemetry แบบสุ่มตัวอย่างอาจพลาดการเปลี่ยนความถี่สั้น ๆ
Conclusion validityข้อสรุปทางสถิติหนักแน่นแค่ไหนนับเท่ากันโดยช่วง ±0.114 (±0.223 ในการทดลองเสริม) ยังเปิดทางให้ต่างได้มาก · 30 run ต่อกรณีให้กำลังทดสอบจำกัด โดยเฉพาะหลังปรับ multiplicity · variant calibrate รอบ latency threshold ไม่ใช่ energy threshold (V2 อยู่ต่ำกว่าด่านพลังงาน 5.9 percentage points ภายใต้ baseline หลัก และ 2.2 ภายใต้ baseline เย็นตายตัว) · สถิติส่วนใหญ่และการลดชั้น Firth กำหนดหลังเก็บข้อมูล · hash ในเครื่องไม่ได้ยืนยันเวลาโดยอิสระ · threshold sweep เป็น post hoc และความแรงของ variant ในการทดลองเสริมเลือกจากผลการทดลองหลัก
External validityใช้กับที่อื่นได้ไหมบอร์ดเดียว workload เดียว variant ที่สร้างขึ้น ตรึงความถี่ และปิดพัดลม · งาน [4] รายงานความต่างกำลังไฟระหว่างบอร์ดมักอยู่ใน ±10% ซึ่งเทียบตรงกับการขยับภายในบอร์ดของเราไม่ได้ · ทั้งสองสภาพอยู่ต่ำกว่าช่วง throttling ที่ [6] ศึกษามาก ใกล้ช่วงนั้น การขยับของพลังงานอาจโตขึ้น [5], [6] และ throttling จะกระทบ latency และ throughput โดยตรง

ส่วนที่ 8ถ้าจะนำไปใช้กับ CI ของตัวเอง

จากบอร์ดเดียว เราเสนอแนวปฏิบัติได้สองข้อ ทั้งสองข้อยังต้องตรวจสอบบนบอร์ดอื่นก่อน และผลของเราไม่ได้กำหนด threshold หรืออุณหภูมิใช้งานที่ใช้ได้ทั่วไป

ข้อแรก วัด baseline ในสภาพความร้อนเดียวกับ candidate หรืออย่างน้อยประเมินว่าการใช้ baseline จากสภาพอื่นทำให้ margin เปลี่ยนไปเท่าไร และดู margin ประกอบเสมอ เพราะผลในหัวข้อ 5.6 บอกว่าใกล้ threshold แม้ baseline ตรงสภาพก็อาจไม่พอ

ข้อสอง เวลารายงานผลของด่าน ให้รายงานสามอย่างคู่กัน คือการขยับที่วัดได้ ระยะจาก threshold ในหน่วยความแกว่งระหว่าง run และผลต่างของอัตรา gate event พร้อมช่วงความเชื่อมั่น

รายการตรวจที่เราใช้เองและแนะนำ

  • บันทึกอุณหภูมิตอนเริ่มของทุก job ที่วัด performance โดยอ่าน thermal zone ตามชื่อ ไม่เอาค่าสูงสุดของทุก zone
  • ตรึงความถี่ ตั้งพัดลมให้คงที่ (หรือปิด) และตรวจจาก telemetry ว่าความถี่ไม่หลุดจริง
  • ปิด service พื้นหลังและใส่ quiet-host check ก่อนเริ่มวัด
  • วัด baseline ใกล้เวลาและสภาพเดียวกับ candidate แทนการเก็บ baseline ไว้ครั้งเดียว
  • คำนวณ margin = (threshold − ผล) ÷ SD ของการวัดซ้ำ ถ้าต่ำกว่าราว 2σ อย่าตัดสินจาก run เดียว ให้รันซ้ำหรือดูเป็นสัดส่วน
  • ตั้งเวลารอให้เครื่องเย็นให้นานกว่าเวลาเย็นตัวจริงของบอร์ดในห้องนั้น และวัดใหม่เมื่อสภาพห้องเปลี่ยน
  • เวลาสรุปว่า “ไม่ต่างกัน” ให้แสดงช่วงความเชื่อมั่นของผลต่างด้วย ไม่ใช่แค่จำนวนนับ

เรื่องการใช้ AI

ใน paper เราเปิดเผยไว้ที่ส่วน Acknowledgment ว่า Claude และ ChatGPT ช่วยร่างและแก้ไขทุกส่วน และช่วยพัฒนาและตรวจสคริปต์วิเคราะห์ ส่วนการออกแบบและการรันการทดลองเราทำเอง ตรวจเนื้อหาและผลที่ AI ช่วยทุกส่วน และรับผิดชอบต่อ paper ทั้งหมด ประสบการณ์ของเราคือ AI ช่วยเสนอวิธีได้เร็วมาก แต่การตัดสินว่าวิธีไหนเหมาะกับข้อมูลจริงยังต้องมาจากการดูข้อมูลเอง ตัวอย่างชัดที่สุดคือ Firth model ซึ่งดูเหมาะบนกระดาษ แต่ใช้ไม่ได้เมื่อเจอข้อมูลที่ collinear และการเปิดเผยลำดับการตัดสินใจอย่างตรงไปตรงมาสำคัญพอ ๆ กับตัววิธีเอง บทความนี้ก็เรียบเรียงโดยมี AI ช่วย และตรวจตัวเลขกับ paper ฉบับสุดท้ายแล้ว

ส่วนที่ 10งานต่อไป

ข้อจำกัดในส่วนที่ 7 บอกเราตรง ๆ ว่างานถัดไปต้องทำอะไร ใน paper เราเขียนไว้สี่เรื่อง

  • สุ่มสภาพให้บล็อกจำนวนมากขึ้น แล้ววิเคราะห์ด้วยโมเดลระดับบล็อกหรือ mixed-effects เพื่อแยกสภาพออกจากเวลาและลำดับ
  • วาง variant ใกล้ threshold ของพลังงานด้วย ไม่ใช่เฉพาะ latency เพราะหลักฐานเรื่อง energy gate ใกล้ขอบยังมีจำกัด
  • calibrate เซนเซอร์กับเครื่องวัดกำลังไฟภายนอก เพื่อดูว่าความคลาดเคลื่อนขึ้นกับโหลดหรือไม่
  • ทำซ้ำบนแพลตฟอร์มที่สอง

งานถัดไปที่เรากำลังเตรียมคือการเทียบคำตัดสินข้าม Jetson AGX Xavier สามบอร์ดที่ตั้งค่าให้ตรงกัน เพื่อดูว่าคำตัดสินยังอยู่ไหมเมื่อ baseline กับ candidate ถูกวัดบนบอร์ดคนละตัว นอกจากนี้ บันทึก protocol ข้อมูลระดับ run และสคริปต์วิเคราะห์ของงานนี้จะเผยแพร่ใน public archive ตามที่เขียนไว้ใน paper

มีสองเหตุผลหลัก หนึ่ง baseline ที่วัดในสภาพเดียวกันก็สูงขึ้นด้วย อัตราส่วนจึงแทบไม่ขยับ สอง ผลด้านพลังงานของ variant อยู่ห่าง threshold อย่างน้อย 9.1σ การขยับราว 3% จึงไม่พอให้ข้ามเส้น ถ้าใช้ baseline เย็นตายตัว V2 warm ขยับจาก +8.8% เป็น +12.8% เข้าใกล้เส้นมากขึ้นแต่ยังไม่ข้าม

การสลับจาก warm ไป cold ต้องรอให้ฮีตซิงก์เย็นลงราว 17 นาทีต่อครั้ง (หัวข้อ 2.4) ถ้าสลับทุก run การทดลองที่ใช้ราวสี่ชั่วโมงจะยืดเป็นหลายสิบชั่วโมง (ตัวเลขนี้เราประมาณจากเส้นการเย็นตัวในบันทึกของเรา ไม่ได้อยู่ใน paper) เราจึงสลับทีละบล็อก แต่ภายในบล็อกยังสุ่มลำดับของเวอร์ชันจาก seed ที่บันทึกไว้ ราคาที่จ่ายคือ confounding กับวิธีเตรียม เวลา และลำดับ ใน paper เราเขียนชัดว่าผลเป็นความสัมพันธ์ ไม่ใช่ผลของอุณหภูมิที่แยกออกมาแล้ว และเสนอการสุ่มบล็อกจำนวนมากขึ้นเป็นงานต่อไป

เซนเซอร์ไม่ได้ calibrate เชื่อตัวเลขได้แค่ไหน

เราเทียบเฉพาะระหว่างสภาพบนชุดเครื่องมือเดียวกัน ถ้าความคลาดเคลื่อนเป็นแบบคูณคงที่ จะหักล้างกันในอัตราส่วน แต่ถ้าขึ้นกับโหลดจะไม่หักล้าง จึงระบุเป็น construct threat และเสนอให้ calibrate กับเครื่องวัดภายนอกในงานต่อไป

ทำไมใช้ Mann–Whitney แทน t-test

ข้อมูลเวลาและพลังงานมักเบ้และมีค่าโดด Mann–Whitney ใช้อันดับ จึงไม่ต้องสมมติการแจกแจงปกติ และใช้คู่กับ Cliff's δ ได้พอดี เพราะ δ คำนวณจากค่า U ตัวเดียวกัน ส่วนขนาดการขยับของมัธยฐาน เรารายงานแยกพร้อมช่วง bootstrap เพราะ Mann–Whitney ไม่ได้ทดสอบมัธยฐานโดยตรง

47 °C ร้อนพอหรือ

เราไม่ได้ตั้งใจให้ร้อนถึงช่วง throttling ทั้งสองสภาพอยู่ต่ำกว่าช่วงนั้นมาก อุณหภูมิสูงสุดที่บันทึกคือ 53.5 °C ความต่างจริงคือ 9 °C ระหว่างการเริ่มแบบเย็นกับการเริ่มหลังงานหนัก ซึ่งใกล้กับสิ่งที่ runner เจอในการใช้งานจริง ผลจึงไม่ขยายไปถึงสภาพที่ร้อนจนบอร์ดลดความถี่

ทำไม Firth model ถูกลดชั้น

สภาพกับอุณหภูมิเริ่มต้น collinear เกือบสมบูรณ์ (r = 0.986, VIF = 39.6) โมเดลแยกสองตัวไม่ออก เราลดชั้นหลังเห็นสรุปผล ซึ่งเป็นการเปลี่ยนแผนหลังเก็บข้อมูล และเปิดเผยไว้ใน paper

RAM ตอน warm ต่ำกว่า เพราะอะไร

ยังอธิบายไม่ได้ครับ peak RAM เป็น RAM ของทั้งระบบ รวมกิจกรรมพื้นหลัง จึงยกให้เป็นผลของโปรแกรมไม่ได้ และไม่ได้เปลี่ยนคำตัดสินใด ๆ

บอร์ดอื่นจะได้ผลเหมือนกันไหม

ยังไม่รู้ ตัวเลขเฉพาะกับการตั้งค่านี้ สิ่งที่น่าจะนำไปใช้ได้คือวิธีรายงาน คือดู baseline ดู margin และรายงาน RD พร้อมช่วง งานถัดไปของเราจะทดสอบบนหลายบอร์ด

ทำไมใช้ 30 run ต่อกรณี

เป็นการแลกระหว่างเวลาเครื่องกับความแม่น 300 run ใช้ 232 นาทีบนบอร์ดเดียว ถ้าเพิ่มเป็นสองเท่าก็ต้องใช้เกือบแปดชั่วโมงต่อเนื่อง เรายอมรับใน paper ว่ากำลังทดสอบจำกัด โดยเฉพาะหลังปรับ multiplicity และช่วงของจำนวนนับยังกว้าง
