นิยาม

การทดสอบ คือการประเมินคุณภาพของซอฟต์แวร์และผลงานที่เกี่ยวข้อง

ไม่ได้มีแค่ "รันโปรแกรมดูว่าพังไหม" แต่รวมถึงวางแผน วิเคราะห์ ออกแบบ เตรียม ดำเนินการ และรายงานผล ทำได้ 2 แบบ
Static testing · ไม่รันโปรแกรม

ตรวจผลงานโดยตรง เช่น อ่านทบทวนเอกสาร หรือใช้เครื่องมือวิเคราะห์โค้ด

ในวิชานี้: inspection SRS ไขว้ทีม (สัปดาห์ 3) · code review และ static analysis (สัปดาห์ 4)
Dynamic testing · รันโปรแกรม

รันซอฟต์แวร์ด้วยข้อมูลที่ออกแบบไว้ แล้วเทียบผลที่ได้กับผลที่คาดหวัง

ในวิชานี้: unit, integration, system, acceptance และการทดสอบเชิงไม่เป็นฟังก์ชัน (สัปดาห์ 8–13)
เป้าหมายของการทดสอบ

เราทดสอบเพื่อ 4 เรื่อง

หาข้อบกพร่องและทำให้ failure ปรากฏก่อนที่ผู้ใช้จะเจอเอง ทั้งในเอกสาร แบบ โค้ด และระบบที่รันจริง
ตรวจว่าตรงข้อกำหนดและความคาดหวังครบตามที่ระบุไว้ (verification) และใช้งานได้ตามที่ผู้มีส่วนได้ส่วนเสียคาดหวัง (validation)
ลดความเสี่ยงและสร้างความมั่นใจลดโอกาสที่ซอฟต์แวร์คุณภาพไม่พอจะสร้างความเสียหาย และให้ทีมมั่นใจขึ้นอย่างมีหลักฐาน
ให้ข้อมูลเพื่อตัดสินใจเช่น พร้อมส่งมอบหรือยัง ต้องแก้อะไรก่อน และยังเหลือความเสี่ยงอะไร
การทดสอบไม่ได้ทำให้คุณภาพดีขึ้นเอง คุณภาพดีขึ้นเมื่อทีมแก้สิ่งที่การทดสอบพบ และปรับวิธีทำงานไม่ให้พลาดซ้ำ
ศัพท์ที่ต้องแยกให้ออก

คนพลาด → ผลงานมีข้อบกพร่อง → ระบบทำงานผิด

ตัวอย่างจากระบบร้านค้าออนไลน์

ลูกค้าซื้อ 1,000 บาทพอดี แต่ไม่ได้ส่วนลด

ข้อกำหนด: "ซื้อตั้งแต่ 1,000 บาทขึ้นไป ลด 10%"
function discount(total) { if (total > 1000) { return total * 0.10; } return 0; } discount(1000) // คาดหวัง 100 // ได้จริง 0
Errorนักพัฒนาอ่านคำว่า "ตั้งแต่" เป็น "มากกว่า"
Defectใช้ > ซึ่งควรเป็น >= ในบรรทัดที่ 2
Failureซื้อ 1,000 บาทพอดี ได้ส่วนลด 0 บาท แทน 100 บาท
Root cause และกรณีที่ควรจับได้ข้อกำหนดไม่มีตัวอย่างค่าขอบ · ทดสอบค่า 999, 1,000, 1,001 (boundary value analysis สัปดาห์ 6)
คิดเดี่ยว 1 นาที แล้วคุยกับคนข้าง ๆ 1 นาที

แต่ละข้อเป็น error, defect หรือ failure

1แอปแสดงยอดเงินคงเหลือติดลบหลังโอนเงินสำเร็จ
2นักพัฒนาเข้าใจว่าเวลาจาก API เป็นวินาที ทั้งที่เอกสารระบุว่าเป็นมิลลิวินาที
3SRS ระบุว่ารหัสผ่านยาวอย่างน้อย 8 ตัว แต่ไม่ได้ระบุว่ายาวได้มากที่สุดกี่ตัว
4ลูปเขียนเป็น i <= items.length ทำให้อ่านเกินท้ายอาร์เรย์
5ผู้ใช้กดบันทึกแล้วหน้าจอค้างไป 30 วินาที
6นักพัฒนาลืมว่าเดือนกุมภาพันธ์ของปีอธิกสุรทินมี 29 วัน
เฉลย

defect อยู่ได้ทั้งในโค้ดและในเอกสาร

1ยอดเงินติดลบหลังโอนสำเร็จFailureผลลัพธ์ผิดที่ผู้ใช้เห็นขณะระบบทำงาน
2เข้าใจหน่วยเวลาผิดErrorความเข้าใจผิดของคน ซึ่งจะไปสร้าง defect ในโค้ด
3SRS ไม่ระบุความยาวสูงสุดDefect (ในเอกสาร)ข้อกำหนดไม่ครบ พบได้ด้วยการทบทวนโดยไม่ต้องรันโปรแกรม
4ลูปใช้ <=Defect (ในโค้ด)ข้อบกพร่องที่จะทำให้เกิด failure เมื่อถูกรัน
5หน้าจอค้าง 30 วินาทีFailureยังไม่รู้ว่า defect อยู่ที่ไหน ต้องดีบักต่อ
6ลืมปีอธิกสุรทินErrorคนลืม ส่งผลให้เขียนโค้ดคำนวณวันผิด
หลักการทดสอบ ISTQB CTFL v4.0.1 หัวข้อ 1.3

หลัก 7 ข้อที่ใช้ได้กับทุกโครงงาน

1การทดสอบแสดงว่ามีข้อบกพร่อง ไม่ได้พิสูจน์ว่าไม่มีผ่านทุกกรณีแปลว่า "ยังไม่พบ" ไม่ใช่ "ไม่มี"Testing shows the presence, not the absence of defects
2ทดสอบทุกกรณีเป็นไปไม่ได้ต้องเลือกกรณีด้วยความเสี่ยงและเทคนิคออกแบบExhaustive testing is impossible
3ทดสอบเร็ว ประหยัดเวลาและเงินเริ่มตั้งแต่ทบทวนความต้องการ ไม่ต้องรอโค้ดEarly testing saves time and money
4ข้อบกพร่องมักกระจุกตัวส่วนน้อยของระบบมักมีข้อบกพร่องส่วนใหญ่Defects cluster together
5กรณีทดสอบเดิมใช้นานแล้วจะสึกรันชุดเดิมซ้ำ ๆ จะไม่พบอะไรใหม่ ต้องปรับและเพิ่มTests wear out
6การทดสอบขึ้นกับบริบทแอปร้านกาแฟกับระบบการแพทย์ ทดสอบไม่เหมือนกันTesting is context dependent
7ไม่มีบั๊ก ไม่ได้แปลว่าใช้ได้ระบบไร้ข้อบกพร่องแต่ไม่ตอบโจทย์ผู้ใช้ ก็ยังล้มเหลวAbsence-of-defects fallacy
ข้อ 3 และ 7คือเหตุผลที่วิชานี้เริ่มจากทบทวน SRS และจบด้วย UAT กับผู้ใช้จริง
หลักข้อ 2 ในตัวเลข

แม้ฟังก์ชันเล็ก ๆ ก็มีกรณีมากเกินกว่าจะลองครบ

ฟังก์ชันบวกเลขจำนวนเต็ม 32 บิต 2 ตัว

232 × 232 = 264 ≈ 1.8 × 1019 กรณี
ทดสอบได้ 1,000 ล้านกรณีต่อวินาที
ใช้เวลา ≈ 585 ปี

ฟอร์มสมัครสมาชิก 3 ช่อง

อายุ 0–120 → 121 ค่า
จังหวัด → 77 ค่า
วิธีชำระเงิน → 4 ค่า
121 × 77 × 4 = 37,268 กรณี
ทางออกไม่ใช่ทดสอบให้มากที่สุด แต่เลือกให้ฉลาด: ใช้ความเสี่ยงจัดลำดับ (สัปดาห์ 5) และเทคนิคอย่าง equivalence partitioning กับ boundary value analysis (สัปดาห์ 6) ลดกรณีโดยยังครอบคลุม
จากหลักการสู่การลงมือ

หลักการทีมจะทำอะไรสัปดาห์
1แสดงว่ามี ไม่ได้พิสูจน์ว่าไม่มีรายงานผลว่า "ทดสอบอะไร พบอะไร เหลือความเสี่ยงอะไร" ไม่เขียนว่า "ระบบไม่มีบั๊ก"16 · CP5
2ทดสอบทุกกรณีไม่ได้จัดลำดับตามความเสี่ยง และใช้ EP/BVA ออกแบบกรณีทดสอบ5–6
3ทดสอบเร็ว ประหยัดกว่าinspection SRS ไขว้ทีม ก่อนเขียนโค้ดส่วนใหญ่3 · CP1
4ข้อบกพร่องกระจุกตัวดูว่าโมดูลไหนมีข้อบกพร่องมากใน issue tracker แล้วทดสอบเพิ่มตรงนั้น15
5กรณีทดสอบเดิมจะสึกทบทวนและเพิ่มชุด regression ทุกครั้งที่แก้บั๊ก12
6ขึ้นกับบริบทแผนการทดสอบเขียนตามประเภทระบบและผู้ใช้ของทีม ไม่ใช้แม่แบบเดียวกันทุกทีม5 · CP2
7ไม่มีบั๊ก ไม่ได้แปลว่าใช้ได้ทำ UAT กับผู้ใช้หรือลูกค้าจริงของโครงงาน12 · CP4
คนละงาน คนละเป้าหมาย

Testing ทำให้ปัญหาปรากฏ Debugging หาต้นเหตุแล้วแก้

Testingวางแผนและออกแบบได้ก่อนมีโค้ด ผลงานคือกรณีทดสอบ ผลการทดสอบ และรายงานข้อบกพร่อง
Debuggingเริ่มจาก failure หรือรายงานข้อบกพร่อง ผลงานคือโค้ดที่แก้แล้ว ซึ่งต้องทดสอบซ้ำเสมอ
ความสัมพันธ์ของ 3 คำ

QA ป้องกันที่กระบวนการ ส่วน QC ตรวจที่ผลิตภัณฑ์

การจัดการคุณภาพ (Quality management)
QA · Quality Assuranceเน้นกระบวนการ · ป้องกันไม่ให้เกิด
  • กำหนดว่าทุก PR ต้องมีคนรีวิว
  • ตั้งมาตรฐานการเขียนโค้ดและแม่แบบเอกสาร
  • อบรมทีม และปรับขั้นตอนจากบทเรียน
QC · Quality Controlเน้นผลิตภัณฑ์ · ตรวจหาแล้วแก้
  • ตรวจ SRS หรือโค้ดของงานชิ้นนั้น
  • รันกรณีทดสอบกับระบบ
Testing เป็น QC รูปแบบหลัก และผลการทดสอบเป็นข้อมูลให้ QA ใช้ปรับกระบวนการ

วิธีจำ: ถ้าคำตอบคือ "เปลี่ยนวิธีทำงานของทีม" เป็น QA ถ้าคำตอบคือ "ตรวจงานชิ้นนี้" เป็น QC

คุยกับคนข้าง ๆ 2 นาที

แต่ละข้อเป็น QA หรือ QC

1ตกลงกันว่าทุก PR ต้องมีคนรีวิวอย่างน้อย 1 คนก่อน merge
2รัน unit test ใน CI แล้วพบ 3 กรณีไม่ผ่าน
3จัดอบรมทีมเรื่องการเขียนกรณีทดสอบ
4ตรวจ SRS ด้วย checklist แล้วพบความต้องการที่กำกวม 5 ข้อ
5นำสถิติข้อบกพร่องของ Sprint ที่แล้วมาปรับขั้นตอนการทำงาน
6ให้ผู้ใช้จริงทดลองระบบตามสถานการณ์จริงใน UAT
เฉลย

ดูว่ากำลังเปลี่ยนวิธีทำงาน หรือกำลังตรวจงานชิ้นหนึ่ง

1กติกาทุก PR ต้องมีคนรีวิวQAกำหนดกระบวนการเพื่อป้องกัน
2รัน unit test แล้วพบ 3 กรณีไม่ผ่านQC (testing)ตรวจผลิตภัณฑ์ด้วยการรันโปรแกรม
3อบรมการเขียนกรณีทดสอบQAพัฒนาคนและวิธีทำงาน
4ตรวจ SRS ด้วย checklistQC (static testing)ตรวจงานชิ้นนี้โดยไม่รันโปรแกรม
5ใช้สถิติข้อบกพร่องปรับขั้นตอนQAใช้ผลจาก QC มาปรับปรุงกระบวนการ
6UAT กับผู้ใช้จริงQC (testing · validation)ตรวจว่าผลิตภัณฑ์ตรงความคาดหวัง
จบช่วงที่ 2

5 ประโยคที่ต้องจำ

  1. 1การทดสอบมีทั้งแบบไม่รันโปรแกรม (static) และรันโปรแกรม (dynamic) และเริ่มได้ตั้งแต่ยังไม่มีโค้ด
  2. 2Error คือคนพลาด defect คือข้อบกพร่องในผลงาน failure คือระบบทำงานผิดที่สังเกตได้
  3. 3ผ่านทุกกรณีแปลว่า "ยังไม่พบ" และทดสอบทุกกรณีไม่ได้ จึงต้องเลือกตามความเสี่ยง
  4. 4Testing ทำให้ปัญหาปรากฏ debugging หาต้นเหตุและแก้ แล้วต้องทดสอบซ้ำเสมอ
  5. 5QA ป้องกันที่กระบวนการ QC ตรวจที่ผลิตภัณฑ์ และ testing คือ QC รูปแบบหลัก
