ตอบในแชต · ข้อละครึ่งนาที

แต่ละข้อเป็น verification หรือ validation

พิมพ์ในแชต: เลขข้อ + ตัวอักษร ve = verification, va = validation 1ve 2va ...3 นาที
  1. ทีมรัน unit test ว่าระบบปฏิเสธคำขอจองที่เวลาทับกันตาม FR-02.03?
  2. เจ้าหน้าที่ลองใช้หน้าบันทึกการคืนอุปกรณ์ที่เคาน์เตอร์จริง?
  3. ทีมคู่ตรวจ SRS ด้วยรายการตรวจในครั้งที่ 3?
  4. ถามผู้ใช้ว่ากฎยืมไม่เกิน 3 ชิ้นเหมาะกับวิชาที่ใช้บอร์ดหลายชิ้นไหม?
  5. ตรวจว่า API ตอบรหัส 409 ตามที่เขียนไว้ใน openapi.yaml?
  6. ให้นักศึกษาปี 1 ที่ไม่เคยใช้ระบบลองจองห้องเอง?
เฉลย

verification เทียบกับเอกสาร validation เทียบกับการใช้งานจริง

  1. ทีมรัน unit test ว่าระบบปฏิเสธคำขอจองที่เวลาทับกันตาม FR-02.03เทียบกับความต้องการที่เขียนไว้verification
  2. เจ้าหน้าที่ลองใช้หน้าบันทึกการคืนอุปกรณ์ที่เคาน์เตอร์จริงดูว่าใช้ทำงานจริงได้ไหมvalidation
  3. ทีมคู่ตรวจ SRS ด้วยรายการตรวจในครั้งที่ 3เทียบเอกสารกับเกณฑ์คุณภาพverification
  4. ถามผู้ใช้ว่ากฎยืมไม่เกิน 3 ชิ้นเหมาะกับวิชาที่ใช้บอร์ดหลายชิ้นไหมตรวจว่าความต้องการเองถูกไหมvalidation
  5. ตรวจว่า API ตอบรหัส 409 ตามที่เขียนไว้ใน openapi.yamlเทียบกับสเปกverification
  6. ให้นักศึกษาปี 1 ที่ไม่เคยใช้ระบบลองจองห้องเองการยอมรับของผู้ใช้จริงvalidation

วิธีจำ: "ตรงกับที่เขียนไว้ไหม" = verification · "ใช้ได้จริงไหม หรือที่เขียนไว้ถูกไหม" = validation

ทวนสอบเมื่อไร

V&V ไม่ได้เริ่มที่การทดสอบ แต่เริ่มที่เอกสารชิ้นแรก

เอกสารก็มีข้อบกพร่องได้ ทวนสอบเชิงสถิตจับได้ตั้งแต่ยังไม่มีโค้ด และถูกกว่าไปเจอตอนทดสอบระบบหลายเท่า ทีมที่ยังไม่เริ่มเขียนโค้ดจึงทำ V&V ได้ตั้งแต่สัปดาห์นี้

IEEE 1012 System, Software, and Hardware Verification and Validation

ไม่ใช่ทุกระบบต้องทวนสอบเข้มเท่ากัน

ความรุนแรงของผลเสียถ้าระบบทำงานผิด ร้ายแรงแค่ไหน: ร้ายแรงมาก ร้ายแรง ปานกลาง เล็กน้อย
โอกาสเกิดผลเสียนั้นมีโอกาสเกิดแค่ไหน: เกิดได้แน่ น่าจะเกิด บางครั้ง แทบไม่เกิด
integrity level 1–4ระดับยิ่งสูง ต้องทวนสอบมากงานขึ้น เข้มขึ้น และอิสระจากผู้พัฒนามากขึ้น

IEEE 1012 ไม่ได้บอกให้ทวนสอบทุกระบบเข้มเท่ากัน แต่ให้กำหนดระดับจากผลเสีย แล้วเลือกงาน V&V ให้พอดีกับระดับ

กำหนดรายส่วนได้: ทั้งระบบระดับ 2 แต่ส่วนที่คุมข้อมูลส่วนบุคคลหรือเงินอาจเป็นระดับ 3

ความรุนแรง × โอกาสเกิด

เลือกระดับจากผลเสียที่ร้ายแรงที่สุดที่เป็นไปได้

เกิดได้แน่น่าจะเกิดบางครั้งแทบไม่เกิด
ร้ายแรงมากเสียชีวิต บาดเจ็บสาหัส สูญเสียระบบหรือเงินจำนวนมาก444 หรือ 33
ร้ายแรงบาดเจ็บ ข้อมูลส่วนบุคคลรั่ว ภารกิจหลักล้มเหลว44 หรือ 332 หรือ 1
ปานกลางงานล่าช้า ข้อมูลผิดบางส่วน ต้องแก้ด้วยมือ33 หรือ 22 หรือ 11
เล็กน้อยผู้ใช้ไม่สะดวก ไม่กระทบงานหลัก22 หรือ 111

ดัดแปลงจากตัวอย่างในภาคผนวกของ IEEE 1012 · ช่องที่มี 2 ค่า ทีมเลือกได้แต่ต้องบอกเหตุผล ตารางเดียวกันอยู่ท้ายแม่แบบ V&V Strategy

ทีมที่ตอบว่ากระทบความปลอดภัยของคน หรือเก็บข้อมูลอ่อนไหว ให้หาว่าส่วนไหนของระบบควรเป็นระดับ 3 ขึ้นไป แล้วเขียนเหตุผลใน V&V Strategy ข้อ 1

ตอบในแชต

ระบบเหล่านี้ควรเป็น integrity level เท่าไร

พิมพ์ในแชต: เลขข้อ = ระดับ 1=? 2=? 3=?3 นาที
  1. ระบบแนะนำเมนูเครื่องดื่มของร้านกาแฟ จากสิ่งที่ลูกค้าเคยสั่งระดับ ?
  2. ระบบจองคิวคลินิก ที่เก็บอาการเบื้องต้นของผู้ป่วยระดับ ?
  3. ระบบคำนวณขนาดยาให้พยาบาลในหอผู้ป่วยระดับ ?

ตอบเป็นตัวเลข 1–4 ถ้ามีเวลา บอกด้วยว่าผลเสียร้ายแรงที่สุดคืออะไร (ระบบสมมุติ ไม่ใช่โครงงานของทีมใดในห้อง)

เฉลย

คำตอบที่ดีมีทั้งระดับและเหตุผล

  1. ระบบแนะนำเมนูเครื่องดื่มของร้านกาแฟ จากสิ่งที่ลูกค้าเคยสั่งแนะนำผิด ลูกค้าแค่ไม่สะดวก (เล็กน้อย)ระดับ 1
  2. ระบบจองคิวคลินิก ที่เก็บอาการเบื้องต้นของผู้ป่วยข้อมูลสุขภาพรั่ว = ร้ายแรง × บางครั้งระดับ 3
  3. ระบบคำนวณขนาดยาให้พยาบาลในหอผู้ป่วยคำนวณผิดอาจถึงชีวิต = ร้ายแรงมากระดับ 4

ระดับมีผลกับงานของทีมในวิชานี้อย่างไร

  • ระดับ 1–2 ทำตามจุดตรวจ CP1–CP5 ตามปกติ
  • ระดับ 3 ส่วนนั้นเพิ่ม 3 อย่าง: coverage สูงกว่าส่วนอื่น ทดสอบสิทธิ์และความปลอดภัยครบทุกบทบาท รีวิวโค้ด 2 คน
  • ระดับ 4 แจ้งอาจารย์ในคาบ เพื่อตกลงการทวนสอบเพิ่มเติม
ก่อนพัก

4 ประโยคจากช่วงที่ 1

  • 1verification สร้างถูกตามแบบไหม เทียบกับเอกสาร · validation สร้างของที่ใช่ไหม เทียบกับการใช้งานจริง
  • 2V&V เริ่มตั้งแต่เอกสารชิ้นแรก ทวนสอบเชิงสถิตไม่ต้องรอโค้ด
  • 3integrity level = ความรุนแรงของผลเสีย × โอกาสเกิด ระดับสูง ทวนสอบเข้มขึ้น
  • 4กำหนดระดับรายส่วนได้ และต้องมีเหตุผลเสมอ
