ENGSE601 · ครั้งที่ 1 · เอกสารประกอบการเรียน

ปฐมนิเทศและพื้นฐานการทดสอบ

อ. 24 พ.ย. 2569 · อ่านประมาณ 60 นาที · CLO1 · ใช้ทบทวนหลังเรียนและเตรียมสอบกลางภาค · ฉบับ 1.0 (26 พ.ย. 2569)

สารบัญ
  1. ครั้งนี้อยู่ตรงไหนของภาค
  2. รายวิชานี้ทำอะไร
  3. พื้นฐานการทดสอบ
  4. วิเคราะห์กรณีซอฟต์แวร์ล้มเหลวจริง
  5. สิ่งที่ต้องจำจากครั้งที่ 1

บทนำครั้งนี้อยู่ตรงไหนของภาค

ครั้งแรกของภาคมี 3 เรื่อง เรื่องแรกคือรายวิชานี้ทำอะไร ทำไมต้องใช้โครงงาน ENGSE212 ของทีม และวัดผลอย่างไร เรื่องที่สองคือพื้นฐานการทดสอบที่ใช้ตลอดภาค ได้แก่ ศัพท์ หลักการ และบทบาทของงานต่าง ๆ เรื่องที่สามคือการนำศัพท์ไปวิเคราะห์กรณีซอฟต์แวร์ล้มเหลวจริง

เอกสารนี้ใช้ทบทวนหลังเรียน ศัพท์ในส่วนที่ 2 อ้างอิงหลักสูตร ISTQB Certified Tester Foundation Level (CTFL) ฉบับ 4.0.1 บทที่ 1 ซึ่งเป็นงานอ่าน R1 ด้วย ครั้งที่ 2 และข้อสอบกลางภาคใช้ศัพท์ชุดนี้ต่อ

หลังอ่านแล้วคุณจะทำได้

  1. บอกได้ว่ารายวิชานี้ใช้โครงงานของทีมอย่างไร มีจุดตรวจอะไร และวัดผลอย่างไร
  2. อธิบายว่าการทดสอบคืออะไร ทำเพื่ออะไร และแยกการทดสอบเชิงสถิตกับเชิงพลวัต
  3. แยก error, defect และ failure ในสถานการณ์ที่ให้มา และบอก root cause ได้
  4. อธิบายหลัก 7 ข้อของการทดสอบ และบอกว่าแต่ละข้อกลายเป็นงานอะไรในโครงงาน
  5. แยก testing กับ debugging และบอกว่ากิจกรรมหนึ่งเป็น QA หรือ QC
  6. วิเคราะห์กรณีความล้มเหลวด้วยห่วงโซ่ error → defect → failure และเลือก V&V ที่น่าจะจับปัญหาได้

ส่วนที่ 1รายวิชานี้ทำอะไร

1.1 อัปเดตเดียว ล่มทั้งโลก

วันที่ 19 กรกฎาคม 2567 CrowdStrike ปล่อยอัปเดตเนื้อหา (Channel File 291) ของซอฟต์แวร์ความปลอดภัย Falcon บน Windows รูปแบบข้อมูลใหม่กำหนดข้อมูลนำเข้า 21 ช่อง แต่โค้ดที่เรียกตัวแปลเนื้อหาส่งให้เพียง 20 ช่อง อัปเดตวันนั้นเป็นครั้งแรกที่มีเงื่อนไขใช้ช่องที่ 21 จริง ตัวแปลจึงอ่านหน่วยความจำเกินขอบเขตและระบบล่ม Microsoft ประเมินว่ามีเครื่องได้รับผลกระทบราว 8.5 ล้านเครื่อง บริการสำคัญอย่างสายการบินหยุดชะงัก

คำถามที่ใช้เปิดวิชาคือ ถ้ามีกรณีทดสอบที่ส่งข้อมูลครบ 21 ช่องเข้าไปจริงสักกรณีเดียว ปัญหานี้จะหลุดไปถึงผู้ใช้ไหม ตัวตรวจเนื้อหาของบริษัทตรวจผ่าน เพราะตรวจบนความเข้าใจว่ามีข้อมูล 21 ช่อง ไม่ได้ตรวจกับสิ่งที่โค้ดส่งจริง วิชานี้ฝึกหาช่องว่างแบบนี้ก่อนผู้ใช้เจอ

1.2 ซอฟต์แวร์คุณภาพต่ำมีราคา และยิ่งพบช้ายิ่งแพง

รายงานของ CISQ (2565) ประเมินต้นทุนจากซอฟต์แวร์คุณภาพต่ำในสหรัฐฯ ปี 2565 ไว้ราว 2.41 ล้านล้านดอลลาร์ และหนี้ทางเทคนิคที่สะสมอีกราว 1.52 ล้านล้านดอลลาร์ ตัวเลขระดับประเทศอาจดูไกลตัว แต่หลักเดียวกันใช้กับโครงงานของทีม ข้อบกพร่องในความต้องการที่หลุดไปถึงผู้ใช้ ต้องแก้ทั้งเอกสาร แบบ โค้ด และทดสอบใหม่ ส่วนข้อบกพร่องเดียวกันถ้าพบตอนทบทวน SRS แก้แค่ประโยคเดียว

1.4 ทวนสอบโครงงานของทีมเอง ไม่มีโปรเจกต์ใหม่

วิชานี้เรียนคู่กับ ENGSE212 โครงงานวิศวกรรมซอฟต์แวร์ ทีมของวิชาคือทีมโครงงานเดียวกัน และระบบที่นำมาทวนสอบตลอดภาคคือระบบของทีม ชิ้นงาน V&V ทุกชิ้นของวิชานี้เป็นชิ้นที่ต้องใส่ในเล่ม ENGSE212 อยู่แล้ว จึงไม่เพิ่มภาระงาน

2.1 การทดสอบคืออะไร

ISTQB ให้ความหมายว่าการทดสอบคือการประเมินคุณภาพของซอฟต์แวร์และผลงานที่เกี่ยวข้อง ไม่ได้มีแค่ "รันโปรแกรมดูว่าพังไหม" แต่รวมการวางแผน วิเคราะห์ ออกแบบ เตรียม ดำเนินการ และรายงานผล ทำได้ 2 แบบ

การทดสอบเชิงสถิต (static testing)การทดสอบเชิงพลวัต (dynamic testing)
ทำอย่างไรไม่รันโปรแกรม ตรวจผลงานโดยตรง เช่น อ่านทบทวนเอกสาร หรือใช้เครื่องมือวิเคราะห์โค้ดรันซอฟต์แวร์ด้วยข้อมูลที่ออกแบบไว้ แล้วเทียบผลที่ได้กับผลที่คาดหวัง
ทำได้เมื่อตั้งแต่ยังไม่มีโค้ดเมื่อมีโค้ดที่รันได้
ในวิชานี้inspection SRS ไขว้ทีม (สัปดาห์ 3) · code review และ static analysis (สัปดาห์ 4)unit, integration, system, acceptance และเชิงไม่เป็นฟังก์ชัน (สัปดาห์ 8–13)

2.2 ทดสอบเพื่ออะไร

  1. หาข้อบกพร่องและทำให้ failure ปรากฏ ก่อนผู้ใช้เจอเอง ทั้งในเอกสาร แบบ โค้ด และระบบที่รันจริง
  2. ตรวจว่าตรงข้อกำหนดและความคาดหวัง ครบตามที่ระบุไว้ (verification) และใช้ได้ตามที่ผู้มีส่วนได้ส่วนเสียคาดหวัง (validation)
  3. ลดความเสี่ยงและสร้างความมั่นใจ ลดโอกาสที่ซอฟต์แวร์คุณภาพไม่พอจะสร้างความเสียหาย และให้ทีมมั่นใจขึ้นอย่างมีหลักฐาน
  4. ให้ข้อมูลเพื่อตัดสินใจ เช่น พร้อมส่งมอบหรือยัง ต้องแก้อะไรก่อน และยังเหลือความเสี่ยงอะไร
การทดสอบไม่ได้ทำให้คุณภาพดีขึ้นเอง

คุณภาพดีขึ้นเมื่อทีมแก้สิ่งที่การทดสอบพบ และปรับวิธีทำงานไม่ให้พลาดซ้ำ รายงานผลการทดสอบที่ไม่มีใครนำไปแก้ ไม่ได้ทำให้ระบบดีขึ้น

2.3 error, defect, failure

ศัพท์ความหมายอยู่ที่ไหน
error หรือ mistakeการกระทำของคนที่ให้ผลผิด เช่น เข้าใจผิด ลืม อ่านข้อกำหนดผิดในหัวคน
defect หรือ bug, faultข้อบกพร่องในผลงาน ซึ่งถ้าถูกใช้งานอาจทำให้ระบบทำงานผิดในเอกสาร แบบ โค้ด หรือขั้นตอน deploy
failureระบบทำสิ่งที่ไม่ควรทำ หรือไม่ทำสิ่งที่ควรทำ ที่สังเกตได้ขณะทำงานในพฤติกรรมของระบบที่รันจริง
root causeเหตุพื้นฐานที่ทำให้คนพลาด ถ้าแก้ที่นี่จะป้องกันข้อบกพร่องแบบเดียวกันได้ในกระบวนการ ความรู้ หรือสภาพการทำงาน

defect ไม่จำเป็นต้องกลายเป็น failure เสมอ ถ้าไม่มีใครใช้งานส่วนนั้นด้วยเงื่อนไขที่ทำให้มันแสดงผล และ failure บางครั้งเกิดจากสภาพแวดล้อม เช่น ฮาร์ดแวร์เสีย โดยไม่มี defect ในซอฟต์แวร์

ตัวอย่าง: ส่วนลดที่ไม่ลด

ข้อกำหนด: "ซื้อตั้งแต่ 1,000 บาทขึ้นไป ลด 10%" ลูกค้าซื้อ 1,000 บาทพอดี แต่ไม่ได้ส่วนลด

function discount(total) {
  if (total > 1000) {        // ควรเป็น >=
    return total * 0.10;
  }
  return 0;
}
discount(1000)  // คาดหวัง 100 · ได้จริง 0
errorนักพัฒนาอ่านคำว่า "ตั้งแต่" เป็น "มากกว่า"
defectใช้ > ซึ่งควรเป็น >= ในบรรทัดที่ 2
failureซื้อ 1,000 บาทพอดี ได้ส่วนลด 0 บาท แทน 100 บาท
root causeข้อกำหนดไม่มีตัวอย่างค่าขอบ
ควรจับได้ด้วยทดสอบค่า 999, 1,000, 1,001 (boundary value analysis สัปดาห์ 6)
error, defect หรือ failure (คลิกแต่ละข้อเพื่อดูเฉลย)
  1. แอปแสดงยอดเงินคงเหลือติดลบหลังโอนเงินสำเร็จเฉลยfailure ผลลัพธ์ผิดที่ผู้ใช้เห็นขณะระบบทำงาน
  2. นักพัฒนาเข้าใจว่าเวลาจาก API เป็นวินาที ทั้งที่เอกสารระบุว่าเป็นมิลลิวินาทีเฉลยerror ความเข้าใจผิดของคน ซึ่งจะไปสร้าง defect ในโค้ด
  3. SRS ระบุว่ารหัสผ่านยาวอย่างน้อย 8 ตัว แต่ไม่ได้ระบุว่ายาวได้มากที่สุดกี่ตัวเฉลยdefect ในเอกสาร ข้อกำหนดไม่ครบ พบได้ด้วยการทบทวนโดยไม่ต้องรันโปรแกรม
  4. ลูปเขียนเป็น i <= items.length ทำให้อ่านเกินท้ายอาร์เรย์เฉลยdefect ในโค้ด จะทำให้เกิด failure เมื่อถูกรัน
  5. ผู้ใช้กดบันทึกแล้วหน้าจอค้างไป 30 วินาทีเฉลยfailure ยังไม่รู้ว่า defect อยู่ที่ไหน ต้องดีบักต่อ
  6. นักพัฒนาลืมว่าเดือนกุมภาพันธ์ของปีอธิกสุรทินมี 29 วันเฉลยerror คนลืม ส่งผลให้เขียนโค้ดคำนวณวันผิด

2.4 หลัก 7 ข้อของการทดสอบ

ISTQB CTFL 4.0.1 หัวข้อ 1.3 สรุปหลักการที่ใช้ได้กับทุกโครงงานไว้ 7 ข้อ ตารางนี้จับคู่แต่ละข้อกับงานที่ทีมจะทำในวิชานี้

หลักการความหมายทีมจะทำอะไรสัปดาห์
1. แสดงว่ามีข้อบกพร่อง ไม่ได้พิสูจน์ว่าไม่มี (testing shows the presence, not the absence of defects)ผ่านทุกกรณีแปลว่า "ยังไม่พบ" ไม่ใช่ "ไม่มี"รายงานว่าทดสอบอะไร พบอะไร เหลือความเสี่ยงอะไร ไม่เขียนว่า "ระบบไม่มีบั๊ก"16 · CP5
2. ทดสอบทุกกรณีเป็นไปไม่ได้ (exhaustive testing is impossible)ต้องเลือกกรณีด้วยความเสี่ยงและเทคนิคออกแบบจัดลำดับตามความเสี่ยง และใช้ EP/BVA ออกแบบกรณีทดสอบ5–6
3. ทดสอบเร็ว ประหยัดเวลาและเงิน (early testing saves time and money)เริ่มตั้งแต่ทบทวนความต้องการ ไม่ต้องรอโค้ดinspection SRS ไขว้ทีม ก่อนเขียนโค้ดส่วนใหญ่3 · CP1
4. ข้อบกพร่องมักกระจุกตัว (defects cluster together)ส่วนน้อยของระบบมักมีข้อบกพร่องส่วนใหญ่ดูว่าโมดูลไหนมีข้อบกพร่องมากใน issue tracker แล้วทดสอบเพิ่มตรงนั้น15
5. กรณีทดสอบเดิมจะสึก (tests wear out)รันชุดเดิมซ้ำ ๆ จะไม่พบอะไรใหม่ ต้องปรับและเพิ่มทบทวนและเพิ่มชุด regression ทุกครั้งที่แก้บั๊ก12
6. ขึ้นกับบริบท (testing is context dependent)แอปร้านกาแฟกับระบบการแพทย์ทดสอบไม่เหมือนกันเขียนแผนการทดสอบตามประเภทระบบและผู้ใช้ของทีม ไม่ใช้แม่แบบเดียวกันทุกทีม5 · CP2
7. ไม่มีบั๊ก ไม่ได้แปลว่าใช้ได้ (absence-of-defects fallacy)ระบบไร้ข้อบกพร่องแต่ไม่ตอบโจทย์ผู้ใช้ ก็ยังล้มเหลวทำ UAT กับผู้ใช้หรือลูกค้าจริงของโครงงาน12 · CP4

ข้อ 3 และข้อ 7 คือเหตุผลที่วิชานี้เริ่มจากทบทวน SRS และจบด้วย UAT กับผู้ใช้จริง

หลักข้อ 2 ในตัวเลข
  • ฟังก์ชันบวกเลขจำนวนเต็ม 32 บิต 2 ตัว มีกรณีที่เป็นไปได้ 232 × 232 = 264 ≈ 1.8 × 1019 กรณี ถ้าทดสอบได้ 1,000 ล้านกรณีต่อวินาที ต้องใช้เวลาราว 585 ปี
  • ฟอร์มสมัครสมาชิก 3 ช่อง: อายุ 0–120 (121 ค่า) × จังหวัด (77 ค่า) × วิธีชำระเงิน (4 ค่า) = 37,268 กรณี

ทางออกไม่ใช่ทดสอบให้มากที่สุด แต่เลือกให้ฉลาด ใช้ความเสี่ยงจัดลำดับ (สัปดาห์ 5) และเทคนิคอย่าง equivalence partitioning กับ boundary value analysis (สัปดาห์ 6) ลดจำนวนกรณีโดยยังครอบคลุม

2.5 testing กับ debugging

testingdebugging
เป้าหมายทำให้ปัญหาปรากฏหาต้นเหตุแล้วแก้
เริ่มเมื่อวางแผนและออกแบบได้ก่อนมีโค้ดมี failure หรือรายงานข้อบกพร่อง
ผลงานกรณีทดสอบ ผลการทดสอบ และรายงานข้อบกพร่องโค้ดที่แก้แล้ว ซึ่งต้องทดสอบซ้ำเสมอ
มักทำโดยผู้ทดสอบหรือนักพัฒนานักพัฒนา

หลังดีบักแล้วต้องทดสอบสองแบบ confirmation testing รันกรณีที่เคยล้มอีกครั้งว่าแก้แล้วจริง และ regression testing รันชุดทดสอบที่เกี่ยวข้องว่าการแก้ไม่ทำให้ส่วนอื่นพัง

2.6 QA, QC และ testing

QA · Quality AssuranceQC · Quality Control
เน้นกระบวนการ · ป้องกันไม่ให้เกิดผลิตภัณฑ์ · ตรวจหาแล้วแก้
ตัวอย่างกำหนดว่าทุก PR ต้องมีคนรีวิว ตั้งมาตรฐานการเขียนโค้ดและแม่แบบเอกสาร อบรมทีม ปรับขั้นตอนจากบทเรียนตรวจ SRS หรือโค้ดของงานชิ้นนั้น รันกรณีทดสอบกับระบบ

ทั้งสองอยู่ใต้การจัดการคุณภาพ (quality management) testing เป็น QC รูปแบบหลัก และผลการทดสอบเป็นข้อมูลให้ QA ใช้ปรับกระบวนการ

วิธีจำ

ถ้าคำตอบคือ "เปลี่ยนวิธีทำงานของทีม" เป็น QA · ถ้าคำตอบคือ "ตรวจงานชิ้นนี้" เป็น QC

QA หรือ QC (คลิกแต่ละข้อเพื่อดูเฉลย)
  1. ตกลงกันว่าทุก PR ต้องมีคนรีวิวอย่างน้อย 1 คนก่อน mergeเฉลยQA กำหนดกระบวนการเพื่อป้องกัน
  2. รัน unit test ใน CI แล้วพบ 3 กรณีไม่ผ่านเฉลยQC (testing) ตรวจผลิตภัณฑ์ด้วยการรันโปรแกรม
  3. จัดอบรมทีมเรื่องการเขียนกรณีทดสอบเฉลยQA พัฒนาคนและวิธีทำงาน
  4. ตรวจ SRS ด้วย checklist แล้วพบความต้องการที่กำกวม 5 ข้อเฉลยQC (static testing) ตรวจงานชิ้นนี้โดยไม่รันโปรแกรม
  5. นำสถิติข้อบกพร่องของ Sprint ที่แล้วมาปรับขั้นตอนการทำงานเฉลยQA ใช้ผลจาก QC มาปรับปรุงกระบวนการ
  6. ให้ผู้ใช้จริงทดลองระบบตามสถานการณ์จริงใน UATเฉลยQC (testing · validation) ตรวจว่าผลิตภัณฑ์ตรงความคาดหวัง

ส่วนที่ 3วิเคราะห์กรณีซอฟต์แวร์ล้มเหลวจริง

3.1 กรอบการวิเคราะห์ 5 ส่วน

กิจกรรมในห้องให้แต่ละทีมวิเคราะห์ 1 กรณีด้วยใบงาน 5 ส่วน เป้าหมายไม่ใช่หาคนผิด แต่ฝึกไล่ห่วงโซ่จากคนพลาดไปถึงระบบพัง แล้วหาจุดที่การทวนสอบควรตัดห่วงโซ่นั้น ใช้กรอบเดียวกันนี้กับข้อบกพร่องในโครงงานของทีมได้ทั้งภาค และจะกลับมาอีกครั้งในการวิเคราะห์สาเหตุของ CP5

ส่วนตอบอะไรข้อควรระวัง
A เกิดอะไรขึ้นfailure ที่สังเกตได้ ใครได้รับผลกระทบ เสียหายแค่ไหนตอบใน 2 ประโยค
B ห่วงโซ่ใครพลาดอะไร (error) ข้อบกพร่องอยู่ในผลงานไหน (defect) และ root causedefect อาจอยู่ในเอกสาร แบบ หรือขั้นตอน deploy ก็ได้
C หลักการที่ถูกละเลยเลือก 1–2 ข้อจากหลัก 7 ข้อ พร้อมเหตุผลอ้างข้อเท็จจริงในการ์ดอย่างน้อย 1 ข้อ
D V&V ที่จับได้ทบทวน, unit, integration, system, acceptance, non-functional, regression หรือการตรวจก่อน deploy เป็น QA หรือ QC และควรทำตอนไหนไม่ตอบกว้าง ๆ ว่า "ทดสอบให้มากขึ้น"
E บทเรียนสำหรับโครงงาน1 การกระทำที่ทีมทำได้จริงกับโครงงานภาคนี้ต้องเจาะจง เช่น "เพิ่มกรณีทดสอบค่าขอบของ..."

3.2 ตัวอย่างที่ทำให้ดู: Patriot ที่ Dhahran

วันที่ 25 กุมภาพันธ์ 2534 (1991) ระบบป้องกันขีปนาวุธ Patriot ที่ Dhahran ซาอุดีอาระเบีย ติดตามและสกัดขีปนาวุธ Scud ไม่ได้ Scud ตกใส่ค่ายทหาร มีผู้เสียชีวิต 28 คน ข้อเท็จจริงจากรายงาน GAO มีดังนี้ ระบบนับเวลาเป็นหน่วย 1/10 วินาที แล้วคูณด้วย 1/10 ในรีจิสเตอร์ fixed-point 24 บิต ค่า 0.1 จึงถูกตัดเศษ ความคลาดเคลื่อนสะสมตามเวลาที่เครื่องเปิดต่อเนื่อง วันเกิดเหตุเครื่องทำงานต่อเนื่องเกิน 100 ชั่วโมง เวลาคลาดราว 0.34 วินาที ช่วงค้นหาเป้าหมายจึงเลื่อนผิดที่ ระบบออกแบบให้เคลื่อนย้ายได้และทำงานที่จุดหนึ่งเพียงไม่กี่ชั่วโมง และไม่เคยใช้ป้องกัน Scud มาก่อน กองทัพพบอาการหลังเปิดต่อเนื่อง 8 ชั่วโมงและแก้ซอฟต์แวร์แล้ว แต่ฉบับแก้ไปถึง Dhahran หนึ่งวันหลังเหตุการณ์

ส่วนใบงานที่กรอกแล้ว
Aระบบติดตามและสกัด Scud ไม่ได้ Scud ตกใส่ค่ายทหาร มีผู้เสียชีวิต 28 คน
Berror: ออกแบบโดยสมมติว่าเปิดเครื่องไม่กี่ชั่วโมง · defect: คำนวณเวลาด้วย fixed-point 24 บิต ค่าคลาดสะสม · failure: หลัง 100 ชั่วโมง เวลาคลาด 0.34 วินาที ค้นหาผิดที่
Cข้อ 6 ขึ้นกับบริบท: บริบทใช้งานเปลี่ยน (ป้องกัน Scud และเปิดต่อเนื่องหลายวัน) แต่การทดสอบยังอยู่บนสมมติฐานเดิม
DQC: system test ตามการใช้งานจริง และ soak test เปิดต่อเนื่องหลายวัน · QA: ขั้นตอนส่งฉบับแก้ถึงหน่วยงานให้เร็ว

ใช้กับโครงงานของคุณ

ลองถามคำถามเดียวกับโครงงานของทีม มีส่วนไหนที่นำโค้ดเดิมมาใช้ในบริบทใหม่ มีจุดเชื่อมต่อไหนที่สองฝั่งอาจตีความต่างกัน เช่น รูปแบบวันที่ หน่วย หรือรหัสสถานะ และมีข้อความแจ้งเตือนหรือ log ที่ทีมเห็นแล้วแต่ไม่มีใครดูต่อไหม คำตอบเหล่านี้คือ "ส่วนที่เสี่ยง 3 อย่าง" ใน V&V Profile (D02)

ลองตอบก่อนอ่านต่อ (คลิกแต่ละข้อเพื่อดูเฉลย)
  1. ในกรณี Ariane 5 การมีระบบอ้างอิงแนวเฉื่อย 2 ตัวช่วยไม่ได้ เพราะอะไรเฉลยทั้งสองตัวรันซอฟต์แวร์เดียวกันกับข้อมูลเดียวกัน จึงล้มด้วยเหตุเดียวกันห่างกันราว 0.05 วินาที การสำรองช่วยกับความเสียหายแบบสุ่มของฮาร์ดแวร์ ไม่ช่วยกับ defect ในซอฟต์แวร์
  2. Mars Climate Orbiter: การทวนสอบแบบใดควรจับปัญหาหน่วยวัดได้ก่อนเฉลยทบทวนส่วนต่อประสานเทียบกับข้อกำหนดส่วนต่อประสาน และ integration test ที่ตรวจหน่วยของข้อมูลที่ส่งข้ามระบบ (verification)
  3. Knight Capital: defect อยู่ในโค้ด ในขั้นตอนติดตั้ง หรือทั้งสองที่เฉลยทั้งสองที่ โค้ดเก่าที่เสียยังค้างอยู่และแฟล็กถูกนำมาใช้ซ้ำ (โค้ด) และติดตั้งไม่ครบทุกเครื่องโดยไม่มีการตรวจ (ขั้นตอน deploy)
  4. Therac-25: เมื่อทำซ้ำอาการไม่ได้ การสรุปว่าเป็นปัญหาฮาร์ดแวร์ผิดหลักข้อใดเฉลยผิดหลักข้อ 1 การไม่พบในการทดสอบไม่ได้แปลว่าไม่มี และ race condition มักทำซ้ำยากเพราะขึ้นกับจังหวะเวลา ควรบันทึกเงื่อนไขที่เกิดให้ละเอียดและหาต้นเหตุต่อ

สรุปสิ่งที่ต้องจำจากครั้งที่ 1

  1. วิชานี้หาหลักฐานว่าซอฟต์แวร์ถูกตามแบบ (verification) และตรงกับที่ผู้ใช้ต้องการ (validation) โดยใช้โครงงาน ENGSE212 ของทีม
  2. การทดสอบมีทั้งแบบไม่รันโปรแกรม (static) และรันโปรแกรม (dynamic) และเริ่มได้ตั้งแต่ยังไม่มีโค้ด
  3. error คือคนพลาด defect คือข้อบกพร่องในผลงาน failure คือระบบทำงานผิดที่สังเกตได้ และ root cause คือเหตุที่ทำให้คนพลาด
  4. ผ่านทุกกรณีแปลว่า "ยังไม่พบ" และทดสอบทุกกรณีไม่ได้ จึงต้องเลือกตามความเสี่ยง
  5. testing ทำให้ปัญหาปรากฏ debugging หาต้นเหตุและแก้ แล้วต้องทดสอบซ้ำเสมอ
  6. QA ป้องกันที่กระบวนการ QC ตรวจที่ผลิตภัณฑ์ และ testing คือ QC รูปแบบหลัก
  7. ความล้มเหลวจริงมักมาจากไม่กี่รูปแบบ เช่น ใช้ของเดิมกับบริบทใหม่ จุดเชื่อมต่อไม่ตรงกัน และไม่ทดสอบตามการใช้งานจริง

ศัพท์สำคัญ

ศัพท์ความหมาย
testingการประเมินคุณภาพของซอฟต์แวร์และผลงานที่เกี่ยวข้อง รวมวางแผน ออกแบบ ดำเนินการ และรายงาน
static testingการทดสอบเชิงสถิต: ตรวจผลงานโดยไม่รันโปรแกรม
dynamic testingการทดสอบเชิงพลวัต: รันโปรแกรมแล้วเทียบผลกับที่คาดหวัง
error (mistake)การกระทำของคนที่ให้ผลผิด
defect (bug, fault)ข้อบกพร่องในผลงาน
failureระบบทำงานผิดที่สังเกตได้ขณะทำงาน
root causeเหตุพื้นฐานที่ทำให้เกิดข้อบกพร่อง
debuggingการหาต้นเหตุของ failure แล้วแก้
confirmation testingทดสอบซ้ำว่าแก้แล้วจริง
regression testingทดสอบว่าการเปลี่ยนแปลงไม่ทำให้ส่วนอื่นพัง
QAการประกันคุณภาพ: เน้นกระบวนการ ป้องกันไม่ให้เกิด
QCการควบคุมคุณภาพ: เน้นผลิตภัณฑ์ ตรวจหาแล้วแก้
