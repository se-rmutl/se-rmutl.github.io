> ใช้ดูความยาวและระดับรายละเอียด ทีมของคุณเขียนจากระบบของตัวเองตามแม่แบบ `vv-strategy-template.md`

- ระบบ: SE LabBook ระบบจองห้องปฏิบัติการและยืมอุปกรณ์ของหลักสูตร
- ฉบับ / วันที่: 1.0 / 4 ธ.ค. 2569

## 1. ระดับความสำคัญของระบบ (integrity level ตาม IEEE 1012)

| คำถาม | คำตอบของทีม |
|---|---|
| ถ้าระบบทำงานผิด ผลเสียร้ายแรงที่สุดคืออะไร เกิดกับใคร | จองห้องซ้อนจนคาบเรียนไม่มีห้อง และอุปกรณ์หายเพราะบันทึกการยืมผิด เกิดกับนักศึกษา อาจารย์ และเจ้าหน้าที่ ส่วนที่ร้ายแรงกว่าคือชื่อ อีเมล และรหัสนักศึกษารั่วไหล |
| ความรุนแรงของผลเสีย | การจองและการยืมผิด: ปานกลาง · ข้อมูลส่วนบุคคลรั่ว: ร้ายแรง |
| โอกาสเกิด | การจองผิด: บางครั้ง (กฎการจองซับซ้อน) · ข้อมูลรั่ว: แทบไม่เกิด ถ้าตรวจสิทธิ์ครบ |
| integrity level ของทั้งระบบ (1–4) และเหตุผล | ระดับ 2 ผลเสียส่วนใหญ่ทำให้งานล่าช้าและแก้ด้วยมือได้ ไม่กระทบความปลอดภัยของคน |
| ส่วนที่ระดับสูงกว่า และเหตุผล | F-01 บัญชีผู้ใช้และสิทธิ์ ระดับ 3 เพราะคุมการเข้าถึงข้อมูลส่วนบุคคล (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล) จึงเพิ่มการทดสอบสิทธิ์ครบทุกบทบาท branch coverage ไม่ต่ำกว่าร้อยละ 80 และรีวิวโค้ด 2 คน |

## 2. ทดสอบอะไร ระดับไหน เมื่อไร

| ระดับการทดสอบ | ทดสอบอะไรในระบบของเรา | Sprint หรือช่วงเวลา | เครื่องมือ | ผู้รับผิดชอบ |
|---|---|---|---|---|
| component (unit) | กฎการจอง (เวลาทับ จองล่วงหน้าไม่เกิน 14 วัน) กฎการยืม (ไม่เกิน 3 ชิ้น ค้างคืนห้ามยืม) การตรวจสิทธิ์ | Sprint 1–2 (ธ.ค.–ม.ค.) | Jest | กิตติ |
| integration | API การจองและการยืมกับฐานข้อมูล PostgreSQL การส่งอีเมลผ่าน SMTP การเข้าสู่ระบบด้วยบัญชี Microsoft | Sprint 2–3 (ม.ค.–ก.พ.) | Supertest, Postman/Newman | ธนา |
| system | ทุก use case แบบ end-to-end บนเบราว์เซอร์ เวลาตอบสนองและการรองรับผู้ใช้พร้อมกัน | Sprint 3 (ก.พ.) | Playwright, k6 | พิมพ์ชนก, ธนา |
| acceptance (UAT) | เจ้าหน้าที่ห้องปฏิบัติการ 2 คน และนักศึกษา 10 คน ทำงานจริงตามสถานการณ์ | ปลาย ก.พ. | แบบบันทึก UAT | กิตติ |

## 3. ทวนสอบเชิงสถิต (ไม่ต้องรันโค้ด)

| สิ่งที่ทบทวน | วิธี | เมื่อไร |
|---|---|---|
| SRS | inspection ไขว้ทีม ด้วยรายการตรวจ SRS | ครั้งที่ 3 (CP1) |
| เอกสารออกแบบ | walkthrough สถาปัตยกรรม ER และ API spec | ครั้งที่ 4 |
| โค้ด | pull request ที่มีเพื่อนรีวิว 1 คน (F-01 รีวิว 2 คน) และ ESLint ใน GitHub Actions | ทุก Sprint ตั้งแต่ครั้งที่ 4 |

## 4. ชนิดการทดสอบ

- เชิงฟังก์ชัน: ความต้องการที่มีความสำคัญ M ทุกข้อใน F-01 ถึง F-04 และข้อ S ที่ทำเสร็จทันภาคนี้
- เชิงไม่เป็นฟังก์ชัน: ประสิทธิภาพ (NFR-01, NFR-02) เพราะช่วงก่อนคาบมีคนจองพร้อมกันมาก และความมั่นคงปลอดภัย (NFR-05, NFR-07) เพราะมีข้อมูลส่วนบุคคล
- regression: ชุด unit test และ API test รันใน CI ทุก pull request ชุด end-to-end รันก่อนปิด Sprint
- ไม่ทดสอบ: การรองรับเบราว์เซอร์รุ่นเก่า (นอกขอบเขตใน SRS) และการกู้คืนจากภัยพิบัติของเซิร์ฟเวอร์ (หลักสูตรดูแล)
