1.1 ทำไมต้องแบ่งการทดสอบเป็นระดับ

ซอฟต์แวร์ถูกสร้างจากชิ้นเล็กไปชิ้นใหญ่ ฟังก์ชันรวมเป็นส่วนประกอบ ส่วนประกอบรวมเป็นระบบ แล้วระบบถูกส่งให้ผู้ใช้ ข้อบกพร่องเกิดได้ในทุกขั้น และแต่ละขั้นมีข้อบกพร่องคนละแบบ ถ้าทดสอบเฉพาะตอนท้าย เมื่อพบปัญหาจะไม่รู้ว่าต้นเหตุอยู่ชั้นไหน และแก้ได้แพงที่สุด

เทียบกับการผลิตรถยนต์

โรงงานไม่ได้รอให้ประกอบรถเสร็จแล้วค่อยขับดูว่าใช้ได้ไหม แต่ทดสอบลูกสูบหนึ่งชิ้นว่าขนาดถูกต้อง (Unit) ทดสอบว่าเครื่องยนต์ต่อกับเกียร์แล้วส่งกำลังได้ (Integration) นำรถทั้งคันไปวิ่งในสนามทดสอบตามสเปก (System) แล้วให้ลูกค้าลองขับว่าตรงกับที่ต้องการใช้จริงไหม (UAT) แต่ละขั้นใช้สถานที่และเครื่องมือต่างกัน เช่นเดียวกับสภาพแวดล้อมการทดสอบซอฟต์แวร์

การแบ่งระดับให้ประโยชน์สามข้อ

  1. พบเร็ว แก้ถูก ข้อบกพร่องที่พบในระดับ Unit แก้ได้ทันทีโดยผู้เขียนโค้ด ถ้าหลุดไปพบใน UAT ต้องย้อนผ่านหลายขั้น
  2. ชี้ต้นเหตุได้ ยิ่งขอบเขตเล็ก ยิ่งรู้ว่าปัญหาอยู่ตรงไหน
  3. ไม่ทดสอบซ้ำซ้อน แต่ละระดับมีหน้าที่ของตัวเอง ระดับบนไม่ต้องทดสอบทุกค่าที่ระดับล่างทดสอบแล้ว

1.2 V-Model และฐานการทดสอบ

V-Model วางงานพัฒนาไว้ฝั่งซ้าย และงานทดสอบไว้ฝั่งขวา เอกสารแต่ละชั้นทางซ้ายคือ ฐานการทดสอบ (test basis) ของระดับที่อยู่ตรงข้าม ฐานการทดสอบคือเอกสารที่บอกว่าผลที่คาดหวังควรเป็นอะไร ผู้ทดสอบต้องเทียบผลจริงกับเอกสารนี้ ไม่ใช่เทียบกับโค้ด

ระดับฐานการทดสอบคำถามหลัก
Unitออกแบบรายละเอียด กฎทางธุรกิจที่อยู่ในฟังก์ชันชิ้นส่วนนี้ทำงานถูกตามที่ออกแบบหรือไม่
Integrationออกแบบสถาปัตยกรรม (HLD) ส่วนต่อประสาน สัญญา APIส่วนประกอบส่งข้อมูลและเรียกใช้กันถูกต้องหรือไม่
SystemSRS ความต้องการเชิงหน้าที่ NFR Use Case เกณฑ์การยอมรับระบบทั้งหมดทำตามความต้องการที่เขียนไว้หรือไม่
UATความต้องการของผู้ใช้ กระบวนการทำงานจริง เกณฑ์การยอมรับที่ตกลงกันผู้ใช้ใช้ระบบทำงานของตนได้สำเร็จหรือไม่
ลองคิดก่อนอ่านต่อ

ถ้าทีมไม่มีเอกสารออกแบบสถาปัตยกรรมเลย การทดสอบระดับ Integration จะรู้ได้อย่างไรว่าผลที่ถูกต้องคืออะไร

คำตอบคือ รู้ได้ยาก ทีมมักใช้โค้ดที่เขียนแล้วเป็นตัวตั้ง ซึ่งเท่ากับยอมรับทุกอย่างที่โค้ดทำ นี่คือเหตุผลที่ครั้งที่ 1 ทบทวนเอกสารออกแบบก่อนเริ่มทดสอบ

1.4 หกเรื่องที่ใช้แยกระดับ

เมื่อพูดถึงระดับใดก็ตาม ให้ตอบหกเรื่องนี้ได้ครบ ถ้าตอบได้ครบ จะไม่สับสนระหว่างระดับ

เรื่องถามว่าตัวอย่างคำตอบของ Unitตัวอย่างคำตอบของ UAT
วัตถุประสงค์ทดสอบเพื่อหาอะไรตรรกะในฟังก์ชันผิดหรือไม่ผู้ใช้ทำงานสำเร็จหรือไม่
ฐานการทดสอบผลที่คาดหวังมาจากเอกสารใดออกแบบรายละเอียดงานจริงของผู้ใช้

ข้อบกพร่องที่พบจับปัญหาแบบไหนได้ดีเงื่อนไขขอบผิดขั้นตอนไม่ตรงงานจริง
ผู้ทดสอบใครทำผู้พัฒนาผู้ใช้จริงหรือตัวแทน
สภาพแวดล้อมทดสอบที่ไหน อะไรจริง อะไรจำลองเครื่องผู้พัฒนา ข้อมูลอยู่ในโค้ดสภาพแวดล้อม UAT ใกล้ระบบจริง

1.5 สภาพแวดล้อมการทดสอบคืออะไร

สภาพแวดล้อมการทดสอบ (test environment) คือทุกสิ่งที่ต้องมีเพื่อให้ทำการทดสอบได้ ทั้งเครื่อง ซอฟต์แวร์ เครื่องมือ ตัวจำลอง และสิ่งสนับสนุนอื่น ๆ สภาพแวดล้อมที่ดีต้องทำให้รันได้และรันซ้ำแล้วได้ผลเดิม ถ้ารันซ้ำแล้วผลเปลี่ยนไปโดยที่โค้ดไม่เปลี่ยน ผลการทดสอบนั้นเชื่อไม่ได้

ข้อมูลทดสอบข้อมูลตั้งต้นที่ระบบมีก่อนเริ่ม และวิธีรีเซ็ตtests/fixtures/*.jsonข้อมูลค้างจากรอบก่อน ทำให้ผลเพี้ยน
การตั้งค่าและบัญชีค่าตั้งของระบบ บัญชีผู้ใช้ทุกบทบาท สิทธิ์NODE_ENV=test · บัญชี u-org-01 u-room-01 u-equip-01ทดสอบสิทธิ์ไม่ได้ หรือเผลอใช้ค่าของระบบจริง
ระบบภายนอกระบบที่เราไม่ได้สร้างแต่ต้องเชื่อมต่อบริการอีเมลบางกรณีรันไม่ได้ ต้องบันทึก Blocked
เครื่องมือทดสอบโปรแกรมที่สั่งรันและตรวจผลJest · Supertest · Playwrightรันอัตโนมัติไม่ได้ ผลอ่านยาก

1.6 บันไดสภาพแวดล้อม

องค์กรส่วนใหญ่ไม่ได้มีสภาพแวดล้อมเดียว แต่มีหลายขั้นเรียงเป็นบันได ซอฟต์แวร์รุ่นหนึ่งจะไต่ขึ้นทีละขั้น ผ่านเกณฑ์ของขั้นหนึ่งแล้วจึงขึ้นขั้นถัดไป

ขั้นมีไว้ทำอะไรระดับที่ทดสอบข้อมูล
DEV เครื่องผู้พัฒนาเขียนโค้ดและรันการทดสอบเร็ว ๆ ระหว่างพัฒนาUnitในโค้ดทดสอบ
CI รันอัตโนมัติรันชุดทดสอบทุกครั้งที่มีการส่งโค้ด บนเครื่องกลางที่สะอาดUnit · APIสร้างใหม่ทุกครั้ง
TEST ทดสอบรวมติดตั้งส่วนประกอบรวมกัน ทดสอบรอยต่อIntegrationชุดข้อมูลทดสอบ รีเซ็ตได้
STAGING เหมือนระบบจริงติดตั้งแบบเดียวกับระบบจริง ทดสอบทั้งระบบและ NFRSystem · NFRปริมาณใกล้จริง ไม่ใช่ข้อมูลส่วนบุคคลจริง
UATให้ผู้ใช้จริงทดลองใช้งานUATเหมือนจริงตามงาน ปกปิดแล้ว
PROD ระบบจริงให้บริการผู้ใช้จริง ไม่ใช่ที่ทดสอบเฝ้าดูหลังส่งมอบข้อมูลจริงของผู้ใช้

ยิ่งขึ้นบันได สภาพแวดล้อมยิ่งเหมือนการใช้งานจริง ผลจึงน่าเชื่อขึ้น แต่ก็ช้าลง แพงขึ้น ต้องนัดหมายมากขึ้น และเมื่อพบปัญหาจะหาต้นเหตุยากขึ้น นี่คือเหตุผลที่ต้องทดสอบให้มากที่ระดับล่าง แล้วใช้ระดับบนยืนยันเฉพาะสิ่งที่ระดับล่างมองไม่เห็น

ทดสอบบนระบบจริง

ทีมที่มีเพียงเครื่องผู้พัฒนากับระบบที่ใช้งานจริง มักทดสอบ System และ UAT บนระบบจริงด้วยข้อมูลจริง ซึ่งเสี่ยงทั้งข้อมูลเสียหาย ข้อมูลส่วนบุคคลรั่ว และผู้ใช้จริงได้รับอีเมลทดสอบ อย่างน้อยต้องมีสภาพแวดล้อมแยกหนึ่งชุดสำหรับทดสอบ (ดูบทที่ 6.6)

สรุปบทที่ 1
  • การทดสอบแบ่งเป็นสี่ระดับ เพื่อพบเร็ว ชี้ต้นเหตุได้ และไม่ซ้ำซ้อน
  • แต่ละระดับมีฐานการทดสอบเป็นเอกสารฝั่งซ้ายของ V-Model
  • Verification เทียบกับเอกสาร · Validation เทียบกับความต้องการจริงของผู้ใช้
  • ทุกระดับตอบหกเรื่อง: วัตถุประสงค์ ฐาน สิ่งที่ทดสอบ ข้อบกพร่อง ผู้ทดสอบ สภาพแวดล้อม
  • สภาพแวดล้อมมีหกส่วน และจัดเป็นบันได DEV → CI → TEST → STAGING → UAT → PROD

ทดสอบความเข้าใจท้ายบท

1. ฐานการทดสอบของระดับ System คืออะไร

SRS ความต้องการเชิงหน้าที่ NFR Use Case และเกณฑ์การยอมรับ ผู้ทดสอบเทียบผลจริงกับเอกสารเหล่านี้

2. รันชุดทดสอบเดิมสองครั้งโดยไม่ได้แก้โค้ด ได้ผลต่างกัน ควรสงสัยอะไรก่อน

สงสัยสภาพแวดล้อม เช่น ข้อมูลค้างจากรอบก่อน ไม่ได้รีเซ็ต หรือการทดสอบพึ่งเวลาหรือเครือข่าย สภาพแวดล้อมที่ดีต้องรันซ้ำได้ผลเดิม

3. ทำไมไม่ควรทดสอบทุกอย่างที่ STAGING

เพราะช้า แพง และหาต้นเหตุยาก ควรทดสอบให้มากที่ระดับล่าง แล้วใช้ STAGING ยืนยันสิ่งที่ระดับล่างมองไม่เห็น

Unit Testing

เวลาอ่านประมาณ 20 นาทีสไลด์ 12–19ข้อสอบ 3.1

บทนี้ตอบคำถาม ทดสอบชิ้นเล็กที่สุดของโค้ดอย่างไร ในสภาพแวดล้อมแบบไหน

อ่านจบแล้วได้ หลักการและสภาพแวดล้อมของ Unit

2.1 Unit testing คืออะไร

Unit testing หรือที่มาตรฐาน ISTQB เรียกว่า component testing คือการทดสอบชิ้นส่วนที่เล็กที่สุดที่ทดสอบแยกได้ เช่น ฟังก์ชัน เมธอด หรือคลาสหนึ่งตัว โดยแยกชิ้นส่วนนั้นออกจากส่วนอื่นของระบบ เพื่อให้แน่ใจว่าถ้าผลผิด ความผิดอยู่ในชิ้นนั้นจริง

วัตถุประสงค์

ตรวจว่าตรรกะภายในทำตามกฎครบทุกกรณี ทุกค่าขอบ ทุกเงื่อนไข

ฐานการทดสอบ

ออกแบบรายละเอียด และกฎที่ถูกกำหนดให้อยู่ในฟังก์ชันนั้น เช่น R-A ขอล่วงหน้าได้ 3 ถึง 30 วัน

ข้อบกพร่องที่พบได้ดี

เงื่อนไขขอบผิด (ใช้ <= แทน <) คำนวณผิด ลืมกรณีค่าว่างหรือค่าติดลบ ลำดับเงื่อนไขผิด

ผู้ทดสอบ และเวลา

ผู้พัฒนา เขียนพร้อมโค้ดหรือก่อนโค้ด รันทุกครั้งที่แก้ ชุดหนึ่งมีได้หลายร้อยข้อ รันจบในไม่กี่วินาที

2.2 คุณสมบัติของ Unit test ที่ดี

แนวทางที่นิยมใช้คือ F.I.R.S.T. ถ้าขาดข้อใด Unit test จะเสียประโยชน์หลักของมันไป

คุณสมบัติหมายความว่าถ้าไม่มี
Fast เร็วรันทั้งชุดในไม่กี่วินาทีผู้พัฒนาไม่อยากรันบ่อย ข้อบกพร่องหลุดไปไกล
Independent อิสระแต่ละข้อไม่พึ่งผลหรือลำดับของข้ออื่นข้อหนึ่งพัง ข้ออื่นพังตาม หาต้นเหตุยาก
Repeatable ซ้ำได้รันกี่ครั้ง ที่เครื่องไหน วันไหน ผลเหมือนเดิมผลเปลี่ยนตามเวลาหรือเครื่อง เชื่อไม่ได้
Self-validating ตรวจตัวเองได้ผลเป็นผ่านหรือไม่ผ่านชัดเจน ไม่ต้องให้คนอ่านต้องมีคนนั่งดูผลทุกครั้ง
Timely ทันเวลาเขียนพร้อมหรือก่อนโค้ดที่ทดสอบเขียนทีหลังมักเขียนให้ผ่านตามโค้ด ไม่ได้ตามกฎ

2.3 โครง Arrange · Act · Assert

Unit test ทุกข้อมีสามส่วนเสมอ Arrange เตรียมข้อมูลที่ป้อน Act เรียกสิ่งที่ทดสอบ Assert เทียบผลจริงกับผลที่คาดหวังจากกฎ ตัวอย่างนี้ทดสอบกฎ R-A ด้วยค่าขอบทั้งชุดจากครั้งที่ 2 ในโค้ดเดียว

tests/unit/requestService.test.js
describe('R-A ขอล่วงหน้าได้ 3 ถึง 30 วัน', () => {
  test.each([
    ['TC-01', 2,  false],   // เลยขอบล่าง
    ['TC-02', 3,  true ],   // ขอบล่าง
    ['TC-03', 15, true ],   // ตัวแทน
    ['TC-04', 30, true ],   // ขอบบน
    ['TC-05', 31, false],   // เลยขอบบน
  ])('%s ขอล่วงหน้า %i วัน ควรผ่าน=%s', (id, days, expected) => {
    const input = { title: 'สัมมนา', daysAhead: days, items: [room] }; // Arrange
    const result = validateRequest(input, resources);                // Act
    expect(result.ok).toBe(expected);                                // Assert
  });
});

ห้าแถวใน test.each คือกรณีทดสอบ TC-01 ถึง TC-05 ค่า 2 และ 31 อยู่นอกช่วง จึงคาดหวัง false ค่า 3 15 และ 30 อยู่ในช่วง จึงคาดหวัง true สังเกตว่าผลที่คาดหวังมาจากกฎ ไม่ได้มาจากการดูว่าโค้ดทำอะไร

2.4 สภาพแวดล้อมของ Unit

สภาพแวดล้อมการทดสอบระดับ Unit
ที่ไหนเครื่องผู้พัฒนา (DEV) และเครื่อง CI ที่รันอัตโนมัติทุกครั้งที่ส่งโค้ด
อะไรเป็นของจริงฟังก์ชันที่ทดสอบเพียงตัวเดียว
อะไรใช้ตัวจำลองทุกสิ่งที่ฟังก์ชันเรียกใช้ เช่น ข้อมูลจากไฟล์ บริการอื่น เวลาปัจจุบัน ตัวสุ่ม การส่งอีเมล
ข้อมูลเขียนไว้ในโค้ดทดสอบ (ในตัวอย่างคือ input และ resources) ไม่อ่านไฟล์หรือฐานข้อมูล
การตั้งค่าไม่ต้องเปิดเซิร์ฟเวอร์ ไม่ต้องมีเครือข่าย ไม่ต้องมีบัญชีผู้ใช้
เครื่องมือJest (JavaScript) · pytest (Python) · JUnit (Java) · xUnit (C#)
สั่งรันในแอปสาธิตnpm run test:unit ในโฟลเดอร์ backend

ทำไมต้องแยกจากส่วนอื่น ถ้า Unit test อ่านไฟล์ข้อมูลจริง เมื่อมีคนแก้ไฟล์ ผลการทดสอบจะเปลี่ยนตาม ทั้งที่โค้ดไม่ได้เปลี่ยน และถ้าการทดสอบไม่ผ่าน จะไม่รู้ว่าผิดที่ฟังก์ชันหรือผิดที่ข้อมูล การแยกจึงทำให้ได้ทั้งความเร็ว (Fast) และผลที่รันซ้ำได้ (Repeatable)

สิ่งที่มักทำให้ Unit รันซ้ำไม่ได้ คือเวลาปัจจุบันและค่าสุ่ม เช่น ฟังก์ชันที่คำนวณจำนวนวันจาก “วันนี้” จะได้ผลต่างกันทุกวัน วิธีแก้คือส่งวันที่เข้าไปเป็นพารามิเตอร์ หรือใช้ตัวจำลองนาฬิกาที่เครื่องมือทดสอบมีให้ ในแอปสาธิต ฟังก์ชันรับจำนวนวันล่วงหน้า daysAhead เป็นตัวเลขโดยตรง ผลจึงไม่ขึ้นกับวันที่รัน

บทเรียนจากผลนี้

ถ้าทดสอบแค่ค่าตัวแทนกลางช่วง เช่น 15 วัน ทุกอย่างจะผ่าน และข้อบกพร่องนี้จะหลุดไปถึงผู้ใช้ ค่าขอบ 3 จากครั้งที่ 2 คือสิ่งที่จับได้ และ Unit คือระดับที่ทดสอบค่าขอบทั้งชุดได้ถูกและเร็วที่สุด

2.6 การวัดความครอบคลุม

เครื่องมือ Unit ส่วนใหญ่วัด ความครอบคลุมของโค้ด (code coverage) ได้ เช่น jest --coverage บอกว่ากี่เปอร์เซ็นต์ของบรรทัดหรือเงื่อนไขถูกรันระหว่างทดสอบ ตัวเลขนี้บอกได้ว่าส่วนใดยังไม่ถูกทดสอบเลย แต่บอกไม่ได้ว่าส่วนที่ถูกรันแล้วทำงานถูก เพราะการรันผ่านบรรทัดหนึ่งไม่ได้แปลว่ามี Assert ที่ตรวจผลของบรรทัดนั้น

2. ฟังก์ชันคำนวณ “อีกกี่วันถึงวันจัดงาน” จากวันที่ปัจจุบัน ทำให้ Unit test รันซ้ำไม่ได้เพราะอะไร และแก้อย่างไร

ผลเปลี่ยนตามวันที่รัน แก้โดยส่งวันที่ปัจจุบันเป็นพารามิเตอร์ หรือใช้ตัวจำลองนาฬิกาให้ทุกครั้งเป็นวันเดียวกัน

3. ความครอบคลุม 100% แปลว่าไม่มีข้อบกพร่องใช่หรือไม่

ไม่ใช่ บอกได้แค่ว่าทุกบรรทัดถูกรัน ไม่ได้บอกว่ามี Assert ที่ถูกต้องตรวจผล และไม่ได้บอกว่าทดสอบค่าขอบครบ

บทที่ 3 กลุ่มที่ 2 สี่ระดับการทดสอบ

Integration Testing

เวลาอ่านประมาณ 20 นาทีสไลด์ 20–29ข้อสอบ 3.1

บทนี้ตอบคำถาม รอยต่อระหว่างส่วนประกอบทดสอบอย่างไร และใช้ตัวจำลองเมื่อไร

อ่านจบแล้วได้ หลักการ Integration และตัวจำลอง

3.1 Integration testing คืออะไร

Integration testing คือการทดสอบรอยต่อระหว่างส่วนประกอบ ไม่ได้ทดสอบตรรกะภายในซ้ำกับ Unit แต่ตรวจว่าเมื่อส่วนประกอบเรียกใช้กันหรือส่งข้อมูลให้กัน ทุกอย่างไปถึงครบและถูกต้อง ISTQB แบ่งเป็นสองแบบ

Component integration ภายในระบบ

ส่วนประกอบของเราต่อกันเอง เช่น บริการ Express กับชั้นข้อมูล เส้นทาง HTTP กับบริการตัดสินใจ

System integration กับระบบภายนอก

ระบบของเราต่อกับระบบอื่น เช่น บริการอีเมล ระบบยืนยันตัวตนของมหาวิทยาลัย ระบบชำระเงิน

3.2 ฐานการทดสอบ และสิ่งที่ต้องตรวจที่รอยต่อ

ฐานการทดสอบคือเอกสารออกแบบสถาปัตยกรรม (HLD) โดยเฉพาะส่วนต่อประสาน (interface) และสัญญา API ซึ่งบอกว่าส่วนประกอบหนึ่งส่งอะไร ในรูปแบบใด และอีกฝั่งต้องตอบอะไร ใน Case X คือส่วนต่อประสาน I-01 ถึง I-08 ที่ทบทวนในครั้งที่ 1 ที่รอยต่อหนึ่งจุด ให้ตรวจหกเรื่องนี้

ตรวจตัวอย่างคำถาม
ข้อมูลส่งครบช่องที่หน้าจอส่งมา ถึงบริการครบทุกช่องหรือไม่
รูปแบบตรงกันชื่อช่อง ชนิดข้อมูล รูปแบบวันที่ ตรงกันทั้งสองฝั่งหรือไม่
รหัสตอบกลับถูกสำเร็จได้ 201 ข้อมูลผิดได้ 400 ไม่ได้เข้าสู่ระบบได้ 401 ไม่มีสิทธิ์ได้ 403
สิทธิ์ถูกตรวจที่ฝั่งที่รับผิดชอบถ้าเรียกตรงโดยไม่ผ่านหน้าจอ บริการยังตรวจสิทธิ์หรือไม่
บันทึกจริงหลังเรียกแล้ว ข้อมูลถูกเขียนลงไฟล์หรือฐานข้อมูลจริงหรือไม่ และไม่บันทึกเมื่อถูกปฏิเสธ
จัดการข้อผิดพลาดถ้าอีกฝั่งไม่ตอบหรือตอบผิด ระบบของเราทำอย่างไร

3.3 กลยุทธ์การรวม

กลยุทธ์ทำอย่างไรข้อดีข้อเสีย
รวมทีเดียว Big-bangรอทุกส่วนเสร็จ แล้วต่อพร้อมกันทั้งหมดไม่ต้องเตรียมตัวจำลองเริ่มทดสอบได้ช้า เมื่อไม่ผ่านหาต้นเหตุยากมาก
บนลงล่าง Top-downเริ่มจากชั้นบน เช่น เส้นทาง HTTP ชั้นล่างที่ยังไม่เสร็จใช้ stub แทนเห็นการทำงานภาพรวมเร็วต้องเขียน stub หลายตัว
ล่างขึ้นบน Bottom-upเริ่มจากชั้นล่าง เช่น ชั้นข้อมูล ใช้ driver เรียกแทนชั้นบนที่ยังไม่มีชั้นพื้นฐานถูกทดสอบละเอียดเห็นภาพรวมช้า

Driver คือโค้ดที่เรียกส่วนที่ทดสอบแทนผู้เรียกจริง ส่วน stub คือโค้ดที่ถูกเรียกแทนส่วนที่ยังไม่มี ในแอปสาธิต Supertest ทำหน้าที่เป็น driver ที่ส่งคำขอ HTTP แทนหน้าจอ

3.4 สภาพแวดล้อมของ Integration

สภาพแวดล้อมการทดสอบระดับ Integration
ที่ไหนเครื่อง CI หรือสภาพแวดล้อมทดสอบรวม (TEST) · แอปสาธิตรันบนเครื่องผู้พัฒนาได้ เพราะ Supertest เรียกแอป Express ได้โดยไม่ต้องเปิดเซิร์ฟเวอร์เอง
อะไรเป็นของจริงส่วนประกอบของเราที่ต่อกันจริง: เส้นทาง HTTP บริการ และชั้นข้อมูล
อะไรใช้ตัวจำลองระบบภายนอกที่เราควบคุมไม่ได้ เช่น บริการอีเมล ใช้ตัวจำลองหรือ sandbox
ข้อมูลไฟล์ข้อมูลทดสอบที่แยกจากข้อมูลจริง ชุดทดสอบของแอปสาธิตสร้างโฟลเดอร์ข้อมูลชั่วคราวใหม่ทุกครั้งที่รัน แล้วรีเซ็ตจาก tests/fixtures ก่อนทุกกรณี
บัญชีบัญชีทดสอบสามบทบาท u-org-01 (ผู้จัด) u-room-01 (เจ้าของห้อง) u-equip-01 (เจ้าของอุปกรณ์) ชื่อขึ้นต้นด้วย test_ เห็นชัดว่าไม่ใช่คนจริง · แอปสาธิตระบุผู้ใช้ด้วย header x-user แทนการเข้าสู่ระบบจริง เพื่อความง่ายของการสาธิต
เครื่องมือSupertest · Postman · REST Assured · Pact (ทดสอบสัญญา API)
สั่งรันในแอปสาธิตnpm run test:api ในโฟลเดอร์ backend

ทำไมต้องรีเซ็ตข้อมูลก่อนทุกกรณี การทดสอบ Integration เขียนลงไฟล์จริง ถ้าข้อหนึ่งสร้างคำขอไว้ ข้อถัดไปจะเห็นคำขอนั้นด้วย ผลจึงขึ้นกับลำดับการรัน การรีเซ็ตทำให้ทุกข้อเริ่มจากสถานะเดียวกันที่รู้ค่าแน่นอน รายละเอียดอยู่ในบทที่ 6.2

3.5 ตัวจำลอง (Test double)

เมื่อสิ่งที่ส่วนประกอบของเราต้องเรียกใช้ยังไม่พร้อม ช้าเกินไป มีค่าใช้จ่าย หรือควบคุมผลไม่ได้ เราใช้ตัวจำลองแทน คำว่า test double ยืมมาจาก “นักแสดงแทน” ในภาพยนตร์

แบบทำอะไรใช้เมื่อตัวอย่าง
Stubตอบค่าที่กำหนดไว้ตายตัวต้องการให้สิ่งที่ถูกเรียกตอบแบบเดิมทุกครั้งบริการตรวจวันหยุดตอบว่า “ไม่ใช่วันหยุด” เสมอ
Mockตอบได้ และจดว่าถูกเรียกกี่ครั้ง ด้วยค่าอะไรต้องการตรวจว่าระบบของเราสั่งถูกต้องตรวจว่าสั่งส่งอีเมลถึงผู้จัด 1 ครั้ง
Fakeทำงานได้จริงแบบย่อต้องการพฤติกรรมใกล้จริงแต่เร็วฐานข้อมูลในหน่วยความจำ
Sandboxระบบภายนอกรุ่นทดสอบที่ผู้ให้บริการเปิดไว้ต้องการเห็นการเชื่อมต่อจริงโดยไม่กระทบข้อมูลจริงบัญชีทดสอบของผู้ให้บริการอีเมลหรือชำระเงิน

3.7 ข้อผิดพลาดที่พบบ่อย

ข้อผิดพลาดทำไมเป็นปัญหา
จำลองทุกอย่าง รวมถึงส่วนประกอบของเราเองไม่มีรอยต่อจริงเหลือให้ทดสอบ กลายเป็น Unit ที่ซับซ้อน
ตรวจแค่รหัสตอบกลับได้ 201 แต่ข้อมูลอาจไม่ได้ถูกบันทึก ต้องอ่านสิ่งที่ถูกบันทึกด้วย
ใช้ข้อมูลร่วมกันโดยไม่รีเซ็ตผลขึ้นกับลำดับ บางครั้งผ่าน บางครั้งไม่ผ่าน
ทดสอบกับระบบภายนอกตัวจริงทุกครั้งช้า มีค่าใช้จ่าย และอาจส่งอีเมลหรือตัดเงินจริง
สรุปบทที่ 3
  • Integration ทดสอบรอยต่อ: ข้อมูลครบ รูปแบบตรง รหัสตอบกลับ สิทธิ์ บันทึกจริง การจัดการข้อผิดพลาด
  • ฐานการทดสอบคือ HLD และสัญญา API · รวมทีละส่วนหาต้นเหตุง่ายกว่ารวมทีเดียว
  • สภาพแวดล้อม: ส่วนประกอบของเราตัวจริง ข้อมูลทดสอบแยกและรีเซ็ตทุกกรณี ระบบภายนอกใช้ตัวจำลองหรือ sandbox
  • Stub ตอบค่าตายตัว · Mock ตรวจว่าถูกเรียกอย่างไร · Fake ทำงานจริงแบบย่อ · Sandbox ระบบภายนอกรุ่นทดสอบ
  • ผลจริงของ v0.9: TC-18 ได้ 200 แทน 403 · ตัวจำลองยืนยันได้แค่ว่าระบบของเราสั่งถูก

ทดสอบความเข้าใจท้ายบท

1. ต้องการตรวจว่าเมื่อคำขอถูกปฏิเสธ ระบบต้องไม่สั่งส่งอีเมล ควรใช้ตัวจำลองแบบใด

Mock เพราะต้องตรวจว่าถูกเรียกหรือไม่ เหมือน TC-22N ที่ตรวจว่า notify ไม่ถูกเรียก

2. API ตอบ 201 แล้ว ทำไมยังต้องอ่านไฟล์ข้อมูลอีก

รหัสตอบกลับบอกว่าบริการตอบว่าสำเร็จ แต่ไม่ได้ยืนยันว่าข้อมูลถูกเขียนลงชั้นข้อมูลจริงและถูกต้อง ซึ่งคือรอยต่อที่ต้องทดสอบ

3. ทีมเลือกส่งอีเมลจริงทุกครั้งที่รันชุดทดสอบ Integration มีปัญหาอะไร

ช้า อาจมีค่าใช้จ่าย ผลขึ้นกับเครือข่าย และอาจส่งอีเมลถึงคนจริง ควรใช้ตัวจำลองในชุดที่รันบ่อย แล้วทดสอบการส่งจริงด้วย sandbox ที่ระดับระบบ

4.1 System testing คืออะไร

System testing คือการทดสอบระบบที่ประกอบครบแล้วทั้งระบบ เทียบกับความต้องการที่เขียนไว้ ทดสอบทั้งหน้าที่ (functional) ว่าระบบทำสิ่งที่ต้องทำ และคุณภาพ (non-functional) เช่น ความเร็ว ความปลอดภัย การใช้งานง่าย มักทดสอบแบบต้นจนจบ (end-to-end) คือเริ่มจากสิ่งที่ผู้ใช้ทำบนหน้าจอ ไปจนถึงผลที่ผู้ใช้เห็น

ฐานการทดสอบ

SRS ความต้องการเชิงหน้าที่ (FR) กฎทางธุรกิจ (BR) Use Case เกณฑ์การยอมรับ (AC) และ NFR

วิธีคิด

แบบกล่องดำ ไม่ดูโค้ด ทำตามขั้นตอนของผู้ใช้ แล้วตรวจสิ่งที่มองเห็นได้ เทียบกับความต้องการ

ผู้ทดสอบ

ทีมทดสอบ ซึ่งควรเป็นอิสระจากผู้เขียนโค้ด เพราะผู้เขียนมักทดสอบตามที่ตนคิดว่าระบบทำ

ข้อบกพร่องที่พบได้ดี

หน้าจอแสดงผลผิด ขั้นตอนต้นจนจบขาดตอน ส่วนประกอบทำงานได้ทีละตัวแต่รวมแล้วไม่ครบ NFR ไม่ผ่าน

4.5 Non-functional testing ที่ระดับระบบ

ความต้องการที่ไม่ใช่หน้าที่ (NFR) บอกว่าระบบต้องทำงานดีแค่ไหน ส่วนใหญ่ทดสอบได้เมื่อระบบประกอบครบแล้ว จึงอยู่ที่ระดับ System เงื่อนไขสำคัญคือ เกณฑ์ต้องวัดได้ และต้องบอกสภาพแวดล้อมที่วัด เพราะผลของ NFR ขึ้นกับสภาพแวดล้อมมากกว่าการทดสอบแบบอื่น

ด้านเกณฑ์ที่วัดไม่ได้เกณฑ์ที่วัดได้สภาพแวดล้อมที่ต้องระบุ
ประสิทธิภาพระบบต้องเร็วมีคำขอ 200 รายการ GET /api/requests ตอบภายใน 500 มิลลิวินาที สมมติสเปกเครื่อง ปริมาณข้อมูล จำนวนผู้ใช้พร้อมกัน เครือข่าย
ความปลอดภัยระบบต้องปลอดภัยผู้ที่ไม่ใช่เจ้าของส่งคำสั่งตัดสินรายการ ต้องได้ 403 ทุกครั้ง และมีบันทึกเหตุการณ์การตั้งค่าสิทธิ์และบัญชีเหมือนระบบจริง
การใช้งานง่ายใช้งานง่ายผู้ใช้ใหม่ส่งคำขอสำเร็จภายใน 3 นาทีโดยไม่ต้องถาม สมมติผู้ใช้จริงบนอุปกรณ์ของตน มักวัดคู่กับ UAT
ความเข้ากันได้ใช้ได้ทุกเครื่องทำงานครบบน Chrome Edge Safari รุ่นล่าสุด และหน้าจอกว้าง 360 พิกเซล สมมติรายชื่อเบราว์เซอร์ รุ่น และอุปกรณ์ที่ทดสอบ

5.1 UAT คืออะไร

User Acceptance Testing (UAT) คือการทดสอบที่ผู้ใช้จริงหรือตัวแทนผู้ใช้ นำระบบไปทำงานจริงของตน แล้วเป็นผู้ตัดสินว่าระบบใช้ได้หรือไม่ UAT เป็นการ validation คือถามว่าเราสร้างระบบที่ถูกต้องสำหรับผู้ใช้หรือไม่ ซึ่งต่างจากสามระดับก่อนหน้าที่ถามว่าระบบตรงตามเอกสารหรือไม่

วัตถุประสงค์

สร้างความมั่นใจว่าระบบช่วยให้ผู้ใช้ทำงานของตนสำเร็จ และพร้อมนำไปใช้ ไม่ได้มุ่งหาข้อบกพร่องให้มากที่สุด

ฐานการทดสอบ

กระบวนการทำงานของผู้ใช้ ความต้องการของผู้ใช้ และเกณฑ์การยอมรับที่ตกลงกันก่อนเริ่มพัฒนา

ผู้ทดสอบและผู้ตัดสิน

ผู้ใช้จริงหรือตัวแทน ทีมพัฒนาและทีมทดสอบช่วยเตรียมและจดบันทึก แต่ไม่ได้เป็นผู้ตัดสิน

ปัญหาที่พบได้ดี

ขั้นตอนไม่ตรงงานจริง คำบนหน้าจอไม่เข้าใจ ข้อมูลที่ต้องใช้ไม่ครบ ระบบถูกตามเอกสาร แต่เอกสารเข้าใจงานผิด

5.4 การเตรียม UAT

  1. ตกลงเกณฑ์การยอมรับ กับผู้ใช้ตั้งแต่ต้น เช่น “จองห้องและอุปกรณ์ได้ครบเองโดยไม่ต้องโทรถามเจ้าหน้าที่”
  2. เลือกผู้ทดสอบ ที่ทำงานนั้นจริง ครอบคลุมทุกบทบาทที่สำคัญ เช่น ผู้จัด 2 คน เจ้าของห้อง 1 คน
  3. เขียนสถานการณ์ เป็นงานของผู้ใช้ ไม่ใช่ลำดับการกดปุ่ม เช่น “จองห้องและโปรเจกเตอร์สำหรับสัมมนาสัปดาห์หน้า”
  4. ตรวจเกณฑ์ก่อนเริ่ม System ผ่านตามเกณฑ์ ไม่มีข้อบกพร่องรุนแรงสูงค้าง สภาพแวดล้อม UAT พร้อม มีคู่มือหรือคำอธิบายสั้น
  5. ระหว่างทดสอบ ให้ผู้ใช้ทำเอง ผู้จดบันทึกจดสิ่งที่ผู้ใช้ทำและพูด ไม่ช่วยกดแทน ไม่ชี้ทาง ถ้าผู้ใช้ถาม ให้จดว่าถามอะไร
  6. สรุปผลและตัดสิน เทียบกับเกณฑ์ ผู้ใช้เป็นผู้บอกว่ายอมรับหรือไม่ ปัญหาที่พบส่งเป็นรายงานข้อบกพร่อง

5.5 สภาพแวดล้อมของ UAT

สภาพแวดล้อมการทดสอบระดับ UAT
ที่ไหนสภาพแวดล้อม UAT ที่ติดตั้งรุ่นที่จะส่งมอบ แยกจากระบบจริง ผู้ใช้เข้าถึงได้จากอุปกรณ์และเครือข่ายที่ใช้ทำงานจริง
อะไรเป็นของจริงระบบทั้งหมด ผู้ใช้จริง งานจริง อุปกรณ์ของผู้ใช้
อะไรใช้ตัวจำลองไม่ควรมี ระบบภายนอกควรเป็นของจริงหรือ sandbox ที่ผู้ใช้เห็นผลได้ เช่น อีเมลถึงกล่องจดหมายที่เปิดดูได้
ข้อมูลเหมือนจริงตามงาน เช่น ชื่อห้องและอุปกรณ์จริงของคณะ แต่ไม่ใช่ข้อมูลส่วนบุคคลจริง หรือปกปิดแล้ว
ความนิ่งห้ามติดตั้งรุ่นใหม่ระหว่างรอบ UAT ถ้าต้องแก้ ให้จบรอบ แก้ แล้วนัดรอบใหม่
สิ่งสนับสนุนคู่มือหรือคำอธิบายสั้น ช่องทางแจ้งปัญหา ผู้จดบันทึก แบบบันทึกผล
ในแอปสาธิตยังไม่มีสภาพแวดล้อม UAT และยังไม่มีผู้ใช้จริงมาทดสอบ สถานะจึงเป็น Not Executed
ข้อมูลส่วนบุคคลในการทดสอบ

การคัดลอกข้อมูลจริงของผู้ใช้มาใช้ทดสอบ ทำให้คนที่ไม่เกี่ยวข้องเห็นข้อมูลส่วนบุคคล และเสี่ยงขัดกับพระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 ให้สร้างข้อมูลขึ้นเองหรือปกปิดก่อนใช้ ดูบทที่ 6.2

5.6 ตัวอย่าง: สถานการณ์ UAT ของผู้จัดกิจกรรม

ช่องเนื้อหา
ชื่อสถานการณ์จองห้องและโปรเจกเตอร์สำหรับสัมมนาสัปดาห์หน้า
ผู้ทดสอบผู้จัดกิจกรรมจริง 1 คน
ขั้นตอน (ลำดับงาน)1 สร้างคำขอของงานจริง · 2 เพิ่มห้องและอุปกรณ์ที่ต้องใช้ · 3 ส่งคำขอ แล้วติดตามผล · 4 เมื่อทุกรายการอนุมัติ ตรวจว่าพร้อมจัดงาน
ผ่านเมื่อจองได้ครบเองโดยไม่ต้องโทรถามเจ้าหน้าที่ และรู้สถานะของงานตลอด
สภาพแวดล้อมสภาพแวดล้อม UAT รุ่นที่จะส่งมอบ · อุปกรณ์ของผู้จัดเอง · ข้อมูลห้องและอุปกรณ์เหมือนจริง
ผลNot Executed ยังไม่มีผู้ใช้จริงมาทดสอบ
แผนทดสอบกับผู้จัดกิจกรรม 2 คน บนสภาพแวดล้อม UAT หลังแก้ข้อบกพร่องรุนแรงสูงแล้ว

สังเกตว่าขั้นตอนเขียนเป็นงานที่ผู้จัดต้องทำ ไม่ได้เขียนว่า “กดปุ่มสร้างคำขอ กรอกช่องที่ 1” เพราะ UAT ต้องการรู้ว่าผู้ใช้หาทางทำงานเองได้หรือไม่ และการบันทึก Not Executed พร้อมแผน ดีกว่าการเติมผลที่ไม่ได้ทดสอบจริง

5.7 ตัวอย่างการบันทึกผล UAT สมมติ

ตารางนี้สมมติขึ้นเพื่อแสดงรูปแบบ ว่าเมื่อมีผู้ใช้มาทดสอบแล้ว ผลควรบันทึกอย่างไร ไม่ใช่ผลของแอปสาธิต

ขั้นผู้ใช้ทำได้เองไหมสิ่งที่ผู้จดบันทึกสังเกต
1 สร้างคำขอของงานจริงได้—
2 เพิ่มห้องและอุปกรณ์ได้ หลังถาม 1 ครั้งหาไม่เจอว่าเพิ่มโปรเจกเตอร์ตรงไหน ถามว่า “อุปกรณ์อยู่เมนูไหน” (ปุ่มชื่อ “เพิ่มทรัพยากร”)
3 ส่งคำขอ แล้วติดตามผลได้พูดว่า “รออนุมัติหลายรายการ แปลว่าต้องทำอะไรต่อ”
4 ตรวจว่าพร้อมจัดงานได้—
สรุปผล (สมมติ) ทำครบทุกขั้น แต่ต้องถาม 1 ครั้ง จึงยังไม่ผ่านเกณฑ์ “ไม่ต้องโทรถามเจ้าหน้าที่” ปัญหาขั้นที่ 2 รายงานเป็นข้อบกพร่องด้านการใช้งาน ข้อสังเกตขั้นที่ 3 ส่งให้ทีมพิจารณาปรับข้อความสถานะ แก้แล้วนัดผู้ใช้ทดสอบซ้ำ

ผลของ UAT เป็นข้อมูลสำคัญของการตัดสินการส่งมอบในครั้งที่ 4 ถ้า UAT ยังไม่ได้ทำ ต้องบอกในรายงานว่ายังไม่ได้ทำ และเป็นความเสี่ยงที่ยังเหลืออยู่

5.8 ข้อผิดพลาดที่พบบ่อย

ข้อผิดพลาดทำไมเป็นปัญหา
ทีมพัฒนาทดสอบเองแล้วเรียกว่า UATผู้ทดสอบไม่ใช่ผู้ใช้ จึงเป็น System ไม่ใช่ UAT
ขั้นตอนเป็นลำดับการกดปุ่มไม่ได้ทดสอบว่าผู้ใช้หาทางทำงานเองได้
เกณฑ์ผ่านว่า “ระบบทำงานถูกต้อง”วัดไม่ได้ และไม่ได้วัดจากมุมของงานผู้ใช้
ช่วยผู้ใช้กดหรือบอกทางปัญหาด้านการใช้งานถูกซ่อนไว้ ผลดีเกินจริง
เริ่ม UAT ทั้งที่ System ยังมีข้อบกพร่องรุนแรงค้างผู้ใช้เจอปัญหาที่รู้อยู่แล้ว เสียเวลาและความเชื่อมั่น
สรุปบทที่ 5
  • UAT คือ validation ผู้ใช้จริงทำงานจริง และเป็นผู้ตัดสิน
  • การยอมรับมีหลายแบบ: UAT · OAT · ตามสัญญาหรือระเบียบ · Alpha · Beta
  • System กับ UAT ต่างกันที่ผู้ทดสอบ ผู้ตัดสิน และคำถาม ไม่ใช่ขอบเขต
  • สภาพแวดล้อม UAT ใกล้จริงที่สุด นิ่งตลอดรอบ ข้อมูลเหมือนจริงแต่ไม่ใช่ข้อมูลส่วนบุคคลจริง
  • ยังไม่มีผู้ใช้มาทดสอบ บันทึก Not Executed พร้อมแผน

ทดสอบความเข้าใจท้ายบท

1. ทีมทดสอบทำตามสถานการณ์ของผู้จัดครบทุกขั้นบน STAGING แล้วผ่าน เรียกว่า UAT ได้หรือไม่

ไม่ได้ ผู้ทดสอบคือทีม ไม่ใช่ผู้ใช้จริง จึงเป็น System test ที่ใช้สถานการณ์ของผู้ใช้

2. เขียนเกณฑ์ผ่านของ UAT สำหรับเจ้าของห้องที่ต้องพิจารณาคำขอ

ตัวอย่าง: เจ้าของห้องพิจารณาคำขอที่ค้างทั้งหมดได้เองโดยไม่ต้องติดต่อผู้จัด และผู้จัดเข้าใจเหตุผลเมื่อถูกปฏิเสธ เกณฑ์วัดจากการทำงานสำเร็จ

3. ระหว่าง UAT ทีมพบข้อบกพร่องเล็กน้อย แล้วติดตั้งรุ่นแก้ทันทีระหว่างที่ผู้ใช้ยังทดสอบอยู่ มีปัญหาอะไร

ผลของผู้ใช้แต่ละคนมาจากคนละรุ่น เทียบกันไม่ได้ และรุ่นแก้ยังไม่ผ่าน System ควรจบรอบ แก้ ทดสอบ แล้วนัดรอบใหม่

6.5 ปัญหาที่เกิดจากสภาพแวดล้อม

สภาพแวดล้อมทำให้ผลเพี้ยนได้ทั้งสองทาง คือผ่านทั้งที่มีข้อบกพร่อง และไม่ผ่านทั้งที่โค้ดถูก ก่อนรายงานข้อบกพร่องทุกครั้ง ให้ถามว่า “ถ้ารันซ้ำในสภาพแวดล้อมที่สะอาด จะได้ผลเดิมไหม”

อาการต้นเหตุจากสภาพแวดล้อมป้องกันอย่างไร
“ผ่านในเครื่องฉัน” แต่พังที่อื่นรุ่น runtime รุ่นไลบรารี หรือการตั้งค่าต่างกันบันทึกรุ่นและการตั้งค่า · รันใน CI ที่สะอาด
ผ่านหลอก ผ่านในการทดสอบ พังเมื่อใช้จริงข้อมูลน้อยเกินไป ใช้ตัวจำลองแทนของจริง สภาพแวดล้อมต่างจากระบบจริงยืนยันอีกครั้งที่ STAGING และ UAT
ไม่ผ่านหลอก ไม่ผ่านทั้งที่โค้ดถูกข้อมูลค้างจากกรณีก่อน เครือข่ายช้า บริการภายนอกล่มรีเซ็ตข้อมูลทุกกรณี · แยกข้อมูลของแต่ละคน
ผลไม่แน่นอน (flaky) รันซ้ำได้ผลไม่เหมือนเดิมการทดสอบพึ่งลำดับ เวลา หรือการรอด้วยเวลาตายตัวทำให้ทุกข้ออิสระ · รอจนสิ่งที่ต้องการปรากฏ
รันไม่ได้ระบบภายนอกหรือสภาพแวดล้อมยังไม่พร้อมบันทึก Blocked พร้อมเหตุผล · ทดสอบส่วนที่ทำได้ด้วยตัวจำลองที่ระดับต่ำกว่า

1. จับคู่สถานการณ์กับระดับ: (ก) ตรวจว่าฟังก์ชันคำนวณจำนวนชิ้นรวมถูกต้อง (ข) เรียก API ลบรายการด้วยบัญชีที่ไม่ใช่เจ้าของ ต้องได้ 403 (ค) ทีมทดสอบส่งคำขอผ่านหน้าจอแล้วตรวจสถานะที่แสดง (ง) ผู้จัดกิจกรรม 2 คนจองห้องสำหรับงานของตนเอง แล้วบอกว่าจะใช้ระบบนี้แทนการโทรจองหรือไม่

(ก) Unit · (ข) Integration · API · (ค) System · (ง) UAT · (ค) กับ (ง) ต่างกันที่ผู้ทดสอบและผู้ตัดสิน

2. บอกสภาพแวดล้อมของ (ข) ในข้อ 1 ให้ครบ: ที่ไหน ของจริง ตัวจำลอง ข้อมูล

รันบนเครื่องผู้พัฒนาหรือ CI · บริการและชั้นข้อมูลเป็นของจริง · ระบบภายนอกที่ไม่เกี่ยวใช้ตัวจำลอง · ไฟล์หรือฐานข้อมูลทดสอบที่รีเซ็ตก่อนทุกกรณี และบัญชีทดสอบทั้งเจ้าของและไม่ใช่เจ้าของ

3. ระบบต้องส่ง SMS ยืนยัน แต่ยังไม่มีบัญชีผู้ให้บริการ SMS ทีมควรทดสอบอย่างไร และบันทึกผลอย่างไร

ระดับ API ใช้ mock ตรวจว่าระบบสั่งส่ง SMS ถูกจังหวะและถูกเนื้อหา บันทึกผลตามจริง ส่วนระดับระบบที่ต้องเห็น SMS จริงบันทึก Blocked พร้อมเหตุผล จนกว่าจะมีบัญชี sandbox

4. “ระบบต้องรองรับการใช้งานพร้อมกัน” เขียนใหม่ให้เป็นเกณฑ์ที่วัดได้ และบอกสภาพแวดล้อมที่ต้องวัด

ตัวอย่าง: ผู้ใช้ 50 คนส่งคำขอพร้อมกัน ทุกคำขอตอบภายใน 2 วินาทีและไม่มีข้อผิดพลาด (สมมติ) วัดบน STAGING ที่ติดตั้งแบบเดียวกับระบบจริง มีข้อมูลใกล้เคียงจริง และบันทึกสเปกเครื่อง

5. ทีมหนึ่งทดสอบทุกอย่างบนระบบจริงที่ผู้ใช้ใช้อยู่ ด้วยบัญชีของผู้ใช้จริง ระบุความเสี่ยงอย่างน้อยสามข้อ

ข้อมูลจริงเสียหายหรือปนข้อมูลทดสอบ · ผู้ใช้จริงได้รับอีเมลหรือการแจ้งเตือนจากการทดสอบ · ข้อมูลส่วนบุคคลถูกเห็นโดยผู้ไม่เกี่ยวข้อง · รีเซ็ตข้อมูลไม่ได้ ผลจึงรันซ้ำไม่ได้

6. ทำไมผลการทดสอบทุกข้อจึงต้องบอกรุ่นและสภาพแวดล้อม

เพราะผลเป็นข้อเท็จจริงของรุ่นหนึ่งในสภาพแวดล้อมหนึ่ง เมื่อแก้โค้ดหรือเปลี่ยนสภาพแวดล้อม ผลอาจเปลี่ยน ถ้าไม่บันทึกจะไม่รู้ว่าต้องทดสอบซ้ำอะไร และตรวจสอบย้อนไม่ได้
