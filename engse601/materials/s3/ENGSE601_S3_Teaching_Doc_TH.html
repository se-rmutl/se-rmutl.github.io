1.4 ไม่ต้องรันทุกข้อทุกระดับ

ไฟล์ TEST_CASES.md ในแอปสาธิตบอกว่าแต่ละข้อรันที่ระดับไหน บางข้อรันระดับเดียว บางข้อรันสองสามระดับ ช่องว่างไม่ได้แปลว่าลืม แต่เลือกแล้วว่าไม่จำเป็น เหตุผลอยู่ในบทที่ 2

เลือกระดับการทดสอบ

เวลาอ่านประมาณ 11 นาทีสไลด์ 15–19ข้อสอบ 3.1

บทนี้ตอบคำถาม ใช้ตำแหน่งของกฎจากครั้งที่ 1 ตัดสินว่ารันที่ระดับไหน

ผลงานของบทนี้ ระดับของทุกกรณีทดสอบ

2.1 ผังสี่คำถาม

  1. อยู่ในฟังก์ชันเดียวไหม ถ้าใช่ ทดสอบที่ Unit เร็วที่สุด ทดสอบได้ทุกค่า
  2. เกิดระหว่างส่วนประกอบไหม เช่น บริการบันทึกลงไฟล์ หรือเรียกผ่าน HTTP ถ้าใช่ ทดสอบที่ API หรือ Integration
  3. ต้องเห็นผลทั้งระบบไหม เช่น ผู้ใช้เห็นสถานะบนหน้าจอ ถ้าใช่ ทดสอบที่ System
  4. ผู้ใช้จริงเป็นผู้ตัดสินไหม เช่น ใช้ทำงานจริงได้หรือไม่ ถ้าใช่ คือ UAT

คำถามที่ 1 และ 2 ตอบได้จากคำถาม “ใครรับผิดชอบ” ของครั้งที่ 1 นี่คือเหตุผลที่ครั้งที่ 1 ต้องหาตำแหน่งของกฎให้ได้ก่อน

2.3 เลือกระดับต่ำสุดที่จับได้ก่อน

ถ้าข้อบกพร่องจับได้ที่ Unit ให้ทดสอบที่ Unit เพราะรันเร็ว ชี้ต้นเหตุได้ชัด แล้วค่อยยืนยันเฉพาะเส้นทางสำคัญที่ระดับบน ถ้าทดสอบทุกอย่างผ่านหน้าจอ การทดสอบจะช้า เปราะ และเมื่อไม่ผ่านจะหาต้นเหตุยาก

3.2 ในแอปสาธิต

การเตรียมข้อมูลของ Unit และ API
// tests/helpers/testData.js
process.env.DATA_DIR = fs.mkdtempSync(path.join(os.tmpdir(), 'casex-test-'));
const store = require('../../src/repository/jsonStore');
function resetData() { store.resetFrom(FIXTURES); }   // คัดลอก fixtures
// ในไฟล์ทดสอบ
beforeEach(() => resetData());
สิ่งที่เตรียมในแอปสาธิตเหตุผล
ข้อมูลตั้งต้นtests/fixtures/*.jsonทุกกรณีเริ่มจากข้อมูลเดียวกัน
โฟลเดอร์ข้อมูลของการทดสอบโฟลเดอร์ชั่วคราวไม่แตะข้อมูลจริงใน backend/data
บัญชีทดสอบu-org-01 · u-room-01 · u-equip-01ครบทุกบทบาท ไม่ใช่ข้อมูลคนจริง
สำหรับ SystemPOST /api/_test/resetเปิดเฉพาะเมื่อ NODE_ENV=test เท่านั้น
ห้ามเปิดจุดรีเซ็ตในระบบจริง

จุดรีเซ็ตข้อมูลที่ใช้ตอนทดสอบ ถ้าเปิดในระบบจริง ใครก็ล้างข้อมูลได้ แอปสาธิตจึงเปิดเฉพาะโหมดทดสอบ โครงงานของทีมต้องทำแบบเดียวกัน

  • Assert เทียบกับผลที่คาดหวัง

8.1 สถานะสี่แบบ

สถานะความหมายต้องมีหลักฐานอะไร
Passรันแล้ว ผลตรงกับที่คาดหวังผลเทอร์มินัล หรือภาพหน้าจอ
Failรันแล้ว ผลไม่ตรง แปลว่าพบข้อบกพร่องผลเทอร์มินัลที่มี Expected กับ Received หรือภาพหน้าจอ
Blockedรันไม่ได้ เพราะติดสิ่งภายนอกเหตุผลที่ติด
Not Executedยังไม่ได้รันเหตุผล และสิ่งที่เตรียมไว้แล้ว เช่น โค้ดที่เขียนแล้ว

Fail ไม่ใช่เรื่องแย่ของผู้ทดสอบ การทดสอบที่ดีคือการทดสอบที่พบข้อบกพร่อง ชุดทดสอบที่ผ่านทุกข้อในรุ่นแรก ควรทำให้สงสัยว่ากรณีทดสอบครอบคลุมพอหรือยัง

8.3 ขยายตารางสอบกลับ

ตารางของครั้งที่ 2 มีแค่ความต้องการกับกรณีทดสอบ วันนี้เพิ่มสองคอลัมน์ คือระดับที่รันและสถานะ ตารางเต็มอยู่ในภาคผนวก และเป็นเนื้อหาของบทที่ 4.3

หลักฐานเท็จ

เติม Pass ให้ข้อที่ไม่ได้รัน ใช้ AI สร้างผลการรัน หรือเปลี่ยน Fail เป็น Pass โดยไม่ได้แก้และรันใหม่ คือหลักฐานเท็จ ส่วน B ของใบงานได้ 0 ทั้งส่วน

สรุปบทที่ 8
  • สถานะสี่แบบ: Pass · Fail · Blocked · Not Executed ทุกสถานะต้องมีหลักฐานหรือเหตุผล
  • Fail คือการพบข้อบกพร่อง ไม่ใช่ความล้มเหลวของผู้ทดสอบ
  • ขยายตารางสอบกลับด้วยระดับและสถานะ แล้วส่งต่อครั้งที่ 4

ท้ายเอกสาร

ทดสอบความเข้าใจตัวเอง

1. ฟังก์ชันคำนวณสถานะรวม ควรทดสอบที่ระดับใด

Unit ตรรกะอยู่ในฟังก์ชันเดียว

2. “เรียก API ตรงด้วยบัญชีที่ไม่ใช่เจ้าของต้องได้ 403” ทดสอบที่ระดับใด

API · Integration ต้องเรียกผ่าน HTTP โดยไม่ผ่านหน้าจอ

3. Expected: true · Received: false หมายความว่าอะไร

ผลที่คาดหวังจากกฎคือ true แต่โค้ดคืน false แปลว่าพบข้อบกพร่อง

4. SYS-03 ผ่าน แสดงว่ากฎ BR-X-02 ถูกต้องใช่หรือไม่

ไม่ใช่ SYS-03 ตรวจแค่ว่าหน้าจอซ่อนปุ่ม TC-18 ระดับ API พบว่าชั้นบริการไม่ตรวจสิทธิ์

5. TC-22M ผ่านด้วยตัวจำลอง บันทึก TC-22 เป็นอะไร

Blocked บันทึกแยกกัน ความเสี่ยงที่เหลือคือการส่งอีเมลจริง

6. “ระบบต้องตอบเร็ว” เป็นเกณฑ์ NFR ที่ดีไหม

ไม่ดี วัดไม่ได้ ต้องระบุตัวเลขและเงื่อนไข เช่น ตอบภายใน 500 มิลลิวินาที เมื่อมี 200 รายการ และกำกับว่าสมมติถ้ายังไม่อนุมัติ
