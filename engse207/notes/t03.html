บทนำครั้งนี้อยู่ตรงไหนของภาค

ครั้งที่ 2 ทีมรัน Task Board v1 ตามคำขอจากหน้าจอถึงฐานข้อมูล และแก้กฎชื่องานจนพบว่ากฎเดียวต้องแก้สองที่ ครั้งนี้เราใช้ระบบตัวเดิม ถามคำถามที่ลึกกว่า “ทำงานถูกไหม” คือ “ทำงานดีแค่ไหน และเมื่อมีบางอย่างผิดปกติ ระบบเป็นอย่างไร”

คำตอบของคำถามนี้คือ คุณลักษณะคุณภาพ (quality attributes) ซึ่งเป็นตัวผลักที่สำคัญที่สุดในการเลือกสถาปัตยกรรม ครั้งนี้ทีมจะ ทำให้ระบบเจอเหตุการณ์จริง เช่น ฐานข้อมูลหยุด งานหนักงานหนึ่งแย่ง CPU หรือมีบั๊กที่ซ่อนอยู่ แล้ว วัด ผลที่เกิดขึ้น ตัวเลขที่วัดได้จะกลายเป็น quality scenario ใน ARCH-01 และเป็นเหตุผลของการเปลี่ยนรุ่นในครั้งที่ 4 และครั้งที่ 10

  2. ส่งสถานะ "flying" แล้วได้ 500 เพราะอะไรแนวคำตอบไม่มีใครตรวจค่า ฐานข้อมูลปฏิเสธด้วย CHECK constraint แล้ว catch ตอบ 500 ทั้งที่ควรเป็น 400
  3. C4 Container กับ Docker container ต่างกันอย่างไรแนวคำตอบC4 Container บอกหน้าที่ในแบบสถาปัตยกรรม Docker container บอกวิธีรัน สองอย่างไม่จำเป็นต้องจับคู่หนึ่งต่อหนึ่ง

  2. อธิบาย modifiability, availability/reliability, performance และ scalability พร้อมวิธีวัดในระบบ Task Board

  4. อธิบาย image, container, port mapping, volume และ network ของ Docker จากระบบที่รันอยู่ และทำนายผลของ down กับ down -v ได้
  5. ไล่หาจุดเสียทีละชั้น จากแท็บ Network ไป log ไปฐานข้อมูล บันทึกหลักฐาน แล้วยืนยันว่าแก้ได้จริง
  6. เขียน ARCH-01 รุ่นแรกของทีม ที่มีบริบท ขอบเขต ข้อสมมติ และ quality scenario 2 เรื่องจากผลทดลองของตัวเอง

ส่วนที่ 1Functional requirement กับคุณลักษณะคุณภาพ

คำถามเปิด (ตอบในใจก่อน แล้วคลิกดูแนวคำตอบ)
  1. ระบบ Task Board สองระบบ ทำได้ทุกฟีเจอร์เหมือนกันทุกปุ่ม แต่ระบบหนึ่งล่มทุกครั้งที่มีคนเปิดหน้ารายงาน อีกระบบไม่ล่ม สองระบบนี้ต่างกันที่อะไรแนวคำตอบต่างกันที่ คุณภาพ ไม่ใช่ฟังก์ชัน ทั้งสองระบบผ่าน functional requirement เหมือนกัน แต่มี availability ต่างกัน ความต่างนี้มักมาจากโครงสร้าง เช่น รายงานรันใน process เดียวกับทุกอย่างหรือแยกออกไป จึงเป็นเรื่องของสถาปัตยกรรม

1.1 สองชนิดของความต้องการ

Functional requirementQuality attribute (non-functional)
ตอบคำถามระบบต้อง ทำอะไรระบบต้องทำ ได้ดีแค่ไหน ภายใต้สถานการณ์อะไร
ตัวอย่าง Task Boardสร้างงาน มอบหมาย เปลี่ยนสถานะ ดูสรุปงานบันทึกงานแล้วต้องไม่หาย · หน้าบอร์ดเปิดภายใน 1 วินาที · เปลี่ยนกฎได้ในครึ่งวัน
ตรวจอย่างไรทดสอบว่ากดแล้วได้ผลถูกทดลองในสถานการณ์ที่กำหนด แล้ว วัดตัวเลข
ผลต่อโครงสร้างทำได้ด้วยโครงสร้างหลายแบบบางคุณภาพทำได้เฉพาะบางโครงสร้าง จึงเป็นตัวผลักให้เลือกสถาปัตยกรรม

ในครั้งที่ 1 เราเรียกสิ่งที่ผลักให้เลือกสถาปัตยกรรมว่า architectural drivers ซึ่งมีทั้ง functional requirement ที่สำคัญ ข้อจำกัด และ quality attribute ในทางปฏิบัติ quality attribute มีน้ำหนักมากที่สุด เพราะฟังก์ชันทำให้ครบได้แทบทุกโครงสร้าง แต่คุณภาพบางเรื่องต้องออกแบบโครงสร้างมาตั้งแต่ต้น

1.2 คุณภาพ 4 เรื่องที่ใช้ในวิชานี้

มาตรฐาน ISO/IEC 25010 จัดกลุ่มคุณภาพของซอฟต์แวร์ไว้หลายหมวด เช่น ความเหมาะสมของฟังก์ชัน ประสิทธิภาพ ความเข้ากันได้ ความน่าเชื่อถือ ความปลอดภัย และความง่ายต่อการดูแลรักษา วิชานี้เลือกใช้ 4 เรื่องที่เห็นผลชัดกับ Task Board ตลอดภาค

คุณภาพความหมายวัดด้วยอะไรใน v1 ขึ้นกับอะไร
Modifiability
แก้ไขได้ง่าย		เปลี่ยนระบบตามความต้องการใหม่ได้เร็ว ต้นทุนต่ำ และไม่ทำส่วนอื่นพังจำนวนไฟล์หรือจุดที่ต้องแก้ เวลาที่ใช้ จำนวนบั๊กที่ตามมากฎกระจายใน route · SQL ปนกับ HTTP
Availability / Reliability
พร้อมใช้ · เชื่อถือได้		ระบบใช้งานได้เมื่อผู้ใช้ต้องการ ทำงานถูกต้องต่อเนื่อง และฟื้นตัวเมื่อมีปัญหาสัดส่วนเวลาที่ใช้ได้ เวลาที่ใช้ฟื้นตัว ข้อมูลที่หาย ข้อความที่ผู้ใช้เห็นprocess เดียว · ฐานข้อมูลตัวเดียว · restart ทั้งก้อน
Performance
ประสิทธิภาพ		ตอบสนองเร็วพอภายใต้ภาระที่กำหนดเวลาตอบ (latency) จำนวนคำขอต่อวินาที (throughput)คำสั่ง SQL · งานที่ใช้ CPU ใน process เดียวกัน
Scalability
ขยายได้		รับภาระที่เพิ่มขึ้นได้ โดยเพิ่มทรัพยากรแล้วคุณภาพยังอยู่ในเกณฑ์เวลาตอบเมื่อผู้ใช้เพิ่ม · ทรัพยากรที่ต้องเพิ่มต่อผู้ใช้ที่เพิ่มขยายได้ทั้งก้อนเท่านั้น · พอร์ตตายตัว
คุณภาพแลกกันเสมอ

การได้คุณภาพข้อหนึ่งมักต้องจ่ายด้วยอีกข้อ เช่น แยกรายงานเป็นบริการต่างหากช่วย performance และ availability แต่ทำให้ระบบซับซ้อนขึ้น ทดสอบยากขึ้น และมีจุดที่ล้มได้มากขึ้น (modifiability บางด้านลดลง) สถาปนิกจึงต้องรู้ว่าระบบนี้ ให้น้ำหนักกับคุณภาพข้อไหน ซึ่งได้มาจากผู้ใช้และโจทย์ ไม่ใช่จากความชอบของทีม

ส่วนที่ 2Quality scenario: เขียนความต้องการคุณภาพให้วัดได้

ประโยคอย่าง “ระบบต้องเร็ว” หรือ “ระบบต้องเสถียร” ใช้ตัดสินใจอะไรไม่ได้ เพราะไม่รู้ว่าเร็วแค่ไหน ในสถานการณ์อะไร และวัดอย่างไร quality scenario คือวิธีเขียนความต้องการคุณภาพให้เป็นสถานการณ์ที่ทดลองและวัดผลได้ แบ่งเป็น 6 ส่วน

2.1 จากประโยคกว้าง ๆ เป็น scenario ที่วัดได้

ประโยคกว้างเขียนเป็น scenario
ระบบต้องแก้ไขง่ายเมื่อ ลูกค้า ขอ เปลี่ยนกฎความยาวชื่องาน ขณะ พัฒนาตามปกติ นักพัฒนาหนึ่งคนแก้ กฎของงาน ได้โดย แก้ที่เดียว ผ่านการทดสอบเดิมทั้งหมด ภายใน 30 นาที
ระบบต้องเสถียรเมื่อ ฐานข้อมูลหยุด ระหว่าง ใช้งานปกติ หน้าเว็บ แสดงข้อความที่เข้าใจได้ภายใน 3 วินาที ไม่ค้าง และเมื่อฐานข้อมูลกลับมา ระบบ ใช้ได้อีกภายใน 10 วินาทีโดยไม่ต้องรีสตาร์ตแอป ไม่มีงานหาย
ระบบต้องเร็วเมื่อ หัวหน้าทีม เปิด หน้าสรุปงาน ขณะ สมาชิกคนอื่นกำลังสร้างงาน การสร้างงานของสมาชิก ตอบภายใน 500 มิลลิวินาที ที่วัดจากแท็บ Network ของเบราว์เซอร์

2.3 แยกให้ออก: ข้อมูลวัดได้ ข้อสมมติ และข้อมูลจากโจทย์

ตัวเลขใน scenario มีที่มาสามแบบ ต้องเขียนกำกับให้ชัด เพราะความน่าเชื่อถือต่างกันมาก

ที่มาตัวอย่างเขียนกำกับว่า
วัดได้จากการทดลองสร้างงานรอ 2.8 วินาทีขณะรายงานคำนวณหนัก (วัด 3 ครั้งบน iMac ห้อง C3-405)“วัดได้” พร้อมวิธีวัด จำนวนครั้ง และเครื่องที่ใช้
ข้อสมมติทีมลูกค้ามีไม่เกิน 10 คน ใช้พร้อมกันไม่เกิน 5 คน“ข้อสมมติ” และบอกว่าถ้าผิดจะกระทบอะไร
ข้อมูลจากโจทย์ลูกค้าบอกว่างานที่บันทึกแล้วต้องไม่หาย“จากโจทย์” และอ้างที่มา เช่น brief ของ Task Board
เกณฑ์ของ scenario ที่ดี
  1. เฉพาะระบบนี้ พูดถึง Task Board ของทีม ไม่ใช่ระบบทั่วไป
  2. ครบ 6 ส่วน โดยเฉพาะสภาพแวดล้อมและตัววัด
  3. ทดลองได้ในห้อง ด้วยเครื่องมือที่มี คือ Docker, DevTools, log และฐานข้อมูล
  4. บอกที่มาของตัวเลข ว่าวัดได้ สมมติ หรือมาจากโจทย์
  5. เชื่อมกับการตัดสินใจ บอกได้ว่าถ้าไม่ผ่าน ทีมต้องพิจารณาเปลี่ยนโครงสร้างตรงไหน

ในครั้งที่ 2 เราใช้ Docker แค่ 4 คำสั่ง ครั้งนี้จะดูว่าเบื้องหลังคำสั่งเหล่านั้นมีอะไร เพราะคุณภาพหลายเรื่องของระบบขึ้นกับการตั้งค่าเหล่านี้โดยตรง เช่น ข้อมูลหายหรือไม่หลัง restart ขึ้นกับ volume และแอปหาฐานข้อมูลเจอหรือไม่ขึ้นกับ network

3.1 Image และการ build

app/Dockerfileสูตรสร้าง image ของแอป

FROM node:24-alpine                       # เริ่มจาก image ที่มี Node.js 24 บน Linux ขนาดเล็ก
WORKDIR /app                              # ทำงานในโฟลเดอร์ /app ของ container
COPY package.json package-lock.json ./    # คัดลอกรายการ dependency ก่อน
RUN npm ci --no-audit --no-fund           # ติดตั้ง express, pg, nodemon ตาม lockfile
COPY . .                                  # คัดลอกโค้ดที่เหลือ
EXPOSE 3000                               # บอกว่าแอปฟังพอร์ต 3000 (เป็นเอกสาร ไม่ได้เปิดพอร์ตเอง)
CMD ["npm", "run", "dev"]                 # คำสั่งที่รันเมื่อ container เริ่ม

image สร้างเป็น ชั้น (layer) ทีละบรรทัด ถ้าบรรทัดไหนและก่อนหน้าไม่เปลี่ยน Docker ใช้ชั้นเดิมที่เก็บไว้ (cache) นี่คือเหตุผลที่คัดลอก package.json ก่อนโค้ด เมื่อแก้ server.js แล้ว build ใหม่ ขั้น npm ci ที่ช้าที่สุดจะไม่ต้องทำซ้ำ ส่วน postgres:16-alpine เป็น image สำเร็จรูปที่ดาวน์โหลดมาใช้เลย ไม่ต้อง build

3.2 Container: ใช้แล้วทิ้งได้

คำสั่งcontainerข้อมูลในฐานข้อมูลใช้เมื่อ
docker compose stopหยุด ยังอยู่อยู่หยุดชั่วคราว
docker compose startเริ่มตัวเดิมอยู่ต่อจาก stop
docker compose restart appหยุดแล้วเริ่มตัวเดิมอยู่จำลองการ deploy ใหม่
docker compose downลบ container และเครือข่ายอยู่ (อยู่ใน volume)เลิกใช้งานวันนี้
docker compose down -vลบ container เครือข่าย และ volumeหาย กลับเป็นข้อมูลตั้งต้นเมื่อ upอยากเริ่มข้อมูลใหม่

หลักคิดสำคัญคือ container ไม่ใช่ที่เก็บข้อมูลถาวร ทุกอย่างที่เขียนลงในตัว container จะหายเมื่อ container ถูกลบ ข้อมูลที่ต้องอยู่รอดจึงต้องเก็บใน volume หรือบริการภายนอก หลักนี้สำคัญมากเมื่อขึ้น Cloud ในครั้งที่ 8 เพราะผู้ให้บริการลบและสร้าง container ใหม่ได้ตลอดเวลา

3.3 Port mapping: ประตูจากเครื่องเราเข้า container

"3000:3000" อ่านว่า พอร์ตของเครื่องเรา : พอร์ตใน container แอปใน container ฟังพอร์ต 3000 เสมอ ส่วนเราเปิดผ่านพอร์ตของเครื่องเราที่จับคู่ไว้ ถ้าพอร์ต 3000 ของเครื่องมีโปรแกรมอื่นใช้อยู่ ให้เปลี่ยนแค่ฝั่งซ้ายผ่าน .env เช่น APP_PORT=3001 แล้วเปิด http://localhost:3001 แอปข้างในไม่ต้องแก้อะไร

ฐานข้อมูลจับคู่ "5433:5432" ตั้งใจให้ฝั่งเครื่องเราเป็น 5433 เพื่อไม่ชนกับ PostgreSQL ที่บางคนติดตั้งไว้แล้ว แต่ในเครือข่ายของ Compose แอปยังต่อที่ db:5432 ส่วนคำสั่ง docker compose exec db psql … เข้าไปรันในตัว container จึงไม่ต้องใช้พอร์ตของเครื่องเราเลย

3.4 Volume: ทำไมข้อมูลยังอยู่หลัง restart

bind mount ./app:/appnamed volume pgdata
ข้อมูลอยู่ที่โฟลเดอร์ในเครื่องเราที่เปิดเห็นได้พื้นที่ที่ Docker จัดการเอง
ใช้ทำอะไรให้แก้โค้ดในเครื่องแล้ว container เห็นทันทีเก็บไฟล์ของฐานข้อมูลให้อยู่รอดเมื่อ container ถูกลบ
หายเมื่อลบไฟล์ในเครื่องเองdocker compose down -v
ไฟล์ใน db/init รันครั้งเดียว

PostgreSQL รัน 01-schema.sql และ 02-seed.sql เฉพาะตอนที่ volume ยังว่าง ผลที่ตามมามีสองข้อ ข้อแรก แก้ไฟล์ seed แล้วจะไม่เห็นผลจนกว่าจะ down -v ข้อสอง เปลี่ยน POSTGRES_PASSWORD ใน .env หลังจากฐานข้อมูลถูกสร้างแล้ว รหัสผ่านในฐานข้อมูลจะยังเป็นค่าเดิม แอปที่ใช้รหัสใหม่จะต่อไม่ได้ นี่คือหนึ่งในข้อขัดข้องที่จะลองในห้อง

3.5 Network: ทำไมใช้ชื่อ db ไม่ใช่ localhost

Compose สร้างเครือข่ายให้ทุก service ในไฟล์ และตั้ง ชื่อเครื่องตามชื่อ service แอปจึงหาฐานข้อมูลเจอด้วยชื่อ db ส่วน localhost ในแต่ละ container หมายถึง ตัว container นั้นเอง ถ้าแอปต่อ localhost:5432 จะไม่เจอ PostgreSQL เพราะ PostgreSQL อยู่อีก container ลองดูได้ด้วยคำสั่งนี้

docker compose exec app node -e "require('dns').lookup('db', (e, ip) => console.log('db =', ip))"
# db = 172.18.0.2   (ตัวเลขแต่ละเครื่องต่างกัน)

3.6 Environment และไฟล์ .env

ค่าที่ต่างกันในแต่ละที่ติดตั้ง เช่น รหัสผ่าน พอร์ต หรือชื่อเครื่องฐานข้อมูล ไม่ควรเขียนตายในโค้ด แต่ส่งเข้ามาทาง environment variable ในไฟล์ Compose เขียนแบบ ${POSTGRES_PASSWORD:-taskboard_dev} แปลว่าใช้ค่าจากไฟล์ .env ถ้ามี ถ้าไม่มีใช้ค่าหลัง :- แล้ว server.js อ่านผ่าน process.env.DB_PASSWORD แยกค่าตั้งออกจากโค้ดแบบนี้ทำให้ใช้โค้ดชุดเดียวกันบน iMac, Notebook และ Cloud ได้ และ ห้าม commit ไฟล์ .env เพราะมีรหัสผ่านจริง ให้ commit .env.example ที่บอกว่าต้องมีค่าอะไรแทน

4.2 สัญญาณที่หลอกตา

  • 200 ไม่ได้แปลว่าถูก ถ้ารูปร่าง JSON ที่ตอบกลับไม่ตรงกับที่หน้าจอคาด เช่น ชื่อ field เปลี่ยน หน้าจอจะแสดงผิดโดยไม่มี error สักบรรทัด ต้องเปิดแท็บ Response ดูของจริงเทียบกับที่โค้ดหน้าจออ่าน
  • log บอกว่าเร็ว แต่ผู้ใช้รอนาน log ของ v1 จับเวลาตั้งแต่ route เริ่มทำงาน ถ้าคำขอต้องรอคิวเพราะ process ไม่ว่าง เวลาที่รอจะไม่อยู่ใน log ต้องวัดจากฝั่งผู้ใช้ด้วยแท็บ Network (ดูส่วนที่ 5)
  • แก้แล้วไม่เห็นผล ตรวจว่าบันทึกไฟล์แล้ว แอปรีสตาร์ตแล้ว (ดู log) เบราว์เซอร์ไม่ได้ใช้ไฟล์เก่า (กด Cmd + Shift + R) และไม่ได้แก้ไฟล์ที่ต้องรอ down -v เช่น seed
  • error แรกไม่ใช่ต้นเหตุเสมอ เมื่อฐานข้อมูลหยุด ทุก route จะ error พร้อมกัน ให้ดูว่าอะไรเปลี่ยนก่อน ไม่ใช่แก้ทีละ route
