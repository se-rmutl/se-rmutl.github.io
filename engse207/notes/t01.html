บทนำครั้งนี้อยู่ตรงไหนของภาค

ภาคนี้มี 15 ครั้งสอน แบ่งเป็น 4 ช่วง และสอบรายบุคคล 2 ครั้ง ทุกช่วงใช้ระบบเดียวกันคือ Task Board ระบบจัดการงานของทีมเล็ก ครั้งที่ 1 เป็นจุดเริ่มของช่วงแรก เราจะรู้จักรายวิชา รู้ว่าสถาปัตยกรรมซอฟต์แวร์หมายถึงอะไร และลองอ่านระบบ Task Board จากโค้ดจริงหนึ่งเส้นทาง ยังไม่ต้องรันระบบและยังไม่ต้องวาดแบบเต็มชุด

หลังอ่านแล้วคุณจะทำได้

  1. บอกได้ว่ารายวิชานี้วัดผลอะไร ส่งอะไร เมื่อไร และใช้กติกาอะไรตลอดภาค
  2. อธิบายว่าสถาปัตยกรรมซอฟต์แวร์คืออะไร ด้วยองค์ประกอบ 4 อย่าง คือ ส่วนประกอบ ความสัมพันธ์ คุณสมบัติ และเหตุผล
  3. แยกข้อความว่าเป็น requirement, architecture หรือ design และบอกได้ว่า requirement ด้านคุณภาพผลักให้ต้องคิดสถาปัตยกรรมอย่างไร
  4. บอกงานของสถาปนิกในแต่ละช่วงของวงจรพัฒนาซอฟต์แวร์ (SDLC)
  5. ตามคำขอ “สร้างงาน” ของ Task Board จากหน้าจอ ผ่าน API ถึงฐานข้อมูล แล้วกลับมาที่หน้าจอ และอธิบายได้ว่ากฎของงานควรอยู่ที่ไหน

1.1 วิชานี้เรียนอะไร

คำอธิบายรายวิชาตามหลักสูตรกำหนดให้ศึกษาและฝึกปฏิบัติพื้นฐานของสถาปัตยกรรมซอฟต์แวร์ใน 5 เรื่องใหญ่ เราจะเรียนแต่ละเรื่องผ่านระบบตัวอย่างเดียวกัน ไม่แยกเป็นทฤษฎีล้วน

เรื่องในคำอธิบายรายวิชาในวิชานี้หมายถึงเรียนในครั้งที่
หลักการและแนวทางออกแบบแบ่งหน้าที่ขององค์ประกอบ ลดการผูกกัน ให้ระบบเปลี่ยนได้โดยไม่ต้องรื้อทั้งหมดT02, T04
รูปแบบและกรอบแนวคิดLayered, Modular Monolith, การแยกบริการ, Event-Driven และกรอบ C4T04, T05, T10, T11
เอกสารและเหตุผลของการออกแบบแผนภาพที่ตรงกับระบบจริง และบันทึกการตัดสินใจ (ADR) ว่าทำไมเลือกแบบนี้T05, T06
กระบวนการออกแบบและประเมินเทียบทางเลือก แล้วตรวจด้วยสถานการณ์คุณภาพและการทดลองขนาดเล็กT03, T06, T13, T14
Cloud และอุปกรณ์เคลื่อนที่นำระบบขึ้น Cloud ดูแลการตั้งค่าและข้อมูล และออกแบบให้ผู้ใช้บนมือถือที่เครือข่ายช้าหรือขาดหายใช้ได้T08, T09, T12

ระดับเป้าหมายคือ ระบบขนาดเล็กที่มีโครงช่วย คุณจะอ่าน ปรับ วัด และอธิบายระบบที่มีอยู่ ไม่ได้สร้างระบบใหญ่จากศูนย์ ความยากอยู่ที่การให้เหตุผลว่าทำไมโครงสร้างนี้เหมาะหรือไม่เหมาะ ไม่ได้อยู่ที่ปริมาณโค้ด

1.2 ผลลัพธ์การเรียนรู้ 7 ข้อ (CLO)

CLOเรียนจบแล้วทำได้วัดจาก
CLO1วิเคราะห์บริบท ความต้องการ และข้อจำกัด เพื่อระบุประเด็นสำคัญทางสถาปัตยกรรมA3, A5
CLO2เสนอและเปรียบเทียบทางเลือกสถาปัตยกรรม พร้อมเหตุผลเรื่องข้อแลกเปลี่ยนและความเสี่ยงA2, A3, A4, A5
CLO3จัดทำและสื่อสารแผนภาพและเอกสารที่ตรงกับระบบ ใช้ไทยและอังกฤษในส่วนสำคัญA1, A3, A4, A5, A8
CLO4ปรับองค์ประกอบของระบบตามแบบ และนำขึ้นใช้งานบน local และ CloudA1, A4, A6
CLO5ประเมินสถาปัตยกรรมด้วยสถานการณ์คุณภาพและการทดลองขนาดเล็ก รวมถึงผู้ใช้บนมือถือA2, A4, A7
CLO6ทำงานทีมอย่างรับผิดชอบ จัดการงานและรุ่น ให้และรับข้อเสนอแนะA8, A9
CLO7สืบค้นและตรวจสอบข้อมูลจากเอกสารเทคนิคและเครื่องมือช่วย รวมถึง AI และอ้างอิงแหล่งที่มาA9

ครั้งที่ 1 เกี่ยวกับ CLO1 (เริ่มมองระบบเป็นโครงสร้างและประเด็น) และ CLO6 (ตั้งทีม แบ่งบทบาท และพื้นที่ทำงานร่วมกัน)

1.3 หนึ่งระบบตลอดภาค

ทุกสัปดาห์ใช้ Task Board ระบบเดียวกัน แกนของระบบมี 3 ชิ้น คือหน้าจอ React, API ด้วย Node.js และฐานข้อมูล PostgreSQL รันบนเครื่องด้วย Docker Compose ตั้งแต่ครั้งที่ 2 จากนั้นแต่ละครั้งจะทดลองเพิ่มทีละเรื่อง เช่น นำขึ้น Cloud ใน T08 ลองเก็บข้อมูลบางส่วนด้วย MongoDB ใน T09 แยกหนึ่งบริการออกมาใน T10 ส่งเหตุการณ์แบบไม่พร้อมกันใน T11 และออกแบบสำหรับผู้ใช้บนมือถือใน T12 ทุกการทดลองจบด้วยคำถามเดียวกันว่า จะเก็บไว้หรือไม่ เพราะอะไร

ทำไมไม่เริ่มระบบใหม่ทุกสัปดาห์

ในงานจริง สถาปนิกแทบไม่เคยได้เริ่มจากศูนย์ งานส่วนใหญ่คือทำความเข้าใจระบบที่มีอยู่แล้วตัดสินใจว่าจะเปลี่ยนอะไร การใช้ระบบเดียวทำให้เห็นผลของการตัดสินใจครั้งก่อนในครั้งถัดไป เช่น ถ้าใน T04 แบ่งโมดูลไม่ดี T10 จะแยกบริการยาก

  1. ลงมือทุกครั้ง แล้วค่อยลดตัวช่วย ทุกคนผลัดกันลงมือในระบบเดียวกัน ตัวช่วยจะลดลงก่อนถึงจุดตรวจรายคน
  2. หลักฐานก่อนความเห็น ตอบด้วย log, diff, ผลทดลอง หรือแผนภาพที่ตรงกับระบบ และไม่สรุปเกินกว่าที่วัดได้
  3. ใช้ AI ได้ แต่ต้องตรวจและอ้างอิง บอกว่าใช้ตรงไหน ตรวจกับระบบหรือผลทดลองแล้ว ยอมรับหรือปฏิเสธเพราะอะไร ห้ามใช้ในเวลาสอบ
  4. งานเดี่ยวเป็นของตัวเอง งานเดี่ยวอยู่ในโฟลเดอร์ individual/ ของ repo ทีม commit ด้วยบัญชีของตัวเอง และอธิบายได้เมื่อถูกถาม

ห้าม commit รหัสผ่าน token หรือไฟล์ .env ลง repo ถ้าส่งงานไม่ทันให้แจ้งในกลุ่ม LINE ของ SEC ก่อนครบกำหนด

ลองแยก R · A · D (คลิกแต่ละข้อเพื่อดูเฉลย)
  1. สมาชิกเปลี่ยนสถานะงานเป็น “เสร็จ” ได้เฉลยR สิ่งที่ระบบต้องทำ (ความต้องการเชิงหน้าที่)
  2. เก็บข้อมูลงานใน PostgreSQL ไม่เก็บไว้ใน browserเฉลยA เลือกที่เก็บข้อมูลของทั้งระบบ เปลี่ยนทีหลังแล้วแพง
  3. ชื่องานยาวไม่เกิน 120 ตัวอักษร ตรวจในฟังก์ชัน createTaskเฉลยD รายละเอียดข้างในชิ้นเดียว (ตัวกฎ “ไม่เกิน 120 ตัวอักษร” เป็น requirement แต่การบอกว่าตรวจในฟังก์ชันไหนเป็น design)
  4. ถ้า API ล่ม งานที่บันทึกแล้วต้องไม่หายเฉลยR ความต้องการด้านคุณภาพ (reliability) และเป็นตัวผลักให้แยกที่เก็บข้อมูลออกจาก API
  5. หน้าจอเรียก API ผ่าน HTTP และรับ JSONเฉลยA วิธีเชื่อมระหว่างชิ้นใหญ่
  6. ปุ่ม “สร้างงาน” อยู่มุมขวาบนของรายการเฉลยD รายละเอียดหน้าจอ เปลี่ยนได้ในไม่กี่นาที
  7. ระบบต้องใช้งานได้บนมือถือที่เครือข่ายขาดหายเป็นช่วง ๆเฉลยR ความต้องการด้านคุณภาพ ซึ่งจะผลักให้คิดเรื่องการเก็บข้อมูลชั่วคราวบนเครื่องและการส่งซ้ำ (เรียนใน T12)
  8. ส่งอีเมลแจ้งเตือนผ่านคิวเหตุการณ์ แทนการเรียกบริการอีเมลทันทีเฉลยA เลือกวิธีสื่อสารแบบไม่พร้อมกัน (async) ระหว่างชิ้น (เรียนใน T11)

3.2 สามชิ้นหลักและวิธีคุยกัน

คำถามสองข้อที่ต้องตอบได้จากภาพนี้

3.3 ตามคำขอ “สร้างงาน” หนึ่งเส้น

3.4 ถ้ากดสร้างโดยไม่ใส่ชื่องาน

ในโค้ดตัวอย่าง คำขอที่ไม่มีชื่องานจะเดินทางถึง service แล้วหยุดที่นั่น service โยน ValidationError route จับแล้วตอบ 400 พร้อม {"error":"กรุณาใส่ชื่องาน"} ฝั่ง tasks.js เห็นว่า res.ok เป็นเท็จจึงโยน Error ต่อ และ TaskForm แสดงข้อความใต้ฟอร์ม ไม่มีข้อมูลใดถูกบันทึก

คำถามสำคัญคือ ทำไม API ต้องตรวจซ้ำ ทั้งที่หน้าจอก็ตรวจได้ คำตอบคือ API ไม่รู้ว่าคำขอมาจากหน้าจอของเราจริงหรือไม่ ใครก็ส่งคำขอตรงมาที่ API ได้ด้วยเครื่องมืออย่าง curl หรือ Postman และในอนาคตอาจมีแอปมือถือหรือระบบอื่นเรียก API เดียวกัน จุดที่ข้อมูลข้ามจากส่วนที่เราควบคุมไม่ได้เข้ามาในส่วนที่เราควบคุม เรียกว่า ขอบเขตความเชื่อถือ (trust boundary) กฎที่ต้องเป็นจริงเสมอจึงต้องอยู่หลังเส้นนี้ เรื่องนี้จะกลับมาอีกครั้งใน T12 เมื่อมีแอปบนมือถือ

สังเกตด้วยว่า เมื่อเกิดข้อผิดพลาดภายใน เช่น ฐานข้อมูลหยุดทำงาน route ตอบ 500 พร้อมข้อความกลาง ๆ ว่า “เกิดข้อผิดพลาดในระบบ” ไม่ส่งรายละเอียดภายในให้ผู้ใช้ เพราะรายละเอียดนั้นไม่ช่วยผู้ใช้ และอาจบอกโครงสร้างภายในกับคนที่ไม่ควรรู้

export default function TaskItem({ task, onChanged }) {
  const [error, setError] = useState("");

  async function markDone() {
    setError("");
    try {
      const updated = await updateStatus(task.id, "done");
      onChanged(updated);           // แทนงานเดิมในรายการ
    } catch (err) {
      setError(err.message);
    }
  }

  return (
    <li>
      <span>{task.title}</span> <small>{task.status}</small>
      {task.status !== "done" && <button onClick={markDone}>เสร็จแล้ว</button>}
      {error && <p className="error">{error}</p>}
    </li>
  );
}

export async function updateStatus(id, status) {
  const res = await fetch(`/api/tasks/${id}/status`, {
    method: "PATCH",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ status }),
  });
  const body = await res.json();
  if (!res.ok) throw new Error(body.error);
  return body;
}

const STATUSES = ["todo", "doing", "done"];

async function changeStatus(id, status) {
  if (!STATUSES.includes(status)) {
    throw new ValidationError("สถานะไม่ถูกต้อง");
  }
  const task = await taskRepository.updateStatus(id, status);
  if (!task) {
    throw new NotFoundError("ไม่พบงานนี้");
  }
  return task;
}

ตอบก่อนเปิดเฉลย (คลิกแต่ละข้อ)
  1. P1 เรียงไฟล์และฟังก์ชันที่คำขอผ่าน ตั้งแต่กดปุ่มจนข้อมูลถูกบันทึกเฉลยTaskItem.jsx (markDone) → tasks.js (updateStatus) → tasks.routes.js (PATCH /tasks/:id/status) → task.service.js (changeStatus) → task.repository.js (updateStatus) → UPDATE tasks แล้วย้อนกลับทางเดิม
  2. P2 ถ้ากด “เสร็จแล้ว” ที่งาน id 42 คำขอมี method, URL และ body อย่างไร และ id อยู่ตรงไหนเฉลยPATCH /api/tasks/42/status body {"status":"done"} · id อยู่ใน URL ไม่ได้อยู่ใน body route อ่านด้วย req.params.id แล้วแปลงเป็นตัวเลข
  3. P3 ถ้าสำเร็จ API ตอบ status อะไร ต่างจากตอนสร้างงานอย่างไร เพราะอะไรเฉลย200 OK (ค่าเริ่มต้นของ res.json) พร้อม JSON ของงานที่อัปเดต ต่างจากการสร้างงานที่ตอบ 201 Created เพราะครั้งนี้แก้งานที่มีอยู่ ไม่ได้สร้างข้อมูลใหม่
  4. P4 มีคนส่งคำขอตรงมาที่ API ด้วย curl พร้อม {"status":"finished"} จะเกิดอะไรขึ้น ถึงฐานข้อมูลไหมเฉลยservice ตรวจแล้วพบว่า finished ไม่อยู่ใน STATUSES จึงโยน ValidationError route ตอบ 400 “สถานะไม่ถูกต้อง” คำขอไม่ถึงฐานข้อมูล นี่คือเหตุผลที่กฎอยู่ใน API ไม่ใช่แค่ในหน้าจอ (หน้าจอส่งได้แค่ "done" อยู่แล้ว แต่ curl ไม่ผ่านหน้าจอ)
  5. P5 ถ้าส่งคำขอไปที่งาน id 999 ซึ่งไม่มีอยู่ ผู้ใช้จะได้อะไรเฉลยUPDATE ไม่เจอแถว result.rows[0] เป็น undefined service จึงโยน NotFoundError route ตอบ 404 “ไม่พบงานนี้” แล้ว TaskItem แสดงข้อความนี้ใต้งาน
  6. P6 ต้องเพิ่มกฎ “งานที่เสร็จแล้วห้ามย้อนกลับเป็น todo” ควรแก้ที่ไหน การซ่อนปุ่มในหน้าจอพอไหมเฉลยแก้ที่ changeStatus ใน service เพราะเป็นที่รวมกฎของงาน และต้องรู้สถานะเดิมก่อน จึงต้องเพิ่มฟังก์ชันอ่านงานตาม id ใน repository ด้วย การซ่อนปุ่มในหน้าจอ (ซึ่งโค้ดทำอยู่แล้วสำหรับงานที่เสร็จ) เป็นแค่ตัวช่วยผู้ใช้ ไม่พอ เพราะคำขอส่งตรงมาที่ API ได้
  7. P7 เส้นทางนี้กับเส้นทาง “สร้างงาน” มีอะไรเหมือนกัน และบอกอะไรเกี่ยวกับสถาปัตยกรรมของ Task Boardเฉลยทั้งสองเส้นผ่านชั้นเดียวกัน 5 ชั้น คือ component → api client → route → service → repository และใช้วิธีจัดการ error แบบเดียวกัน (service โยน error ที่มีความหมาย route แปลงเป็น status code) รูปแบบที่ซ้ำกันทุกเส้นทางนี้คือโครงสร้างของระบบ เมื่อเห็นรูปแบบซ้ำ แปลว่าเริ่มเห็นสถาปัตยกรรมแล้ว

คำถามทบทวน (คลิกแต่ละข้อเพื่อดูแนวคำตอบ)
  1. อธิบายสถาปัตยกรรมซอฟต์แวร์ใน 1–2 ประโยค ให้ครบ 4 องค์ประกอบแนวคำตอบโครงสร้างหลักของระบบ คือระบบแบ่งเป็นส่วนประกอบอะไร แต่ละส่วนสัมพันธ์และสื่อสารกันอย่างไร ทั้งหมดนี้ทำให้ระบบมีคุณสมบัติอย่างไร และมีเหตุผลอะไรที่เลือกโครงสร้างนี้แทนทางเลือกอื่น
  2. ทำไม “ใช้ PostgreSQL เก็บข้อมูลงาน” เป็น architecture แต่ “ชื่อคอลัมน์ assignee_id” เป็น designแนวคำตอบการเลือกที่เก็บข้อมูลกระทบทั้งระบบ เปลี่ยนทีหลังต้องย้ายข้อมูล แก้ repository ทุกตัว และเปลี่ยนการติดตั้ง ส่วนชื่อคอลัมน์กระทบแค่คำสั่ง SQL ไม่กี่บรรทัดในชิ้นเดียว เปลี่ยนได้ถูกกว่ามาก

  4. ยกตัวอย่างข้อแลกเปลี่ยน (trade-off) 1 เรื่องแนวคำตอบแยกเป็นหลายบริการทำให้ขยายเฉพาะส่วนที่ทำงานหนักได้ แต่แลกกับความซับซ้อนในการติดตั้ง ทดสอบ และจุดที่ล้มได้มากขึ้น หรือเพิ่ม cache ให้ตอบเร็วขึ้น แต่แลกกับการที่ข้อมูลอาจไม่ล่าสุดชั่วขณะ
  5. ในช่วงทดสอบและช่วงใช้งานจริง สถาปนิกทำอะไรแนวคำตอบตรวจว่าโค้ดตรงกับแบบ วัดคุณภาพจริงเทียบกับ quality scenario เก็บหลักฐาน แล้วตัดสินใจว่าจะคงหรือปรับโครงสร้าง ถ้าความต้องการเปลี่ยนก็วนกลับไปหา drivers ใหม่
  6. ในคำขอ “สร้างงาน” ถ้าฐานข้อมูลหยุดทำงาน ผู้ใช้จะเห็นอะไร และทำไมไม่แสดงรายละเอียด errorแนวคำตอบdb.query เกิด error ซึ่งไม่ใช่ ValidationError route จึงตอบ 500 “เกิดข้อผิดพลาดในระบบ” และหน้าจอแสดงข้อความนี้ใต้ฟอร์ม ไม่ส่งรายละเอียดเพราะไม่ช่วยผู้ใช้ และอาจเปิดเผยโครงสร้างภายใน รายละเอียดควรอยู่ใน log ฝั่ง API
  7. ขอบเขตความเชื่อถือ (trust boundary) ของ Task Board อยู่ตรงไหน และมีผลกับการวางกฎอย่างไรแนวคำตอบอยู่ระหว่างหน้าจอ (ซึ่งรันใน browser ของผู้ใช้ ควบคุมไม่ได้) กับ API กฎที่ต้องเป็นจริงเสมอจึงต้องตรวจใน API การตรวจที่หน้าจอเป็นเพียงตัวช่วยให้ผู้ใช้รู้เร็ว
  8. ARCH ส่วนไหนคือระบบที่รันได้ และส่งเป็นรุ่นเมื่อไรแนวคำตอบARCH-04 ระบบที่รันได้ทั้ง local และ Cloud เริ่มตั้งแต่ T02 ส่งเป็นรุ่นด้วย git tag ที่ T07 และ T14 พร้อม ARCH ส่วนอื่น
  9. การบรรลุ CLO ดูจากอะไร ถ้าคะแนนทีมดีมากจะช่วยให้ CLO รายคนผ่านไหมแนวคำตอบดูจากงานเดี่ยว A1–A4 และ A9 ดัชนี 3 × ได้ ÷ เต็ม ต้องได้ 2.00 ขึ้นไปและหลักฐานสำคัญครบ คะแนนทีมไม่ถูกนำมาเติมให้ CLO รายคนผ่าน

ศัพท์สำคัญ

คำความหมายในวิชานี้
software architectureสถาปัตยกรรมซอฟต์แวร์ โครงสร้างหลักของระบบ (ส่วนประกอบ ความสัมพันธ์ คุณสมบัติ) และเหตุผลของการเลือก
architectural decisionการตัดสินใจระดับสถาปัตยกรรม เปลี่ยนทีหลังแล้วแพง ควรบันทึกเหตุผลไว้ใน ADR
requirementสิ่งที่ระบบต้องทำ (functional) และต้องดีแค่ไหน (quality)
quality attributeคุณลักษณะคุณภาพ เช่น modifiability, reliability, performance, scalability ต้องเขียนให้วัดได้
constraintข้อจำกัดที่เลือกไม่ได้ เช่น เวลา ขนาดทีม งบ เทคโนโลยีที่กำหนด
architectural driverสิ่งที่ผลักให้เลือกโครงสร้างแบบหนึ่ง ได้แก่ ความต้องการเชิงหน้าที่ คุณลักษณะคุณภาพ และข้อจำกัด
trade-offข้อแลกเปลี่ยน ได้คุณภาพข้อหนึ่งเพิ่มแต่เสียอีกข้อ
designการออกแบบข้างในแต่ละส่วนประกอบ เช่น ฟังก์ชัน คลาส โครงตาราง
SDLCวงจรพัฒนาซอฟต์แวร์ ตั้งแต่ความต้องการจนใช้งานจริงและวนกลับมาเปลี่ยน
request traceการตามคำขอ ไล่ดูว่าคำขอหนึ่งผ่านส่วนไหนบ้างจนถึงข้อมูลและกลับมา
sequence diagramแผนภาพลำดับ แสดงการเรียกและการตอบระหว่างส่วนประกอบตามเวลา
route · service · repositoryสามชั้นใน API ของ Task Board รับคำขอ HTTP · กฎของงาน · คุยกับฐานข้อมูล
validationการตรวจว่าข้อมูลถูกต้องตามกฎก่อนนำไปใช้
trust boundaryขอบเขตความเชื่อถือ จุดที่ข้อมูลเข้ามาจากส่วนที่เราควบคุมไม่ได้
C4 Containerหน่วยซอฟต์แวร์ที่รันแยกกันในแผนภาพ C4 ไม่ใช่สิ่งเดียวกับ Docker container
ADRArchitecture Decision Record บันทึกการตัดสินใจ บริบท ทางเลือก และผลที่ตามมา
repository · commit · collaboratorที่เก็บงานบน GitHub · การบันทึกการเปลี่ยนแปลงหนึ่งครั้ง · คนที่ได้รับสิทธิ์เข้าร่วม repo
