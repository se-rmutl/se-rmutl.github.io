ทำไมต้องมี W11

ถึงตอนนี้เรารู้ว่า ต้องทำอะไร (SRS) และ อะไรสำคัญ (W10) — แต่ถ้าส่งแค่นี้ให้ Dev เขาจะถามต่อทันที 4 ข้อ

1ระบบแบ่งเป็นกี่ชิ้นที่ต้อง “รัน”?
2แต่ละชิ้นทำอะไร ใช้เทคโนโลยีชนิดไหน?
3ชิ้นไหนคุยกับชิ้นไหน ส่งอะไรกัน?
4กติกาสำคัญ (D1–D3) อยู่ชิ้นไหน?
W11 ตอบ 4 ข้อนี้ด้วย “แผนที่ของระบบ” ที่ทุกคนในทีมเห็นตรงกัน — ถ้าไม่ตอบ Dev แต่ละคนจะเดาเอง และกติกาอาจไปอยู่ผิดที่ แบบในภาพนี้

มองระบบแบบ C4 — ซูมทีละระดับ

C4 คือวิธีวาดสถาปัตยกรรมเป็น 4 ระดับ เหมือนแผนที่ที่ซูมเข้าได้ แต่ละระดับตอบคำถามคนละข้อ และมีผู้อ่านคนละกลุ่ม

ระดับตอบคำถามในภาพมีอะไรในวิชานี้
1 System Contextระบบเราอยู่ตรงไหน ใครใช้ คุยกับระบบอะไรระบบเรา 1 กล่อง · ผู้ใช้ · ระบบภายนอกW11 ทุกทีม
2 Containerระบบแบ่งเป็นกี่ชิ้นที่ต้องรัน แต่ละชิ้นใช้เทคโนโลยีชนิดไหน คุยกันอย่างไรแอปและที่เก็บข้อมูล + ชนิดเทคโนโลยี + เส้นที่บอกว่าส่งอะไรW11 ทุกทีม
3 Componentข้างใน container หลัก แบ่งความรับผิดชอบอย่างไรกล่องความรับผิดชอบ + ข้อมูลที่แต่ละกล่องดูแลW13 เฉพาะ container ที่มีกติกามากที่สุด (ส่วนใหญ่คือ API)
4 Codeแต่ละ action ทำงานอย่างไร ข้อมูลหน้าตาเป็นอย่างไรวิชานี้ใช้ สัญญา action + data model + sequence แทน class diagramW13 สัญญาและข้อมูล · โค้ดจริง = Dev
Container คืออะไร
แอปหรือที่เก็บข้อมูลที่ต้อง “รัน” เพื่อให้ระบบทำงาน เช่น เว็บแอป โปรแกรมฝั่ง server แอปมือถือ ฐานข้อมูล — ไม่ใช่ Docker container
Component คืออะไร
กลุ่มหน้าที่ที่เกี่ยวข้องกัน อยู่หลัง interface ที่ชัดเจน อยู่ ข้างใน container และ deploy แยกเองไม่ได้
ต้องวาดครบ 4 ระดับไหม
ไม่ต้อง — c4model.com แนะนำ Context + Container สำหรับทุกทีม · Component เมื่อมีประโยชน์ · Code เป็นทางเลือก

วิชานี้ลึกแค่ไหน

ENGSE206 เป็นวิชา requirement และ design — เราออกแบบถึงระดับที่ส่งให้ Dev ได้ ส่วนการเลือกสถาปัตยกรรมเชิงลึกเป็นงานของวิชา Software Architecture

ENGSE206 — วิชานี้ (W11–W14)
  • C4 ระดับ 1–2 ทุกทีม (W11) · ระดับ 3 เฉพาะ container หลัก (W13)
  • เริ่มจากโครงพื้นฐาน เว็บ + API + ฐานข้อมูล แล้วเพิ่ม container เมื่อมี requirement หรือ NFR บังคับเท่านั้น
  • เลือก ชนิด เทคโนโลยีจาก NFR/driver พร้อม decision card ≤ 3 ใบ
  • ทุกขั้นใน Spine ทุก driver และทุก NFR ชี้ได้ว่าอยู่ชิ้นไหน
  • ระดับ code ใช้ สัญญา action + data model + sequence ของ Spine (W13)
วิชา Software Architecture — เทอมหน้า ข้อเสนอการแบ่ง
  • เปรียบเทียบ architecture style/pattern หลายแบบ
  • quality attribute scenario และ trade-off analysis เชิงลึก
  • deployment diagram · infrastructure · scaling · reliability
  • ประเมินและปรับปรุงสถาปัตยกรรม (evaluation / evolution)
เส้นแบ่งความลึก
ลึกพอให้ Dev เริ่ม Sprint 1 ได้โดยไม่ต้องเดาโครงสร้าง — ไม่ต้องพิสูจน์ว่าเป็นสถาปัตยกรรมที่ดีที่สุด
W11 ยังไม่ทำ: deployment / server / cloud · microservice / message broker · performance tuning · class diagram · physical schema
