2. System Context (C4 ระดับ 1)

ระบบ 1 กล่อง + ใครมาใช้ + ระบบภายนอก — ตอบคำถามว่า อะไรอยู่ในระบบเรา อะไรอยู่ข้างนอก ยังไม่มีกล่องย่อยในภาพนี้ (ภาพที่ 2 อยู่ท้ายหัวข้อนี้)

มาลองทำไปด้วยกัน
  1. วาดระบบของเราเป็น กล่องเดียว ก่อน — ยังไม่แบ่งข้างใน
  2. เปิดตาราง actor ใน SRS หัวข้อ 2 แล้ววาด ACT-01 ถึง ACT-04 รอบกล่อง
  3. เปิด SRS หัวข้อ 8 (External Interfaces) วาด EXT-01 ถึง EXT-03 และติดป้าย Core / Extension / TBD ตามสถานะใน SRS
  4. ลากลูกศรทุกเส้นพร้อมป้ายว่า ส่งอะไร รับอะไร

ระบบรับผิดชอบ: ข้อมูลทรัพยากรและช่วงเปิด/ปิดรับคำขอ · คำขอจอง · การตรวจความครบและ conflict · การตัดสินใจ · สถานะ · การส่งมอบ/รับคืน · แจ้งเตือนในระบบ · audit trail

ไม่รับผิดชอบ: การเก็บรหัสผ่าน · การเงิน · การซ่อมบำรุงเต็มระบบ · ตารางเรียนต้นฉบับ · การส่งข้อความภายนอกเมื่อยังไม่ยืนยัน integration

ทำไมเขียนแบบนี้
  • Context diagram ไม่มีกล่องภายใน — ถ้าเริ่มวาดกล่องย่อยตั้งแต่ภาพนี้ จะมองไม่เห็นขอบเขต
  • ระบบภายนอกที่ยังไม่ตัดสินต้องติดป้าย TBD หรือ Extension และวาดเส้นประ ไม่วาดเหมือนตัดสินแล้ว
  • ลูกศรทุกเส้นมีป้ายว่าส่งอะไร — ลูกศรไม่มีป้ายไม่ได้บอก Dev อะไรเลย

3. Container diagram (C4 ระดับ 2)

ซูมเข้าไปในกล่อง CRBS: ระบบต้องมี 3 ชิ้นที่ต้องรัน — เว็บแอป · โปรแกรมฝั่ง server · ฐานข้อมูล — แต่ละชิ้นบอกชนิด เทคโนโลยี และหน้าที่ (ภาพที่ 3 อยู่ท้ายหัวข้อนี้)

มาลองทำไปด้วยกัน
  1. ถาม ผู้ใช้ใช้ระบบผ่านอะไร — ทุก actor ใช้หน้าจอทั่วไปบนเบราว์เซอร์ → Web Application
  2. ถาม กติกา BR-01–BR-10 และการตรวจสิทธิ์ต้องอยู่ที่ไหน — ต้องอยู่ฝั่งที่ทีมควบคุม → API Application
  3. ถาม ข้อมูล DR-01–DR-13 เก็บที่ไหน — ต้องเก็บถาวรและมี transaction → Database
  4. ใส่ [ชนิด · stack] ใต้ชื่อทุกกล่อง และเขียนป้ายบนลูกศรว่าส่งอะไร ผ่านอะไร — ในตารางบอกด้วยว่าแต่ละชิ้น รันที่ไหน ใครควบคุม (ดูหัวข้อ 4)
  5. ตรวจว่าระบบภายนอกจากภาพที่ 2 ยังอยู่ครบ และต่อกับ container ที่ถูกชิ้น
Containerหน้าที่ชนิด · stack (Proposed)รันที่ไหน · ใครควบคุมข้อมูลที่เก็บคุยกับ (ส่งอะไร)
Web Applicationหน้าจอของ Requester และ Officer: ค้นหา · ฟอร์มคำขอ · คำขอของฉัน · คิวตัดสิน; แสดงเมนูตาม roleเว็บแอปในเบราว์เซอร์ · Reactเบราว์เซอร์บนเครื่องผู้ใช้ — ผู้ใช้ควบคุมไม่เก็บข้อมูลถาวรAPI Application — เรียก API ค้นหา · ส่งคำขอ · ตัดสิน · ดูสถานะ [REST/JSON · HTTPS]
API Applicationกติกา BR-01–BR-10 · ตรวจสิทธิ์ทุก action · precheck/recheck overlap · เปลี่ยน state · บันทึก AuditEvent และ in-app notificationโปรแกรมฝั่ง server · Node.js + Expressserver ของทีม — ทีมควบคุมไม่เก็บเอง — อ่าน/เขียนผ่าน DatabaseDatabase [SQL · transaction] · EXT-01 [protocol = TBD] · EXT-02/03 (Extension)
Databaseเก็บข้อมูลทั้งหมดของระบบ · แหล่งเดียวของ Confirmedฐานข้อมูลเชิงสัมพันธ์ · PostgreSQLserver ฐานข้อมูล — ทีมควบคุม · เข้าถึงผ่าน API เท่านั้นDR-01–DR-13API Application เท่านั้น
ทำไมเขียนแบบนี้
  • Container คือสิ่งที่ต้อง "รัน" เพื่อให้ระบบทำงาน (แอปหรือที่เก็บข้อมูล) — ไม่ใช่ Docker container และไม่ใช่โฟลเดอร์ของโค้ด
  • หน้าเว็บไม่ต่อฐานข้อมูลตรง ทุกอย่างผ่าน API — จึงมีจุดตรวจกติกาและสิทธิ์จุดเดียว
  • เริ่มจาก 3 ชิ้นก่อน แล้วเพิ่มเฉพาะเมื่อ requirement บังคับ — SRS ของ CRBS ไม่มี FR/NFR ที่ต้องใช้แอปมือถือหรืองานตามเวลา จึงไม่เพิ่ม

4. ชนิดและสภาพแวดล้อมของ container

ก่อนเลือกเทคโนโลยี เราต้องรู้ว่าแต่ละชนิด รันที่ไหน และใครควบคุม — เพราะเป็นตัวตัดสินว่ากติกาและความลับวางที่ไหนได้ (ภาพที่ 4)

เมนูชนิด container — ใช้เลือกชนิดที่ case ต้องการ

ชนิด containerรันที่ไหน / ใครควบคุมเหมาะกับข้อควรระวังตัวอย่างเทคโนโลยี
เว็บแอปในเบราว์เซอร์เครื่องของผู้ใช้ — ผู้ใช้ควบคุมหน้าจอที่ใช้ได้หลายอุปกรณ์ ไม่ต้องติดตั้งผู้ใช้แก้หรือข้ามได้ ห้ามเก็บความลับ ห้ามเป็นที่ตัดสินสิทธิ์หรือกติกาReact · HTML/CSS/JavaScript · Vue
แอปมือถือโทรศัพท์ของผู้ใช้ต้องใช้กล้อง ตำแหน่ง แจ้งเตือนบนเครื่อง หรือใช้ตอนไม่มีเน็ตต้องติดตั้งและอัปเดตผ่าน store งานเพิ่มมากFlutter · React Native
แอป desktopคอมพิวเตอร์ของผู้ใช้ต้องเปิดค้างทั้งวัน หรือใช้อุปกรณ์ในเครื่องต้องติดตั้งทุกเครื่องElectron
โปรแกรมฝั่ง server (API)server ที่ทีมควบคุมกติกาธุรกิจ ตรวจสิทธิ์ เชื่อมระบบภายนอก บันทึก auditต้องออกแบบ API ให้ชัด ต้องเปิดตลอดNode.js + Express · Python + FastAPI · PHP + Laravel
ฐานข้อมูลserver ฐานข้อมูล — ทีมควบคุมเก็บข้อมูลถาวร ค้นหา transactionให้ API เข้าถึงเท่านั้น ไม่ให้หน้าเว็บต่อตรงPostgreSQL · MySQL/MariaDB
งานตามเวลา (scheduled job)server ของทีมงานที่ต้องเกิดตามเวลาโดยไม่มีคนกด เช่น เตือนก่อนถึงเวลาเพิ่มเมื่อมี requirement บังคับเท่านั้นตัวตั้งเวลาบน server (cron)

CRBS เลือกอะไร

ชนิดCRBS ใช้ไหมเหตุผลจาก requirement
เว็บแอปในเบราว์เซอร์ใช้ทุก actor ใช้ผ่านหน้าจอทั่วไป · NFR-06 (flow หลักใช้ keyboard ได้)

  • เบราว์เซอร์อยู่ในเครื่องของผู้ใช้ ผู้ใช้เปิดดูและแก้โค้ดฝั่งนี้ได้ — จึงห้ามเป็นที่ตัดสินสิทธิ์หรือกติกา
  • NFR เลือก "ชนิด" ของเทคโนโลยี ส่วน "ยี่ห้อ" (React, Express, PostgreSQL) มาจาก stack อ้างอิงของรายวิชา — บันทึกไว้ใน DEC-04

5. NFR กระทบ container ไหน

ไล่ NFR ทีละข้อว่ากระทบ container ไหน — ถ้า NFR ยัง TBD เราไม่ออกแบบเกิน

มาลองทำไปด้วยกัน
  1. เปิด SRS หัวข้อ 5 อ่าน NFR ทีละข้อ
  2. ถามว่า ข้อนี้ทำให้ต้องวางอะไรไว้ที่ container ไหน
  3. ถ้า NFR ยังมีค่าเป็น TBD (เช่น NFR-05, NFR-07) ให้เขียนว่ายังไม่ออกแบบ และชี้ OI ที่รออยู่
