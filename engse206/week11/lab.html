Activity A — Context diagram (C4 ระดับ 1)

25 นาทีWorksheet W11-ATemplate หัวข้อ 2ผลงาน: Context diagram

เป้าหมาย ขีดขอบระบบ — อะไรอยู่ในระบบเรา อะไรอยู่ข้างนอก ใครมาใช้ และส่งอะไรกัน (ยังไม่มีกล่องย่อย)

  1. วาดระบบของทีมเป็น กล่องเดียว กลางกระดาษ — ยังไม่แบ่งข้างในผู้วาด
  2. เปิดตาราง actor ใน SRS ของทีม → เติม A1 ทีละตัว: ส่งเข้าระบบอะไร รับอะไรกลับผู้ดำเนินการ
  3. เปิดหัวข้อ External Interfaces ใน SRS → เติม A2 พร้อมป้าย Core / Extension / TBD ตามที่ SRS เขียนผู้ตรวจ ID
  4. ร่างภาพในช่อง A3 ก่อน แล้วผู้วาดวาดใน draw.io — ระบบภายนอกที่ยังไม่ตัดสินใช้ เส้นประผู้วาด
  5. ลากลูกศรทุกเส้นพร้อมป้ายว่า ส่งอะไร — ถ้าเขียนป้ายไม่ได้ แปลว่ายังไม่รู้ว่าเส้นนี้มีไว้ทำไมผู้วาด
  6. ผู้บันทึกเขียน ระบบรับผิดชอบ / ไม่รับผิดชอบ ลงหัวข้อ 2 · export PNG วางในกรอบ “ภาพที่ 1” ของแบบฟอร์ม Wordผู้บันทึก
ดูตัวอย่าง CRBSหัวข้อ 2 System Context
Context diagram ของ CRBS
  • CRBS 1 กล่อง · ACT-01 ถึง ACT-04 รอบกล่อง

  • EXT-02 ตารางเรียน · EXT-03 ช่องทางแจ้งเตือนภายนอก = Extension → เส้นประ
  • ไม่รับผิดชอบ: เก็บรหัสผ่าน · การเงิน · ตารางเรียนต้นฉบับ

ข้อสังเกต
  • Context ตอบแค่ “ขอบระบบ” — ความละเอียดข้างในรอ Activity B
  • ป้าย Core / Extension / TBD มาจาก SRS ไม่ใช่จากความชอบของทีม
  • เขียน “ไม่รับผิดชอบ” ด้วยเสมอ — Dev จะรู้ว่าไม่ต้องสร้างอะไร
จุดที่มักพลาด
  • ✗ วาดกล่องย่อย (หน้าจอ API ฐานข้อมูล) ในภาพนี้→ เก็บไว้ภาพ Container
  • ✗ ระบบภายนอกที่ยังไม่ตัดสินวาดเส้นทึบเหมือน Core→ เส้นประ + ป้าย TBD หรือ Extension
  • ✗ ลูกศรเขียนแค่ “เชื่อมต่อ” หรือไม่มีป้าย→ เขียนว่าส่งอะไร เช่น “ส่งคำขอจอง”
  • ✗ ตั้งชื่อ actor ใหม่เอง→ ใช้ ID และชื่อตาม SRS
ผ่านเมื่อ
  • ระบบเป็นกล่องเดียว ยังไม่มีกล่องย่อย
  • actor ครบตาม SRS ของทีม
  • ระบบภายนอกทุกตัวมีป้าย Core / Extension / TBD
  • ลูกศรทุกเส้นบอกว่าส่งอะไร รับอะไร

Activity B — Container diagram (C4 ระดับ 2)

45 นาทีWorksheet W11-BTemplate หัวข้อ 3–4ผลงาน: Container diagram + ตาราง

เป้าหมาย ซูมเข้าไปในกล่องระบบ — ระบบต้องมีกี่ชิ้นที่ต้อง “รัน” แต่ละชิ้นเป็นชนิดอะไร ใช้เทคโนโลยีอะไร และคุยกันอย่างไร

การ์ดคำถามอ้างตัวอย่าง CRBSไปจบที่
ใครใช้ผ่านอะไรผู้ใช้แต่ละคนใช้ระบบผ่านอะไรUCRequester ค้นหาและส่งคำขอผ่านหน้าจอทั่วไป (UC-01, UC-02)เว็บแอปในเบราว์เซอร์
กติกาอยู่ที่ไหนกติกาหรือการตรวจนี้ต้องอยู่ฝั่งไหนBR / NFRrecheck overlap ก่อน Confirmed (BR-07)โปรแกรมฝั่ง server (API)
ข้อมูลเก็บที่ไหนข้อมูลนี้เก็บถาวรที่ไหน ต้องมี transaction ไหมDRBookingRequest + state (DR-07)ฐานข้อมูล
  1. เขียนการ์ด 3 แบบลง B1 อย่างน้อยแบบละ 3 ใบ ใบละ 1 เรื่อง อ้าง IDทั้งทีม
  2. วางการ์ดบนเมนูชนิดใน B2 — ติ๊ก “ใช้ไหม” เฉพาะชนิดที่มีการ์ดรองรับ และเขียนว่าเพราะ FR/NFR ข้อไหนผู้ดำเนินการ
  3. เริ่มจาก 3 ชิ้น (เว็บแอป + API + ฐานข้อมูล) แล้วตอบคำถาม ชิ้นที่ 4 ต้องมีไหม — มีเมื่อ FR/NFR บังคับเท่านั้นผู้ตรวจ ID
  4. เติมตาราง B3: ชื่อ · [ชนิด · เทคโนโลยี] · หน้าที่ · รันที่ไหน ใครควบคุม · ข้อมูลที่เก็บ · คุยกับใคร ส่งอะไร — ใช้ stack อ้างอิง (ดูรูป L4)ผู้บันทึก
  5. ผู้วาดคัดลอกภาพ Context แล้วซูมเข้า: ระบบภายนอก ชุดเดิม ต่อกับ container ที่ถูกชิ้น · ลูกศรเขียน “ส่งอะไร [ผ่านอะไร]”ผู้วาด
  6. ผู้บันทึกกรอกหัวข้อ 3 (ตาราง container + กรอบ “ภาพที่ 2”) และหัวข้อ 4 (ตอบทุกแถวของเมนูว่าใช้/ไม่ใช้ + เหตุผล)ผู้บันทึก

Container diagram ของ CRBS
  • 3 ชิ้น: Web Application [React] · API Application [Node.js + Express] · Database [PostgreSQL]
  • Web → API: “เรียก API ค้นหา · ส่งคำขอ · ตัดสิน · ดูสถานะ [REST/JSON · HTTPS]”
  • หน้าเว็บ ไม่ต่อ ฐานข้อมูลตรง — ทุกอย่างผ่าน API
  • งานตามเวลา: ไม่ใช้ในรุ่นแรก — ไม่มี FR ที่ต้องเกิดตามเวลา (no-show บันทึกโดย Officer, FR-14)

อ่านภาพนี้อย่างไร
  1. เครื่องของผู้ใช้ — ผู้ใช้เปิดดูและแก้โค้ดฝั่งนี้ได้ → หน้าเว็บห้ามเก็บความลับ และห้ามเป็นที่ตัดสินสิทธิ์หรือกติกา
  2. server ของทีม — ทีมควบคุม → กติกา BR ทั้งหมด การตรวจสิทธิ์ และ audit อยู่ที่ API · ข้อมูลถาวรอยู่ที่ Database
  3. เส้นแบ่งความไว้ใจ — ทุกอย่างที่ข้ามเส้นนี้ต้องผ่าน API เท่านั้น
  4. ใช้เติมช่อง รันที่ไหน · ใครควบคุม ในตาราง container (Template หัวข้อ 3 และ Worksheet B3)

ข้อสังเกต
  • Container = แอปหรือที่เก็บข้อมูลที่ต้อง รัน — ไม่ใช่ Docker ไม่ใช่โฟลเดอร์โค้ด ไม่ใช่หน้าจอ
  • ถ้าการ์ด “กติกา” ทุกใบไปจบที่ API แปลว่าถูกทาง — W13 จะใช้การ์ดชุดนี้แบ่ง component ข้างใน API
  • NFR เลือก ชนิด · ข้อจำกัดของทีมเลือก ยี่ห้อ — วันนี้ใช้ stack อ้างอิงไปก่อน
จุดที่มักพลาด
  • ✗ ตั้งชื่อ container ตามหน้าจอ เช่น “หน้าฟอร์มจอง”→ หน้าจอทุกหน้าอยู่ใน Web Application — ออกแบบใน W12
  • ✗ ให้หน้าเว็บต่อฐานข้อมูลตรง→ ทุกอย่างผ่าน API — จุดตรวจกติกาและสิทธิ์จุดเดียว
  • ✗ ตรวจสิทธิ์หรือกติกาที่หน้าเว็บ→ ผู้ใช้แก้หรือข้ามได้ — ตรวจที่ API
  • ✗ เพิ่มแอปมือถือ microservice หรือ message broker “เผื่อไว้”→ เพิ่มเมื่อมี FR/NFR บังคับเท่านั้น
ผ่านเมื่อ
  • เริ่ม 3 ชิ้น และทุกชิ้นที่เพิ่มมี FR/NFR รองรับ
  • ทุกกล่องมีชื่อ + [ชนิด · เทคโนโลยี] + หน้าที่
  • ตาราง container บอกรันที่ไหน ใครควบคุม และข้อมูลที่เก็บ
  • ลูกศรทุกเส้นบอกว่าส่งอะไร ผ่านอะไร
  • ระบบภายนอกตรงกับภาพ Context
  • ตอบทุกแถวของเมนูชนิดว่าใช้/ไม่ใช้ พร้อมเหตุผล

เป้าหมาย ไล่ NFR ทุกข้อว่ากระทบ container ไหน แล้วเขียนเหตุผลของการตัดสินใจที่ Dev จะถามว่า “ทำไม” เป็น decision card

  1. เติม C1 ทีละ NFR: ต้องการอะไร (สั้น ๆ) → กระทบ container ไหน → ออกแบบแล้ว (DEC) หรือ TBD (OI)ผู้ดำเนินการ
  2. NFR ที่ค่ายังเป็น TBD ให้เขียน TBD + OI ที่รอ และ “ยังไม่ออกแบบ” — ห้ามเดาตัวเลขเองผู้ตรวจ ID
  3. เลือก 3 เรื่องใน C2 ที่กระทบ container มากที่สุด — มักเป็นที่อยู่ของกติกา · ที่เก็บข้อมูล · ผู้ใช้ใช้ผ่านอะไรทั้งทีม
  4. เขียน decision card 3 ใบใน C3: ตัดสินใจ · เพราะ (NFR/driver) · ทางเลือกที่ไม่เลือก · ผลที่ตามมา — สถานะ Proposedผู้บันทึก
  5. ใบที่ 4 เรื่อง stack บังคับ เมื่อทีมเปลี่ยนจาก stack อ้างอิง — อ้าง NFR หรือข้อจำกัดของทีม · ถ้าใช้ stack อ้างอิง จะเขียนแบบ DEC-04 ของ CRBS หรือไม่เขียนก็ได้ผู้ดำเนินการ
  6. ผู้บันทึกวางการ์ดทั้งหมดในช่อง 3 ของ frame Miroผู้บันทึก
  7. ตอบ sticky ชมพูจาก Checkpoint 1 — คำตอบมักอยู่ในการ์ดใบใดใบหนึ่งทั้งทีม

ข้อสังเกต
  • NFR ทุกข้อต้องมีที่อยู่ในแบบ หรือถูกบันทึกว่ารอใครตอบ — ไม่มีข้อที่ “ลอย” อยู่
  • card ที่หา NFR หรือ driver มาอ้างไม่ได้ อาจเป็นเรื่องที่ไม่ต้องตัดสินในสัปดาห์นี้
  • Proposed = ข้อเสนอของทีมออกแบบ · Dev ยืนยันหรือขอเปลี่ยนได้ (ส่งมอบใน W14)
จุดที่มักพลาด
  • ✗ NFR performance ยังไม่มีตัวเลข แต่ใส่ cache ไว้ก่อน→ เขียน TBD ชี้ OI แล้วบันทึกเป็น open decision
  • ✗ decision card ไม่มี “ทางเลือกที่ไม่เลือก”→ ใส่ทุกใบ — แสดงว่าเปรียบเทียบแล้ว ไม่ได้เลือกเพราะชอบ
  • ✗ เลือกยี่ห้อเทคโนโลยีโดยไม่มีเหตุผล→ ใช้ stack อ้างอิง หรือเขียนใบที่ 4 อ้าง NFR/ข้อจำกัด
  • ✗ เขียนสถานะ card ว่า Approved→ สถานะ Proposed เสมอในสัปดาห์นี้
ผ่านเมื่อ
  • NFR ทุกข้อของ SRS ทีมอยู่ในตาราง
  • NFR ที่ TBD ไม่มีตัวเลขแต่ง และชี้ OI
  • decision card ≤ 3 ใบ (+1 ถ้าเปลี่ยน stack) อ้าง NFR/driver ทุกใบ
  • ทุกใบมี “ทางเลือกที่ไม่เลือก” อย่างน้อย 1 ทาง
